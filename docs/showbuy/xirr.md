## 二、核心假设与约束

### 2.1 业务假设
1. ShowBuy 是面向个人投资者的投资记账工具，核心场景是不定期、不定额的开放式投资。
2. 用户对年化收益率的认知基准是支付宝/理财通/Excel 的 XIRR 结果。
3. 99% 的用户交易记录数量不超过 10000 条。
4. 货币基金/逆回购属于“活钱管理”，不视为投资资产，不参与收益率计算。
5. 账户资金划转（`deposit`/`withdraw`）属于内部资金调度，不是投资行为，不参与收益率计算。

### 2.2 技术约束
1. 必须支持 SQLite 数据库，不能引入额外的服务依赖。
2. 所有计算必须在后端完成，前端只负责展示。
3. 必须保证极端环境下的可用性（无网络、老旧系统）。
4. 严格遵循 SPEC 15.2 条：按需开发，只实现需求明确要求的功能，不提前预埋。

### 2.3 架构约束
1. 货币基金/逆回购的交易会记录在 `transactions` 表中，但不创建持仓。
2. 所有服务层目录保持统一风格：`app/services/{功能域}/`。
3. 外部调用方只能访问 `__init__.py` 导出的接口，不感知内部文件划分。

## 三、技术决策（最终版，所有争议点已明确）

### 决策 1：XIRR 计算引擎

**最终结论**：优先使用 `pyxirr` 库，保留 xalpha 纯 Python 实现作为兜底。

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| pyxirr（Rust 实现） | 与 Excel 完全一致（ACT/365 日计数惯例）；性能极快（10-20 倍于纯 Python）；零外部依赖（预编译 wheel） | 极少数老旧平台可能需要编译 | **首选** |
| xalpha 纯 Python 实现 | 零依赖；100% 兼容所有环境；经过多年生产验证 | 性能较慢；少数边界条件与 Excel 有微小差异 | **兜底** |
| numpy-financial | — | 收敛性差、结果与 Excel 不一致、依赖 numpy | **不采用** |
| scipy.optimize | — | 性能极差、收敛性问题 | **不采用** |

**选择理由**：
1. 用户会用支付宝/理财通/Excel 的 XIRR 结果比对，“与 Excel 一致”是信任基础。
2. pyxirr 在 99.9% 的部署环境下可直接安装预编译包，无需编译环境。
3. 纯 Python 兜底只在 pyxirr 不可用时激活，保证极端环境下 100% 可用性。

**实现要求**：
- 使用 try/except 导入 pyxirr，失败时自动降级为纯 Python 实现。
- 降级时通过 loguru 记录 warning 日志。
- 两种实现必须返回一致的结果格式。
- 所有实现返回的年化收益率必须限制在 **[-1, 10]** 范围内（即 -100% 到 1000%），超出此范围视为异常值，返回 0.0。

---

### 决策 2：收益率计算方式

**最终结论**：聚焦 XIRR（内部收益率），不做简单年化收益率，不做 TWR（时间加权收益率）。

**理由**：
- ShowBuy 用户场景是典型的**开放系统**（随时买卖、定投、赎回），XIRR 是唯一科学的衡量指标。
- 简单年化收益率在开放系统中没有意义（无法定义“总投入”和“持有天数”）。例如：投入 1 万元赚 1000 元（年化 10%），再投入 10 万元，总收益还是 1000 元，简单年化会变成不到 1%，完全失真。
- TWR 更适合作封闭系统的业绩归因，属于 P2 专业功能。

**xalpha 概念对齐**：
- ShowBuy 是 xalpha 中的 `mul` 系统（开放组合），使用 `xirrrate()` 方法。
- ShowBuy 不是 `mulfix` 系统（封闭组合），不做净值曲线。
- 净值曲线作为 P2 辅助功能，在“无资金进出”时间段可选展示。

### 决策 4：资产类型排除规则与数据架构变更

**最终结论**：以下资产类型的交易**存在**于 `transactions` 表中，但**不参与** XIRR 计算，包括其历史交易和当前持仓市值。

| 排除类型 | 决策理由 |
|----------|----------|
| money_fund（货币基金） | 属于活钱管理，收益率极低，无净值波动，与投资能力无关 |
| reverse_repo（逆回购） | 同货币基金，属于现金管理 |
| cash（现金） | 不是投资资产 |

**关键架构变更**：为精准过滤，在 `Transaction` 模型新增 `asset_type` 字段（列名 `type`），作为资产类型快照。理由：
1. 孤儿交易（`position_id` 为空）无法通过关联 `Position` 表获取类型，必须存储快照。
2. 与 `position_name`、`account_name` 快照字段设计完全一致。
3. 避免 XIRR 计算时 JOIN 表查询，提升性能。
4. 历史数据通过 SQL 回填，新数据在导入时自动写入。

**实现方式**：`generate_cashflows` 通过 `asset_type NOT IN ('money_fund', 'reverse_repo', 'cash')` 显式过滤。同时，在 `orchestrator.py` 的 `_fill_names_and_types` 中采用**元数据查询 + 关键词临时兜底**双重机制识别货币基金。

> **注意**：关键词兜底（`['货币', '现金', '宝', '增利', '天天益']`）为临时方案，待元数据同步完全覆盖货币基金类型后移除。此决策已记录为技术债务。

---

### 决策 5：分红再投资与现金流方向规则（修正）

**最终结论**：现金流只包含以下四类投资交易，账户资金划转（`deposit`/`withdraw`）**不参与**。

| 交易类型 | 现金流方向 | 符号 | 说明 |
|----------|-----------|------|------|
| buy（买入） | 流出 | 负（-） | 实际投资买入 |
| dividend_reinvest（红利再投资） | 流出 | 负（-） | 视为用分红金额再投入 |
| sell（卖出） | 流入 | 正（+） | 实际投资卖出 |
| dividend_cash（现金分红） | 流入 | 正（+） | 现金分红收入 |
| 当前持仓总市值（虚拟卖出） | 流入 | 正（+） | 计算截止日的持仓估值 |

**排除 `deposit`/`withdraw` 的原因**：实际运行中发现，账户资金划转（如银行转证券）被当作投资现金流出，严重拉高了“总投入”的计算基准，导致 XIRR 出现畸高异常值（如 697%）。这些划转属于内部资金调度，不是投资行为。

---

### 决策 6：虚拟卖出逻辑（保持不变）

**最终结论**：所有非排除类型持仓的当前市值**合并为一笔总市值现金流**，不按持仓分开处理。

**理由**：数学上完全等价，减少现金流数量，代码更简洁。

### 5.2 统一返回格式（已更新）

所有计算器返回完全一致的结构：

```python
{
    "xirr": 0.1234,              # 年化收益率
    "total_invested": 50000.00,   # 总投入（买入 + 红利再投资）
    "current_value": 58000.00,    # 当前持仓市值
    "total_withdrawn": 8000.00,   # 历史累计收回金额（卖出 + 现金分红，不含虚拟卖出）
    "total_return": 88000.00,     # 总收益（current_value + total_withdrawn - total_invested）
    "cashflow_count": 15          # 参与计算的现金流笔数
}
```

# 净资产口径（`net_worth`）与现金腿

> 状态：**生效**（2026-11-10，D98，源 [#3039](https://github.com/imoyao/fundmate/issues/3039)）
> 实现：`backend/app/services/pnl_calendar.py`（收益日历分母）、`backend/app/services/summary_service.py`（账户 / 家庭汇总）
> 口径同源：[`cashflow-layers.md`](./cashflow-layers.md)（L1 外部资金流 / L2 资产转换 / 内部划转配对）

## 1. 为什么需要这一份口径

「我的资产是多少」这个问题，仓里有**三个**出口，各自都能算出一个数，且都没有报错：

| 出口 | 算法 | 实际行为 |
|---|---|---|
| `summary_service.get_summary_data` | 按 `ledger_id` 分桶，`total_assets − total_liabilities` | 正确分桶；但**现金行不存在**，所以「现金」这一块是 0 |
| `pnl_calendar` 的 `net_worth` | `Σ持仓市值 + Σ累计已实现`（`pnl_calendar.py:1462`） | 不含现金，且把已实现**再加一次** |
| 前端「收益率」分母 | 取 `pnl_calendar` 的 `net_worth` | 继承上一条的全部缺口 |

同一个账户，资产总览显示 A、收益日历的分母是 B，两个数都不报错。**先统一语义，再谈哪个更准。**

## 2. 定义

### 2.1 账户净资产

```
账户净资产 = Σ该账本持仓市值 + 该账本名下现金 + 该账本其他资产 − 该账本负债
```

**每一项都只取该账本自己名下的行**。禁止从别的账本借行进来。

### 2.2 家庭净资产

```
家庭净资产 = Σ账户净资产
```

`summary_service._bucket`（`summary_service.py:165-195`）已经是这个结构：逐 `ledger_id` 入桶，出口 `net_worth = total_assets − total_liabilities`。**`Σ账户桶 ≡ 家庭桶` 是构造出来的恒等式**，不是两边各自算对来维持的。

### 2.3 日历口径（`pnl_calendar`）的范围

日历只回答「投资这件事赚没赚」，故**范围比家庭净资产窄**：

| 计入 | 不计入 |
|---|---|
| 投资类持仓市值（`positions`） | 房产、应收应付等静态资产 |
| 现金账本余额（`Asset(major_category='cash')`） | 家庭负债（房贷等） |

**这是故意的范围差异，不是口径打架。** 判定标准：这个数会不会随「我今天买卖了」而变。房产不会，因此不进日历。

## 3. 现金：存量单点持有

### 3.1 只有一处落点

现金**余额**是存量，只存在于**现金账本自己名下**的一行 `Asset(major_category='cash')`。判据一句话：

> **同一笔钱在同一时刻只能有一个落点。**

因此 `net_worth` 取现金的方式是**一条固定的行查询**，不是一次遍历：

```python
# 唯一合法形态：只查现金账本自己
db.query(func.sum(Asset.amount)).filter(
    Asset.ledger_id == cash_ledger_id,
    Asset.major_category == MAJOR_CATEGORY_CASH,
).scalar()
```

参考实现：`ledger_service.get_cash_balance`（`ledger_service.py:288-304`）。

### 3.2 `linked_cash_ledger_id` 只做展示，**禁止**用于累加

`ledgers.linked_cash_ledger_id` 的语义是「点进证券账户，能顺带看到关联银行余额」——**导航**，不是归属。

实测（2026-11-10，真库副本）：指向账本 3 的账本有 **8 个**（12 / 13 / 15 / 16 / 17 / 20 / 21 / 26）。若按「每个引用方账本都把关联现金余额并入自己的 `net_worth`」实现，同一笔钱会进 **8 次**。

> 这是本规范的**核心禁令**。它曾经以「家庭级会重复计 7 次」的说法被写进 issue，但那是**假设实现的后果**，不是现状——实测现状是现金**一次都没计**。两件事都要防：既不能展开 8 次，也不能因为怕重复就干脆不算。

### 3.3 流转（流量）不改总额

账户间转账 = 同一笔事件的两个分录：转出方 `withdraw`、转入方 `deposit`，金额相等、方向相反。

- 对**家庭**：一进一出净额为 0，**不进外部现金流、不入 XIRR、不改家庭净资产**；
- 对**单账户**：仍是真实的资金进出（对 A 是出金、对 B 是入金），账户页照常展示。

配对判定**复用** `cashflow_layers.pair_internal_transfers`（`cashflow_layers.py:102-145`）：同日 + 同额（分精度）+ 方向相反 + 不同 `ledger_id`。**禁止另写一份。**

### 3.4 为什么 `net_worth` 不该再 `+ Σrealized`

已实现盈亏**已经通过现金体现**（卖出所得进了现金余额）。再把它加进净资产就是双计：

| 时点 | 市值 | `realized` | 现在（`市值 + realized`） | 应为（`市值 + 现金`） |
|---|---|---|---|---|
| 买入 100 元 | 100 | 0 | 100 | 100（现金 0） |
| 涨到 120 后卖出 | 0 | +20 | **20** | **120**（现金 120） |

右列才是真值。左列缺的是**本金回笼**那 100 元——它卖出后既不在 `positions`，也没有现金承接。

> 这正是 #3037 只能用「清仓后保留残值 `realized − fee_cum`」止血的机理：那一步保住的是**已实现**，保不住**本金**。本金要有载体，只能是现金。

## 4. 历史余额从哪来（以及拿不到时怎么办）

`Asset.amount` 只有**当前值**，没有时间序列。历史某日的现金余额只能回放：

```
历史余额(d) = 当前余额 − Σ(日期 > d 的现金类流水净额)
```

其中「现金类流水」= `deposit` / `withdraw` / `interest` / 已配对的内部划转；**不含** `buy` / `sell` / `dividend`（那些是资产转换与收益实现，已体现在市值与现金的相互转换里，重复计入会二次计算）。

**回放的前提是流水完整。** 流水缺失时：

- 回放值会偏大或偏小，且**没有任何报错**；
- 正确做法是让该区间的 `rate` / `range_rate` 返回 `None`（前端「—」+ 成因文案），**不得**用回放值硬算；
- 判据：拿不到完整输入 ⇒ 结论不可信，显式声明，不退化成一个看起来正常的数字。

## 5. 判据

| 判据 | 形态 |
|---|---|
| 现金只算一次 | 构造「8 个账本共享同一现金账本」的用例，断言家庭 `net_worth` 只含该现金**一次** |
| 可加性 | `Σ账户桶 ≡ 家庭桶`（`summary_service` 的结构恒等式，改动不得破坏） |
| 缺数据不冒充 | 现金行为 0 或流水不全时，`rate` / `range_rate` 返回 `None` 而非 `0` |
| 不双计 | `net_worth` 不再 `+ Σrealized`；`daily_pnl` 的 `level` 公式（`市值 − 成本 + realized − fee`）**独立于** `net_worth`，不得联动修改 |
| 流转净额 0 | 「A 转出 + B 转入（同日同额）」时，家庭净资产变化 = 0 |

## 6. 明确不做的事

- **不把静态资产**（房产、应收应付）塞进收益日历——日历只回答「投资赚没赚」；
- **不展开 `linked_cash_ledger_id`**（见 §3.2）；
- **不从流水反推当前余额**：未记录的流水会被静默算成收益（`cashflow-layers.md` §7 已明文反对）；
- **不为凑出历史数字而编造现金余额**：缺数据时显示「—」是正确答案，不是缺陷；
- **不改 `summary.net_assets_cny` 的现有结构**：它已按 `ledger_id` 正确分桶，本规范只要求「现金那一行真的存在」，不改累加方式。

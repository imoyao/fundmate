## 3. 由矩阵得出的裁决

### 3.1 「聚合页 = 详情页的聚合视图」这一自我描述不成立

`position-analysis/index.vue:7-12` 的分工表写着「组合档 = 详情页核心块的聚合视图」「账户档同理」。但矩阵显示：

- **组合档与组合详情页 100% 重叠**（归因/结构/穿透全同）⇒ 若严格按此表，组合详情页应当是「无意义的重复页」。**显然不是。**
- 真实关系是：**组合详情页 = 该组合的分析视图；聚合页 = 可切换口径的分析视图**。两者是**同源内容的两个入口**，不是「一个是另一个的子集」。

⇒ 原分工表的措辞（"= 详情页核心块的聚合视图"）**有歧义**，它把「可切换」误表述成「子集关系」。**这是我原文档 §2.3 引用它时的判断错误**——我不该把它当"详情页不该有分析块"的依据。

### 3.2 三页同源 ≠ 功能冗余

聚合页 / 组合详情页 / 账户详情页 都用同一批组件，**但服务的意图不同**：

| 页面 | 用户此刻的问题 | 需要的交互 |
|---|---|---|
| 聚合页 | 「我的钱整体怎么样？换个账户/组合看看？」 | **切换**（口径选择器在页面顶部，是页面的主角） |
| 组合详情页 | 「这个组合长什么样？」 | **深读**（11 个分区 + 页内目录 + 锚点导航） |
| 账户详情页 | 「这个账户的钱压在哪儿？」 | **深读 + 操作**（持仓明细、流水都在这页） |

**判定：同源组件 ≠ 功能冗余。** 冗余的判据是「同一页面上同一内容出现两次」或「两个入口给出**矛盾**的口径」，不是「两个页面用了同一个组件」。

### 3.3 账户详情页的缺位是**真缺口**，不是设计选择

三个事实交叉验证：

1. 组合详情页有 `nav-structure` / `nav-penetration` 两个正式分区；
2. 账户详情页**已有** `PnlCalendar` / `PnlAttribution` / `CashFlowPanel` 三块分析块 —— **同类的分析块在详情页内嵌是既有实践**，不是新开先例；
3. 账户详情页**已有** `LedgerDetailHoldingsPane`（持仓明细）与 `LedgerDetailTransactionsPane`（流水）—— 用户在这个页面的意图是**深读 + 操作**。

而账户详情页恰恰**独缺**「持仓结构 / 穿透」两块，被一块写着「规划中，敬请期待」的假占位卡占据。

⇒ **组合详情页有的、账户详情页没有的，正是这两块；而账户详情页的分析块密度本来就不低于组合详情页。** 缺位是历史遗留（2026-08-27 移除环形图后用占位卡填空），不是「详情页不该有分析」的设计决定。

### 3.4 真正的冗余风险不在「详情页 vs 聚合页」，在「聚合页 vs 组合详情页」

矩阵显示组合档与组合详情页 100% 重叠。**这才是需要 owner 留意的冗余点**，但它**不在本卡范围内**——组合档的价值在于「切换」，若用户只想看一个组合，直接进组合详情页即可，聚合页的组合档是「切换到别的组合」的快捷方式。这是合理的。

本卡若强行把账户档与账户详情页也做成 100% 重叠，才是**制造**冗余——所以实现必须走 §3.5 的「账户详情页内嵌，但不做口径切换器」路线。

### 3.5 因此，正确的形态是「深读型内嵌」，不是「切换型镜像」

若在账户详情页镜像聚合页的全部内容（口径切换器 + 四卡 + 日历 + 归因 + 结构 + 穿透），**那才是冗余**——详情页已经有了日历、归因、超额四卡。

**账户详情页应该补的只有它缺的那两块**（结构 / 穿透），沿用组合详情页的**内嵌分区模式**（`nav-structure` / `nav-penetration`），**不搬口径切换器、不搬已存在的块**。

## 4. 页面冗余度实测（担心「页面过长」）

组合详情页有 **11 个分区**、纵向明显超一屏（其注释原文：「纵向区块 9 个、明显超一屏，符合 components.md 的 PageToc 接入判据」），且它**已经接受了这个长度**（专门做了 TOC rail + 锚点胶囊）。

账户详情页当前分区（`LedgerDetailOverview` + `detail.vue` 合并计）：账本概览 / 账外类现金 / 收益日历 / 收益归因 / 占位卡 / 资金流动 / 持仓明细 / 流水 —— 约 7~8 块。

**加 2 块 ⇒ 约 9~10 块**，与组合详情页同量级。**结论：页面长度不构成否决理由**，但需补页内导航（见设计文档 §6）。

## 5. 落地后复核（2026-10-29，owner 裁定 B′ + 补导航）

§1 的矩阵是实现前快照。落地后（PR #2745）：

| 分析块 | 持仓分析 | 账户详情页 | 组合详情页 |
|---|:---:|:---:|:---:|
| **持仓结构 / 集中度** | ✔ | **✔（本 PR）** | ✔ |
| **持仓穿透 / 行业分布** | ✔ | **✔（本 PR）** | ✔ |

**冗余结论复核：矩阵变化没有制造冗余。** §3.1 指出真实关系是「同源内容的两个入口，不是子集」——账户详情页补上这两块后，它与聚合页的**账户档**在同一块内容上 100% 重叠，与组合详情页的情形**同构**（组合档也与组合详情页 100% 重叠）。既然「组合档 ↔ 组合详情页」的重叠被判定为合理（§3.4：聚合页的价值在「切换」，详情页的价值在「深读 + 操作」），那么「账户档 ↔ 账户详情页」的重叠同样是合理的——**两个入口的意图分工没变，重叠面积变大不等于冗余**。

**两处措辞/口径的同步**：

- `position-analysis/index.vue:7-12` 的分工表措辞**已更正**：「组合档 = 详情页核心块的聚合视图」「账户档同理」⇒ 改为「组合档 / 账户档与详情页**同源同口径**（同一批面板/端点）」，并补一段说明二者是**并列入口**而非子集。聚合页的**口径与端点一字未动**（owner 裁定 3：不加深链）。
- 账户详情页的这两块与聚合页**用的是同一对组件、同一对后端端点**，口径切换控件（集中度两档 / 穿透两档）也沿用组件自带的那一套 ⇒ 同一账户在两处看到的数字**必然一致**，不存在「同数据不同数」的风险。

**新增的一条纪律（本次实现的副产品）**：账户口径的数字 id 必须走**有限数字**过滤（`useLedgerDetail.ledgerIdNum`）。原先各处的 `Number(p.ledgerId)` 在「未归置持仓」伪账户上算出 NaN，NaN 被后端按「不传」处理 ⇒ 静默退回家庭级。矩阵类文档看不到这类退化，故补记在此。

## 5. 独立评估的最终结论

| 问题 | 结论 |
|---|---|
| 聚合页与详情页已产生功能冗余了吗？ | **没有**。二者是同源组件的两个不同意图入口（切换 vs 深读），不产生矛盾口径。 |
| 真实冗余点在哪？ | 聚合页「组合档」与组合详情页 100% 重叠——但那是「切换 vs 深读」的合理重叠，不在本卡范围。 |
| 账户详情页该不该有集中度/行业分布？ | **该有**。组合详情页有这两个正式分区，账户详情页同类的分析块密度不低于它，独缺这两块且被假占位卡占据——是历史遗留缺口。 |
| 该复制聚合页整页吗？ | **不该**。只补缺的两块，不搬口径切换器、不搬已有块——搬整页才是制造冗余。 |

# 资金流水分层口径（L1/L2/L3）

> 状态：**生效**（2026-10-25，D67，源 #2615）
> 实现：`backend/app/services/performance/cashflow_layers.py`（唯一入口）
> 消费方：组合 / 账户 XIRR（`xirr_engine.py`）、账户资金流动区块（#2616）、三级视图聚合（#2595）

## 1. 为什么需要这一份口径

「总投入 1.68 亿 / 总收益 −1886 万」这类数字的根因不是算术错，而是**每个页面各自决定「哪些交易算投入」**：

| 出口 | 过去的做法 | 问题 |
|---|---|---|
| 组合 XIRR | 把买入当投入，完全不看入金/出金 | 答的是「这些持仓赚了多少」，不是「我的账户赚了多少」 |
| 收益日历 | 按日市值差分（`daily_pnl` 天然剔除资金流） | 本身正确，但与上面不同源 |
| 账户页 | 没有资金流动视图 | 用户无法解释「为什么收益和账户余额对不上」 |

同一份事实算出几个不同口径，页面之间就永远对不上。故本规范只做一件事：
**按层分类，让每个消费方显式声明自己使用哪几层**。

## 2. 四层定义

判据一句话：**交易对手方是否跨出「本账户集合」**。

| 层 | 交易类型（`transactions.txn_type`） | 算盈亏 | 算外部现金流 | 进账户口径 XIRR |
|---|---|---|---|---|
| **L1 外部资金流** | `deposit` / `withdraw`（未被内部划转配对） | 否 | **是** | 是 |
| **L2 资产转换** | `buy` / `sell` / `dividend_reinvest` / `split` | 否 | 否 | 否 |
| **L3 收益实现** | `dividend` / `dividend_cash` / `bond_redeem` / `tax` | 是 | 否 | 否 |
| **L4 估值变动** | 未实现浮盈浮亏（来自持仓市值，**无流水**） | 是 | 否 | 终端虚拟卖出 |

- **L1 与 L2 的区别就是这张表的全部价值**：入金让账户钱变多（外部来的），买入只是把现金换成基金（钱还在账户里）。
  把两者都当「投入」，等于把同一笔钱数两遍。
- L3 是「已经落袋的收益」，计入盈亏但不构成外部现金流（钱本来就在账户里转）。
- L4 不进流水表，由持仓市值在区间末端以「虚拟卖出」进入 XIRR。
- 未登记类型（如历史 `other`）**不猜层**：单列到 `unknown`，让「有多少笔没被归类」可见。

## 3. 内部划转（家庭内账户互转）

配对条件：**同日 + 同额（分精度）+ 方向相反 + 分属本集合内不同账户（按 `ledger_id`）**。

- 一进一出净额为 0，**组合级**不应出现在资金流动总额或 XIRR 里；
- **账户级**仍是真实的资金进出（对 A 是出金、对 B 是入金），账户页照常展示；
- 按 `ledger_id` 判定，不按账户名——同名账户串味会把外部入金误当划转剔掉（历史 bug）。

**2026-10-27 落地（#2681）**：`cashflow_layers.build_layers` 在 `totals` 累加时跳过被配对的流水
（每条 flow 带 `internal_transfer=True` 标记，`l1` 桶仍保留以便诊断）；消费方展示逐笔流水 /
月度柱状 / 累计净投入曲线时须同样按该标记过滤，否则出现「列表里有、总额里没有」。
此前本规范已规定「组合级不应出现在总额里」，但实现只把配对标进了 `basis_by_ledger`，
`totals` 照旧累加——组合级接入时才暴露成「外部入金 5 万 + 组合内划转 1 万 = 显示 6 万」。
账户级（单账本传入）配不上对，行为不变。

> 2026-10-25 修复：`xirr_engine.generate_portfolio_cashflows` 此前把配对结果赋给 `_` **丢弃**
> （`_ = _exclude_internal_transfers(...)`），看起来过滤了、实际什么都没做。现由
> `cashflow_layers.pair_internal_transfers` 统一判定，配对结果真正参与现金流构造。

## 4. 净投入与现金残差

- **净投入 = 累计入金 − 累计出金**（用户视角「我一共压进去多少」）。

  > 刻意**不**把已实现盈亏混进来。#2615 卡面示例写「入金 10 万 / 出金 2 万 → 净投入 7 万」，
  > 其中 7 万来自「10 − 2 − (卖出 9 − 买入 8)」，把赚到的钱从投入里减掉——那是收益，不是投入。
  > 本规范取 8 万；已实现盈亏单独作为收益项展示，两者不相减。

- **现金残差 ≈ 入金 − 出金 − 买入 + 卖出 + 现金分红 + 兑付 − 税费**（账户现金视角）。
  红利再投与份额拆分**不动现金**，不进任何一侧。
  它用于解释「账户余额去哪了」，**不是**对账单，缺失的流水会让它偏大/偏小——页面必须注明是推导值。

## 5. 逐账户口径与降级（关键）

组合内账户常常混着两种数据状态：老账户只导过交易、新账户认真记了入金。故口径**按账户判定**：

| 账户状态 | 口径 | 现金流构造 |
|---|---|---|
| 有真实 L1 入金/出金 | `account` | 只有 L1 进出算投入/回收，买卖不进现金流 |
| 只有交易、没有入金流水 | `position`（降级） | 沿用历史行为：买入算投入、卖出/分红算回收 |

整组合按 `account` 一刀切会让老账户丢掉本金 → 现金流里只剩终端虚拟卖出 → **年化 0%，比改之前更糟**。
故 API 必须回填口径（`cashflow_basis: account|position|mixed`），页面据此提示
「未记录入金，按买入成本估算」——**不能让两种口径的数字并排展示却不说**。

## 6. 单位纪律

`transactions.amount` 存的是**分**。`cashflow_layers` 对外一律返回**元**（`Money.cents_to_yuan`）。
消费方不得再换算一次——#2610 的 100 倍错误（总投入 1.68 亿）就是二次换算/漏换算造成的。

## 7. 明确不做的事

- **不改收益日历**：`daily_pnl` 按日市值差分，天生免疫资金流，是这条链上的正确实现（TWR 也吃它）。
- **不用「账户余额变化」反推收益**：余额包含未记录流水，反推会把缺数据算成收益。
- **不在本层做盈亏归属**（哪笔卖出赚了多少）：那需要成本配对（FIFO/加权），属独立议题；本层只做
  「这笔钱是哪一类」。
- **不为 `unknown` 类型兜底猜层**：猜错比留空更贵，留空至少能看见。

## 8. 回归网

`backend/tests/services/performance/test_cashflow_layers.py`（5 条）+ `test_xirr_engine.py`、
`test_portfolio_xirr_units.py`（既有 106 条同目录用例）。钉的是**口径本身**：

- 入金/出金必须在 L1、买入/卖出必须在 L2、现金残差符号（账户视角）；
- 内部划转配对后组合净额为 0 且不进 XIRR 现金流；
- 有入金的账户走 `account`（买入不进现金流），只导交易的账户降级 `position`；
- 组合内混着两种账户时报 `mixed`，不假装单一口径。

# 基金净值数据保留期与瘦身：分层保留方案

> 定稿：2026-10-13 · 性质：**数据策略决策 + 执行计划**（已拍板，执行分 P0/P1/P2）
> 权威全文在本文；GitHub issue 只做跟踪与拆卡，不承载全文。
> 关联：#1396（基金公司覆盖率）、#2118（风险指标调研）、`docs/spec/data-strategy.md`（D21 数据策略）

## 1. 结论摘要（已拍板）

| 决策 | 结论 |
|---|---|
| **热集保留** | **全历史，不删**（持仓/自选/流水 = 121 只，其中 107 只有净值，仅占 2%） |
| **冷集保留** | **近 1 年**（约 250 交易日/只）→ 全表留存约 13%，删除约 **87%** |
| **1 年还是 3 年** | 取决于「是否做全市场选基」（见 §7）；当前按 D21「当前无此产品需求」→ 取 **1 年** |
| **先补后清** | 先补货基 `annual_return_7d`（当前填充率 **0%**）与「冷集长曲线按需取」能力，再动存量 |
| **不动 `equity_position`** | 回填它是 #1403 限流炸弹；改用 `fund_type_id`/`fund_variety_id` 类型过滤替代 |

**为什么热集要留全历史而不是 3 年**：我们**已经对外声明了档位**——`fund_performance.py` 的 `_PERIODS` 含 `1y/2y/3y/5y/ytd/since`。热集若只留 3 年，同一只基金的 `5y` 与「成立以来」档会**时有时无**，即「同一只基金、同一接口、不同时间返回不同档位」，属对外契约不稳定（埋坑 + 反复工作）。留全历史成本仅 2%，没有理由省。
## 2. 决定性事实：哪些指标自算、哪些上游拉

| 品类 | 指标来源 | 依赖本地序列？ |
|---|---|---|
| **基金（场外）** | **全部自算**：`fund_performance.py` 从 `daily_worth.acc_nav` 日频算区间收益 / 最大回撤 / 年化波动率；未来的 UI / UPI / 夏普 / 波回比 / 胜率（#2118）同理 | **是，承重数据** |
| 投顾组合 | **上游拉**：天天基金 `SYL_*` → `return_1w/1m/1y/ytd/since_incep` + `max_drawdown`（上游另提供 `sharpe_ratio`/`volatility`，覆盖率 92~96%，我们尚未落库） | 否，存一列即可 |
| 股票 | 自算（`price_history.close`） | 是，承重数据 |
| 指数 | PE / 股息率 / 分位基线均为上游拉（`index_valuations` 仅最新一期；`index_valuation_baselines` 乐咕月频近 5 年，#1407） | 否 |

**推论（决定整件事的逻辑）**：

- `daily_worth` 的日频序列是**自算的前提**，因此「长曲线按需从天天基金取」成立；但「**指标改成从天天基金拉**」**不可取**——那会丢掉口径控制权（§3.10 要求指标自带 `window`/`as_of`/`basis`，且要解释 `acc_nav` 是「分红不再投近似复权」与天天口径的差异）。
- 正确形态是：**曲线按需取 → 取回落库 → 指标照旧自算**。两者不冲突。

## 5. 先补后清：4 项「现在还不全、不该谈清理」

1. **✅ 货基表半残（P0-1 已完成，2026-10-13）**：`money_fund_daily_worth` 121 万行，`annual_return_7d` 填充率原为 **0.00%**——`fund_nav_job._save_data` 写死 `'annual_return_7d': None  # 暂不计算'`，而详情页 `_money_fund_performance` 正是读它，**货基「七日年化」恒为 `—`**。**已补齐**：
   - 口径（单一来源 `app/services/money_fund_yield.py`）：
     `七日年化(%) = [Σ(该行往前 7 个**自然日**窗口内已发布的万份收益) / n] / 10000 × 365 × 100`，`n < 2 → NULL`；
   - **窗口必须按自然日、不能按「最近 7 条观测」**：实测热点货基 `000379` 在窗口 `[10-05, 10-11]` 内只有 6 条观测（7 天国庆缺口让「最近 7 条」一路跨到 13 个自然日前）。收益率突变时（窗口外 0.60 / 窗口内 0.20）两种口径差 **28%**（0.73% vs 0.94%）；
   - **「窗口内满 7 条」不可行**：实测该条件**全库填充率 0.0%**（货基有节假日/周末缺口），故取窗口内已发布日求日均，缺失日**不补 0、不补均值**；
   - **不需要任何新上游**：货基上游（lsjz `DWJZ` / pingzhongdata `SYType=='每万份收益'`）只给万份收益，七日年化本来就只能自算——正合 §2「不把指标改成从上游拉」的推论。实测 357/357 只货基万份收益均 ≥7 天、**0 只**有空值；
   - 落地：写入侧 `fund_nav_job._save_data`（插入后按批重算，滑动窗口必须重算最近 7 天）+ `async_backfill`（一次拿到全历史，内存内算好随行落库）；存量回填 `scripts/backfill_money_fund_annual_return_7d.py`（默认 dry-run、`--apply` 才写、幂等、回滚 = 置 NULL）；
   - 实测效果：`000379` 七日年化 **0.8422%**（2026-10-11），详情页不再显示 `—`；数据不足的行（如国庆缺口后的 `2026-10-06`）**诚实留 NULL**，不编造。

### 6.3 删除冷集长历史为何对用户几乎无感

用户把某只冷基金加入自选/持仓 → `async_backfill` 会静默回补**全历史** → 走势图、业绩卡、风险指标照常有数据。**所以清理存量不是砍功能，而是把冷数据挪到懒加载之后。** 这是本方案风险可控的核心支点。

**仍需注意**：唯一会短促变差的是「用户**未**持有、仅浏览详情页」时，1 年以外的曲线要等按需取（§8 P0-2）——所以**必须先建按需取能力再清数据**，否则会出现「曲线断档 + 按需取未上线」的空窗。

### 8.1 口径与风险

- **回收磁盘**：SQLite 删除后需 `VACUUM` 才真正还空间；生产是 Turso，**须单独确认其删除/回收语义**，不要假设等同 SQLite。
- **回滚**：`--snapshot`（31 张市场域表，含 `daily_worth`）+ `--import-snapshot`（幂等 `INSERT OR IGNORE`，不覆盖本地）已具备；**清理前必须先出快照**。
- **不可逆点**：删除的部分若要重建需逐只回填（限流风险）。缓解：重建只发生在「用户真的持有/查看那只基金」时，按单只触发，不需要全量重建。
- **热集判定口径**：持仓/自选/流水。**待评估**：是否把「近 N 天被浏览过的基金」也计入热集——需要访问信号（`CacheService` 的 `get_or_set` 记录可作信号源）。

### 8.2 P0-2 按需取的实际形态（防打爆是重点）

模块 `app/services/fund_nav_on_demand.py`，只做**判定 + 丢线程**，外部 HTTP 与写库都在
`async_backfill` 后台线程里完成，**读请求不等待**。两个触发点：

| 触发点 | 判据 | 为什么这么判 |
|---|---|---|
| `product_trend.fetch_product_trend`（走势图） | 本次**请求区间**被本地序列盖不住 | 用请求区间而非最长档，避免「只看 3M 却为 5Y 回补」 |
| `fund_performance._open_fund_performance`（详情页业绩卡） | 本地序列盖不住**最长声明档位**（`_LONGEST_PERIOD_DAYS`，从 `_PERIODS` 派生） | 该卡对外声明了 `1y/2y/3y/5y/since`，盖不住就是 §1 说的「对外契约不稳定」。放在样本不足早退**之前**——完全没数据才是最该回补的情况 |

**三条防打爆机制**（各有用例，见 `tests/services/test_fund_nav_on_demand.py`）：

| 机制 | 参数 | 防的是什么 |
|---|---|---|
| 防抖（同只） | 30 分钟，**两层**：进程内标记 + `CacheService` 文件层 TTL | 用户反复刷新/切页把同一只基金重复打源；文件层那层跨进程/跨重启生效 |
| 全局节流 | 任意两次触发间隔 ≥ 3 秒，**不按 code 区分** | 「遍历全市场」把天天基金打爆（#1403 限流炸弹的教训） |
| 一键关停 | `FUND_NAV_ON_DEMAND_ENABLED=0/false/no/off` | 源出问题或合规顾虑时立即停用；沿用 `fundfof_crowding` 的 `_TRUTHY_OFF` 白名单体例（空值/乱值不改变默认） |

两条容易写错的细节，已在代码注释里钉住：

- **`monotonic` 哨兵必须用 `None` 而非 `0.0`**：`time.monotonic()` 是进程启动后的秒数，
  进程刚启动时只有几百秒、小于 TTL，用 `0.0` 当默认值会让「从未记录」被算成「命中」——
  后果是应用每次重启后前 30 分钟内按需取整体失效，且开发机永远绿、只有 CI 红。
  `fund_company_backfill` 为同一个坑写过详细复盘，本模块照抄其修法。
- **判据是时间跨度、不是行数**：行数少可能只是节假日密集（货基周末照常发布，缺口来自

3. `floor` 下限保护：对「近窗口行数 < floor」的冷集基金额外保留其**最近 floor 行**，避免整只

4. 单事务 + 三条断言：实际删除 == 行数差、热集行数不变、冷集基金只数不变（即没有基金被清空为空）。

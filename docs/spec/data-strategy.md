# 数据策略（按需存、禁止全量堆砌）

**版本**: v1.1
**最后更新**: 2026-09-30
**状态**: 事实标准。**约束级别等同硬约束**——新增表 / 列 / job 不通过本文的准入检查不得合入。
**决策依据**: [`decisions.md`](./decisions.md) D21（2026-09-10）。
**上位规范**: [`conventions.md`](./conventions.md) §16.2「简洁优先规则（禁止过度工程、禁止臃肿冗余）」——本文是该节在**数据维度**的展开。

---

## 0. 为什么需要这份文档

项目已有 `conventions.md` §16.2 明令「禁止过度工程、禁止臃肿冗余」，但该节**通篇只讲代码**：不封装多层抽象、不写冗余容错、杜绝 50 行扩为数百行。

它没有一句话讲数据。于是产生了一个系统性误读：

> 「按需开发」被读成**「不写多余代码」**，而不是**「不存多余数据」**。

后果（2026-09-10 本地真库实测，库体积 **1.22 GB**）：

| 现象 | 实测 | 用户实际需要 |
|---|---|---|
| `funds` 表 | 26,938 行 | **117 只**（0.43%） |
| `daily_worth` 表 | 7,539,287 行 / 3,427 只 | **112 只**（3.3%） |
| `funds` 表 22 列 | 7 列零填充且零读者 | 0 列 |
| 库内游离表 | 14 张不在数据域注册表 | 0 张 |

**数据膨胀不会报错、不会失败、不会有人投诉**——它只会在某天让备份变慢、让同步撞限流、让新人花三天搞不清哪些表是活的。所以它必须靠**流程闸门**而不是靠自觉来防。

### 0.1 分层清理后的实测（2026-10-13，#2120 已执行）

按「热集全留 / 冷集留 1 年」清理并 VACUUM 后（`invest.db`，本地库从 2.15 GB 含 WAL 降到 **130.6 MB**）：

| 表 | 清理前 | 清理后 | 删除 |
|---|---|---|---|
| `daily_worth` | 7,547,049 行 / 3,419 只 | 632,355 行 | 6,914,694（91.62%） |
| `money_fund_daily_worth` | 1,215,625 行 / 357 只 | 141,812 行 | 1,073,813（88.33%） |

热集 126 只（持仓 ∪ 自选 ∪ 流水）一行未删；`floor` 下限保护多留 28 行（14 只残缺冷集 + 货基各留 2 行）。

**上表不是终点，而是新的起点**：冷集过期行数从此被 `app/services/cold_set_guard.py` 持续盯着
（见 §4.5），清理后它应稳定在 28 行这个 floor 量级。

## 1. 第一原则

> **数据策略由产品场景驱动，不由工程完整性驱动。**

记账软件的核心价值是**「算得准」**（L1 + L2）。参考展示类与关联关系类数据（L3 + L4）是锦上添花：**缺了显示 `—`，不影响产品可用性**。

因此：

- **不存在「为了数据完整所以要把全库补齐」**——完整性只有在「用户会看到」时才有价值。
- **「工程上重要」不等于「产品上重要」**。基金公司字段对数据模型是必要的（有外键、有主数据），但对 99.6% 的用户永远不会持有的基金而言，它是纯成本。
- **每存一个字段都要能回答：谁在用？在什么场景用？缺了会怎样？**

---

## 2. 数据四层分类

| 层 | 性质 | 策略 | 典型数据 |
|---|---|---|---|
| **L1 用户数据** | 唯一真相源，不可替代 | **必须自己存**，完整性要求最高 | 持仓、交易、成本、份额、自选列表、账户、家庭 |
| **L2 派生计算** | 依赖 L1，口径必须可控 | **必须自己算**，第三方给不了口径 | 收益、盈亏（已实现/未实现）、年化、最大回撤、XIRR、仓位分布 |
| **L3 参考展示** | 锦上添花，可缺失可过期 | **按需取 + 缓存 + 可降级 `—`**，不追全量 | 基金公司、基金经理、基金全称、指数估值（PE/分位）、可转债条款 |
| **L4 关联关系** | 按需建立 | **按用户触达范围建**，不预建全库 | ETF↔联接基金、指数↔ETF、A/C 份额、行业配置 |

### 关键区分

- **L1/L2 是产品核心**：缺一条持仓，账就是错的；缺一个 XIRR，用户就看不到真实收益。这两层「完整性」是硬指标。
- **L3/L4 的「存」目的是缓存，不是真相源**：
  - 可以缺（显示 `—` 是可接受的降级）
  - 可以过期（缓存有 TTL，过期就重取）
  - 不需要全量（**用户触达不到的部分永远不请求、永远不存储**）
- **判断口诀**：**L2 必须自己算，L1 必须自己存；L3/L4 一律「按需 + 缓存 + 可降级」，不追求全量。**

## 3. 数据准入四问（强制）

新增**表 / 列 / job / 抓取目标池**时，必须在 PR 描述中逐条回答：

| # | 问题 | 不合格的回答 | 合格示例 |
|---|---|---|---|
| 1 | **谁在用？** | 「以后可能有用」「数据完整性需要」 | 「自选列表页第 3 列展示基金公司简称」 |
| 2 | **什么场景用？** | 「后台分析」（无具体路径） | 「用户打开 `/watchlist` 时，每行渲染 `company.name`」 |
| 3 | **缺了会怎样？** | 未回答 / 「不完整」 | 「显示 `—`，排序功能该行降级到末尾，其余功能不受影响」 |
| 4 | **成本多大？** | 未评估 | 「新增 ≈1.2 万行；每次同步 +161 次外部请求，需分片限流」 |

**判定规则**：

- **前三问答不出具体答案 → 判定为伪需求，禁止开发。**
- 第四问的答案若显示成本远高于产品收益（如「26,938 次外部请求」换取「用户永远看不到的字段」），应回到第 1~3 问重新质疑需求本身。
- 四问的回答与结论**必须留痕**在 PR 描述或对应 issue 评论中，不得只在口头讨论。

## 4. 分类准入细则

### 4.1 新增**表**

除通过「四问」外，还须：

1. 确认**不是**在为一张已有表的子集另立新表（若只是筛选条件不同，应加列或走查询）。
2. 确认**读写双方都存在**：有明确写入路径（job / 接口），且有 ≥1 个读取路径（API / 计算 / 界面）。**只写不读的表禁止建立**。
3. 登记 `core/db_factory.DATA_DOMAIN_REGISTRY`（见 `AGENTS.md`「数据域架构」硬规则 §1）——**数据策略准入与数据域登记并行，不可互相替代**。
4. 同步更新 [`data-model.md`](./data-model.md)。

> 反面先例：`fund_management_companies`（user 域，165 行）——唯一写方是一个 job，**零读者、零外键、零接口**，长期存在于库里，最终在 `decisions.md` 的《基金公司主数据合并》（2026-09-10，D21 上一行）中被合并删除。**建表时若执行了「读取路径」检查，这张表不会被建出来。**

### 4.2 新增**列**

- **必须当场指定至少一个读者**，三者之一：
  1. **API 序列化字段**（出现在某个 `OutSchema` / 响应体里）
  2. **计算输入**（被 L2 计算逻辑读取）
  3. **界面展示**（前端某处渲染）
- **禁止**「先存着，以后可能有用」。
- 该列的**填充率**与**写者**须在 PR 中说明：预期填多少比例？谁写？若预期填充率长期接近 0，说明写入路径不可用或需求不成立，应在开发前解决而非先建列。
- **存量死列不得私自删除**（`conventions.md` §16.3）：发现后登记 `tech-debt.md` 并报用户拍板。

> 反面先例（**2026-09-11 复核修正**）：`funds` 表 7 列填充率为 0%（`is_fe_charge` 为 100% 但值全为默认 `False`），但**「0% 填充」不等于「无价值」**。逐列复核后分四种**成因**：
>
> | 成因 | 列 | 为什么是 0 | 处置 |
> |------|----|-----------|------|
> | **源不提供** | `risk_level` | 映射与写入代码均在位（`akshare_adapter.py:385-397`、`fund_detail_enrich_job.py:162`），但实测 `ak.fund_info_ths`（18 字段）与 `ak.fund_individual_basic_info_xq`（14 字段）**均无「风险等级」** | **修**：换源或按投资类型估算 |
> | **回填链路未跑通** | `scale` / `recent_shares` / `equity_position` | 是 #1285 明确要展示的「基金：规模 / 股票仓位」正式字段，底座由 #1286 定义、#1358 落地模型，回填 job 从未跑通 | **修**：见 §4.3 收敛方式。`equity_position` 已随 #870 修复（2026-09-30）：口径改为「行业配置合计」，落 `fund_holdings` / `fund_industry_allocs` 两表并派生；调度为**每周一次**（季报数据日变更量为 0），见 `data-model.md` §5.16 |
> | **v1 迁移遗留** | `symbol_prefix` / `is_fe_charge` | v1 备份 `.backup-v1-2026-08-01/fundmate/data/` 内有真实取数逻辑，v2 换 akshare 后未接 | 可删（须先确认信息由谁替代） |
> | **功能未启用** | `pinyin_full` | `fund_service.py:216` 搜索只用 `pinyin_abbr` | 保留待用 |
>
> 本条原有「六列零填充零读者」的表述**把成因当成了结论**，曾使整批字段被判为「死列」并进入删除清单（后经用户复核全部保留）。教训：登记「填充率 + 写者」之外**必须写清「为什么是 0」**——源缺失 / 链路未通 / 设计废弃三者的处置完全相反，前两者要修，只有后者才可删。

### 4.3 新增 **job**

1. **目标池必须显式**：只能来自
   - 用户触达范围（`positions ∪ watchlist`，经 `orchestrator.resolve_targets()`），或
   - 代码中**明确配置的核心池常量**（如 `INDEX_TARGETS`）。
2. **禁止空 targets 静默退化为全库**。空 targets 的正确语义是「无需处理，跳过」，**不是**「处理所有记录」。反例：`fund_manager_job.py:37` 的 `codes = targets if targets else self._get_all_fund_codes()`——语义与 `fund_detail_enrich_job`（空 targets 直接返回「无基金需要补充详情」）**相反**。
3. **`__full__` 使用有前提**：仅当该 job 单次调用**不产生逐条外部请求**时可用全量（如一次 HTTP 返回全市场列表）。**逐只抓取类 job 一律按目标池限量**，且必须设批量上限与节流。
4. **docstring 必须与行为一致**：job 名称与 docstring 若声称「全量」，实现就不得是「只增不改」；反之若实现是增量，名称与注释必须如实描述。**契约谎报会误导后来人对数据状态的判断。**
5. **请求路径禁止全表扫描**：接口 / 页面渲染路径中禁止 `for x in db.query(Model).all()` 这类无条件全量加载。跨域读取走 `services/cross_domain.py` 的「两步法」（先取 key，再 `in_` 批量查）。
   **已有机器化守卫（#1643）**：`scripts/check_cross_domain_query.py` 静态拦截「跨域模型进同一 SQL 语句」——五类形态 A（单链 `join` / `outerjoin`）/ B（`subquery()` 变量耦合）/ C-eager / C-join / C-rel（跨域 `relationship()` 声明，须显式登记豁免），接入 pre-commit 与 CI 的 backend job。**为什么必须是静态层**：门禁与全部单测跑单库（`tests/conftest.py` 把 `engine` / `user_engine` 指向同一个内存引擎），跨域 join 在两域同库时不报错，**结构上测不出**；生产每日调度才跑真双库。判据见 `architecture.md` §6，决策见 `decisions.md` 2026-09-21 行（D34）。
6. **失败必须可见**：job 抛出的异常不得被静默吞掉导致 `sync_logs` 无记录（当前 `orchestrator.py:341-358` 存在该盲区，见 `tech-debt.md`）。
7. **`--full-sync` 必须带范围，且基金净值 T 日不回填（#824 / #1776 ④）**：
   - **范围强制**：逐标的回填型 job（`fund_nav` / `price_history` / `fund_detail_enrich` / `fund_manager` / `fund_type` / `fund_company_backfill` / `fund_position` / `position_price` / `dividend_split`）裸 `--full-sync`（无 `--targets` / `--target-file`）由 CLI **直接拒绝执行**（`sync/orchestrator.py` 的 `SYMBOL_BACKFILL_JOBS` + `require_full_sync_scope`，接入 `sync_metadata.py` / `sync_cli.py`）。理由同本条第 3 点：逐标的全市场全量回填是数万次外部请求，触发数据源封禁且耗时以小时计。列表型 / 指数型 / 温度计型 job 单次调用换全市场，裸 `--full-sync` 属正常模式，不受限。
   - **T 日不回填**：`fund_nav_job` 写入前丢弃 `date >= today` 的记录——净值发布有滞后，当日（含未来）净值尚未成立，入库等于伪造数据。
8. **全市场数据的初始化/重建走 DB 快照，不走云端全量拉取（#1776 ⑤）**：
   `pdm run sync --snapshot <path>` 导出市场域只读快照（31 张市场域表 + `snapshot_meta`，**不含用户私有数据**、排除 `sync_logs`），
   `pdm run sync --import-snapshot <file>` 校验（SQLite magic / meta / 表白名单，含用户域表即拒绝）后按**本地唯一约束**幂等导入（`INSERT OR IGNORE`，不覆盖本地记录）。
   实现见 `services/sync/snapshot.py`。日常增量仍走 `--all`；单只/CSV 范围回填走本条第 7 点的 `--full-sync --targets`。

> 反面先例（**2026-09-11 已按本条收敛**）：`fund_meta_job.py:50,71-82`——`for code, fund in db.query(Fund).all(): fetch_fund_top_holdings(code)` 即**全库 26,938 次逐只外部请求**（实测 ≈1.8 s/只 ⇒ **≈13.5 小时**），而其 docstring 声称「本地只存用户核心池，不把全市场基金灌进库」。
>
> 收敛方式：拆为 `fund_scale`（走本节第 3 条的「全市场单次调用」例外，1 次请求换 6,976 只）与 `fund_position`（逐只，仅核心池 + 硬上限 500；`__full__` 与空 targets 显式跳过）。
>
> **关键教训**：同一个业务概念（「基金元信息」）**内部**就存在 3 个数量级的成本差，不能按 job 名粗粒度判断该不该全量——必须下沉到「这条链路单次调用产生几条请求」。

### 4.4 **读路径上的按需回填**（L3 数据的推荐落地形态）

§4.3 管的是「批量 job 怎么取数」。**读路径上发现数据缺失时能不能就地补**，是另一条规则，
本节定它（#2037 落地的第一条，详见 `services/fund_company_backfill.py`）：

1. **允许，且优先于排期 job**：L3 字段的覆盖率目标不是全库，而是**用户触达口径**。
   排期 job 只能按固定目标池跑，用户触达是动态的——「打开详情页时发现没有，就地补这一只」
   天然对齐触达口径，且**触达不到的基金永远不请求、永远不存**。
   例：`funds.company_id` 全库仅 11.5%，但详情页「基金公司」栏有 `fund_company_backfill`
   按需回填兜底，覆盖率不再是验收指标（与 §190「全库 ≥90% 是反面先例」一致）。
2. **必须仍走既有唯一写入口**：读路径不得为同一实体新开一个写入口。若既有入口是
   「主数据解析器」（如 `company_resolver.get_or_create_fund_company`），按需回填也必须
   经它——否则同一主体会在库中长出第二行，而错配（A 公司的官网写到 B 公司上）
   是最难发现的一类数据腐蚀。
3. **必须有负缓存**：失败不能每次重试。取不到时若下次冷开又打一次外部请求，
   L3 的「可降级」就退化成「每次都卡」。负缓存 TTL 是**保守值**（本仓取 30 分钟），
   取舍理由写在实现的 docstring 里，不当作精确结论。
4. **外部请求的成本要按「首请求」而非「复用后」记账**：实测同一接口首次请求含
   TLS 握手约 **1.8~2.8s**、连接复用后仅 **43~87ms**（约 30 倍差）。故读路径上的取数
   **必须走长连接 Session**（配锁，`requests.Session` 非线程安全），否则把握手成本
   付给每个冷开用户——那才是拖垮首屏的真凶。
5. **写路径会 commit，故顺序要对**：按需回填要跨请求存活就必须落库（`commit`），
   会让会话内 ORM 实例过期。**必须先把只读字段拼装完再回填**，否则后续读 `fund.xxx`
   会触发逐字段 refresh SELECT（慢）乃至 `DetachedInstanceError`。
6. **上限仍受 §4.3 第 3 条约束**：按需回填是「一次一只」，不是新的批量入口。
   任何「遍历全库逐只回填」的写法仍需走 §4.3 的目标池与批量上限闸门。

### 4.5 **清理之后的防回灌**（冷集膨胀守卫，#2120 P2）

§4.3 挡住「误跑全量」，§4.4 让按需取合法化——但两者合起来仍留一个缺口：
**「反复小批量灌」**。每次给 50 只冷集基金补一次历史，单看每次都合法，累起来
把分层清理删掉的行逐步灌回来。而数据膨胀不会报错、不会失败、不会有人投诉（§0）。

故清理之后必须有一道**只读巡检**，而非依赖自觉：

1. **监测「冷集在保留窗口之外的行数」**（`stale_rows`），而不是绝对行数。
   绝对行数会随用户增持自然增长，只有「本该被清掉却还在」才是回灌信号。
   清理执行到位后它应稳定在 floor 保护量级（实测 28 行）。
2. **阈值按「单次增量」而非绝对值**：正常按需取是慢速路径（30 分钟防抖 + 3 秒
   全局节流），一天补只数到数十只；而误跑全量 / 反复小批量灌是万行级，两者差
   2~3 个数量级，阈值取中间值（默认 5,000 行）不会误报。
3. **首次巡检不判定膨胀**：没有基线就说不出「增长过快」，此时只记录当前值作为
   下次基线。否则一上线就误报，守卫立刻失去可信度。
4. **时序复用 `sync_logs`**：判定需要上一次的数据，而项目已有每跑一次落一行的
   审计表（`stats` 存 JSON）。复用它不用新表、不用迁移；代价是它不保证按时间严格
   排序，因此取最近一条而不做时间匹配。
5. **不进每日调度**：`daily_scheduler` 的准入判据是「数据日变化 + 用户直接看得见」，
   健康检查两条都不满足。真实频率应为**周报级 / 手动**，避免为巡检每天多打上游。

实现：`app/services/cold_set_guard.py`（纯测量 + 判定，不写库）+
`scripts/check_cold_set_bloat.py`（默认 dry-run，`--record` 才落基线，膨胀时退出码 1
便于 cron / CI 直接告警）。

## 5. 「存」的成本模型

数据不是免费的。每多存一份，就多一份：

| 成本项 | 表现 |
|---|---|
| **存储与备份** | 1.22 GB 库 → 备份 22 秒；库越大，本地开发与灾备越慢 |
| **外部请求与限流** | 每条记录若需外部抓取，直接转化为请求数；本项目已有 akshare/东财限流封 IP 的历史（见 `docs/bias-datasource-troubleshooting.md`） |
| **认知负担** | 后来人无法分辨哪些表 / 列是活的，动一个字段要考古三天 |
| **漂移风险** | 同一事实存在多处副本 → 必然出现口径不一致（项目已多次踩坑） |

**结论**：对 L3/L4 数据，「不存」是默认选项；「存」需要举证。

## 6. 落地机制

| 环节 | 做法 |
|---|---|
| **PR 闸门** | 新增表 / 列 / job / 抓取目标池的 PR，描述中必须包含「数据准入四问」的回答；未回答者 review 直接打回 |
| **AI 编码约束** | AI（含本仓 AI review、各类编码 agent）在提出新增数据实体时必须先自问四问；发现存量冗余须主动提出异议（`conventions.md` §16.1 已有此要求） |
| **存量清理** | 发现死表 / 死列 / 孤儿表 → 登记 `tech-debt.md`，**报用户拍板后**再清理（§16.3 禁止私自删除历史死代码） |
| **定期巡检** | 结合里程碑复核节奏，抽查：新表是否都有读者？新列填充率是否符合预期？有无游离于 `DATA_DOMAIN_REGISTRY` 之外的表？**「哪些数据靠什么刷新、最后一次跑通是什么时候」的现状台账见 [`data-refresh-inventory.md`](./data-refresh-inventory.md)**（含各接口实测成本与调度缺口）。 |
| **验收口径纪律** | issue 的验收标准**不得写「全库覆盖率 ≥X%」而未经第 1~3 问验证**。参考展示类数据的验收应优先采用「用户触达口径」 |

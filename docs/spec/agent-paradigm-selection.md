## 1. 结论先行

三种范式优化的是**三种不同的不确定性**，选错不是「多做点工」，而是把架构叙事一起改掉。
本系统的不确定性主要不在「下一步该查什么」，而在「这一轮到底问了几件事、几件事之间有没有依赖」。

| 范式 | 判定 | 一句话理由 |
|---|---|---|
| **Plan-and-Execute（最小形态）** | **最适配** | 与现有两阶段管线同构，只需把「选 1 个工具」升级成「输出 1~N 步计划」，执行层仍是纯代码 |
| **ReAct** | **不适用** | 它优化「路径未知、需中途改道」；本系统路径由问题类型静态决定，且 Observation 回灌会破掉防幻觉护城河 |
| **Reflection** | **排除** | 输出质量已有确定性外部判据（schema / 护栏 / 评估集），模型自评是降级而非增强，且会邀请模型改数值 |
| **方案四：不改范式（前置子查询拆分）** | **必须并列评估** | 现有唯一实证案例 #1718 就是并列多问，用它就够；P&E 在这里用不上 |

**分水岭判据**：目标问题集是「并列多问」还是「链式依赖」？前者用方案四，后者才需要 P&E。

**诚实边界（必须写在选择前面）**：当前**没有任何证据表明 P&E 能带来可测收益**——45 条评估集的 `expect.tool` 全是单工具断言，`agent_eval.py` 只判 `status` / `tool_name`；#1718 的一轮三问是并列的，且其中两问根本无工具可答。选择 P&E 属于**为链式依赖做前瞻性架构准备**，不是修复一个已复现的故障。若拿不出含链式依赖的真实问法，本轮结论应收敛到方案四或直接不做。

## 2. 三种范式的第一性区分

| | ReAct | Plan-and-Execute | Reflection |
|---|---|---|---|
| 优化什么不确定性 | **下一步该做什么**（路径未知） | **要做哪些步骤**（步骤集合未知，步骤间关系确定） | **输出好不好**（质量无客观判据） |
| 控制流 | Thought → Action → Observation → Thought 循环 | 一次 Planner 出完整计划 → Executor 确定性执行（可选 Re-plan） | 生成 → 自评 / 批评 → 修订循环 |
| 决策权位置 | 分散到**每一步**，交给模型 | **集中一次**交给模型，之后全交代码 | 评判权交给模型 |
| LLM 调用 | N 次（随步数增长） | 通常 1 次 plan + 1 次汇总 | 至少 +1 次，常多次 |
| 终止条件 | 模型自己说结束，或预算 / 轮次耗尽 | **计划长度有界**，执行完即止 | 自评满意或轮次上限 |
| 典型失效模式 | 循环不收敛、错误逐步累积、Observation 撑爆 context | Planner 把不存在的工具写进计划；环境变化时僵化 | 自我肯定、无外部 critic 时无效、延迟翻倍 |
| 必要前提 | 工具可重入、有逐步预算、有循环内重复调用检测 | 计划可被 schema / 白名单校验，执行层可纯代码 | 存在可验证的质量信号 |

一句话区分：**「路径不确定」选 ReAct，「步骤不确定」选 P&E，「质量不确定」选 Reflection。本系统只有「步骤不确定」。**

## 4. 逐范式适配判定

### 4.1 ReAct：不适用 —— 是能力错配，不只是成本高

- **能力错配**：ReAct 的价值是「看到上一步结果再决定下一步」。本系统路径由问题类型静态决定（问收益 → XIRR，问基准 → 基准对比，问归因 → 收益归因），模型**不需要看到数值才决定查什么**。核心能力在此无用武之地。
- **致命冲突**：Observation 回灌意味着模型要基于真实数值做下一步决策。即便仍是只读，S6 简历与 README 里「模型物理上接触不到账本」这条论据就要改写——而这正是本项目防幻觉叙事的护城河。
- **结构代价**：决策 / 叙事两阶段合并；L1 铁律须在每一步生效；trace 从 1 行变 N 行；取消检查点重排；新增循环内重复调用检测与逐步预算；四态信封扩展；`repeat_tracker` 语义要从「跨轮用户追问」扩到「单请求内工具调用」。
- **本域失效尤其隐蔽**：金融问答里「越查越多」不会抛错，只会产出一份看起来完整、实则答非所问的长回复。#1718 已是这个症状的轻量版（一轮三问被答成组合总结）。
- **唯一可重评条件**：将来做诊断型任务，且下一步确实取决于上一步数值（例：先查最大回撤，若超阈值再查归因），同时能接受有界循环与重开 D19。

### 4.2 Plan-and-Execute：最适配，且是三种里改动最小的

- **控制流同构**：现状本来就是「模型出一次决策 → 代码执行 → 模型转述」。P&E 只是把决策载荷从 `tool_name: str` 升级成 `plan: list[Step]`，执行层仍复用 `ToolExecutor.run`。
- **三条护城河原样保留**：模型只在 plan 阶段输出工具名与参数，**不接触任何数值**；执行纯代码；叙事轮仍只一次。防幻觉论据无需改写。
- **天然可校验**：计划可对着 `TOOLS_METADATA` 白名单与 `_validate_params`（`tools.py:563-566`）做**执行前静态校验**，幻觉工具名在执行前就被拒；计划长度硬上限天然就是终止条件，不需要「模型自己说停」。
- **成本与合规**：LLM 调用次数不变（决策 1 + 叙事 1，失败重试 +1，压缩可能 +1），不撞全站 token 预算；一个 `list[Step]` 的 for 循环符合 D19「轻量封装、不引 LangGraph」。
- **可测性最好**：`cases.yaml` 把 `expect.tool` 扩成 `expect.plan` 即可断言「拆没拆对」，正好补上 §3 第 10 条的验收缺口。
- **必须定死但本轮不裁定的四个边界**：
  1. **无工具可答的子问题**（#1718 的「数据来源 / 更新频率」）要有显式步骤类型，否则 Planner 会硬塞一个工具进去；
  2. **步骤间参数依赖是否支持** —— 这是复杂度分水岭：不支持 = 并行独立查询，支持 = 真链式，需要定义步骤间数据引用语法；
  3. **部分失败语义**：整计划失败还是返回部分结果，绝不能让模型看到半截数据后自行补全；
  4. trace / 取消检查点 / 四态信封 / token 计费按「步骤」还是按「请求」计。
- **诚实降级**：若边界 2 裁定为「不支持依赖」，P&E 在实现上就**退化成方案四**，此时引入范式概念没有收益，应直接按方案四做。

### 4.3 Reflection：排除

- **判据已存在且更强**：本系统的输出质量由确定性外部信号判定 —— JSON Schema 校验、`filter_output` 词法护栏、评估集断言、数值由代码算。用模型自评替换其中任何一项都是**降级**。
- **直接撞 L1**：让模型复查「这个数字对不对」，模型没有任何权威依据去判断或修改，只会引入新的幻觉面。
- **额外成本无对应收益**：至少 +1 次 LLM、延迟翻倍；没有外部 critic 时自评普遍偏向自我肯定（Reflexion 类方法的收益依赖可验证反馈信号）。
- **唯一沾边处**：护栏命中后的「定向重写」——但那是规则触发的重写，不属于 Reflection 范式，且现状 `filter_output` 的替换式降级已够用。
- **重评条件**：将来出现开放式文案生成，且配了人工 / 规则评分信号时再谈。

## 5. 方案四：不改范式（必须并列评估，否则选型会自我拔高）

- **形态**：在前置意图分类层把一轮输入拆成 N 个**独立子查询**，各自走现有单工具固定管线，最后合并叙事。`run_agent` 一行不改。
- 严格说这既不是 ReAct 也不是 P&E，而是**结构化输入分解**：计划由规则产生，不由模型规划。
- **优点**：风险最低，§3 的 12 条已验收面一条不动；评估集可立即新增「一轮多问」用例自证收益。
- **天花板**：无法表达链式依赖（「查贡献最大的那只，再看它最新净值」），也无法按前一步结果裁剪后续步骤。
- **与实证对齐**：#1718 的三个子问题是**并列**的（数据来源 / 更新频率 / 贪恐指数），其中两问无工具可答 —— 方案四足以覆盖，P&E 在这个案例里是多余的。**这是本文最反直觉、也最该先向 owner 说明的一条。**

## 9. 真实测试向量（来自 owner 讨论，2026-11-11）

owner 给出一段一次性四连问，作为选型判据的 concrete 探针。逐问对照 9 工具与执行路径
（`tools.py:351-535`、`agent_loop.py:630/635/672/691/563`），结论如下：

> 用户问：「① 我近 3 个月的持仓收益如何？② 哪一个亏得最多？③ 你能够针对这个产品给我一些
> 持仓建议，或者调仓建议吗？④ 它亏的原因是什么？是没有跟上市场，还是自己确实出问题了？」

| 子问 | 应走工具 | 当前能否答 | P&E 后 | 备注 |
|---|---|---|---|---|
| ① 近 3 月收益 | `get_portfolio_performance`（XIRR+区间） | 单次可答，但 4 问中只会被选中其一 | ✓ plan 第 1 步 | 单工具即覆盖 |
| ② 亏得最多 | `list_position_pnl`（按盈亏率排序） | 单次可答 | ✓ plan | **口径是「当前每个持仓」，不含已平仓** → 覆盖缺口 |
| ③ 持仓/调仓建议 | **无任何工具** | 落判断顺序③ `ask_clarification`「不支持」 | ✗ **解不了** | 9 工具关键词 0 命中；`get_trading_behavior` 明示「只给客观统计，不做好坏评价」；叙事契约 `:690` 禁「超出数据本身发挥」 |
| ④ 亏的原因：市场 vs 自身 | `get_return_attribution` **+** `get_portfolio_vs_benchmark` | 单工具只答一半 | ✓ 两工具进 plan 做对照 | benchmark 答「市场给的」、attribution 答「哪个标的自身拖累」 |

**结构发现 1（修正「4 个并列子问题」的直觉）**：4 问**非全并行**，存在依赖链 ——
Q4 的「它」= Q2 找出的最亏产品；Q3 的产品也依赖 Q2/Q4 结果。即 Q4 必须先跑 Q2、
**把结果注入 Q4 的参数**才能正确生成 plan。这正是 §8 待裁定 #2「步骤间参数依赖」的真实样本：
若 P&E 不支持「上一步结果进下一步参数」，Q4 连 plan 都排不出来。

**结构发现 2（当前行为比「不支持」更隐蔽）**：决策层 `tool_name` 单值（630）、
`ToolExecutor.run` 只跑一个（635）、叙事只吃一份 `data`（672/691），判断顺序 ① 写
「tool_name 必须**直接回答该提问**」（563，单数）。4 问进来模型挑 1 个工具，其余 3 问
**不出现在任何环节**——静默丢弃，与 #1718 一轮三问只回通用总结同病灶。

**Q3 的关键区分（避免误判 P&E 的边界）**：Q3 不是编排问题，是「生成 / 范围」问题。
P&E 只编排数据工具，而 9 工具里没有任何一个产出建议；叙事契约又禁止模型超出数据发挥。
因此 **P&E 单独解不了 Q3**。Q3 的正确实现路径是**新增一个只读计算型工具**（与现有 9 个同构，
由代码算出「客观参考」而非让模型自由生成建议），这条路径**与 P&E 决策正交**——可独立于

## 10. Q3 专题评估：调仓建议的可实现性与用户价值

owner 追问：「持仓分析根据估值给出调仓建议」能否实现？对用户有无价值？本节能否独立于
P&E 决策推进？

**结论先行**：可实现，且正确路径是**新增一个只读计算型工具**（与现有 9 个同构，由代码算出
「客观参考」），**不是**放开叙事让模型自由生成建议。对用户价值高，但必须框定为「客观参考 /
提示」而非「投资建议」，否则撞既有契约与责任边界。该能力与 P&E **正交**，可独立落地。

### 10.1 可实现性：是，且比 P&E 便宜得多

- **数据底座已存在，只是没被 Agent 工具暴露**：
  - `index_valuations` 表：指数 PE/PB/股息率（中证官方，#1285/#1394）；
  - 基金收盘估值快照（`funds/models.py:321`，#2141，时点 NAV 定格）；
  - 市场温度估值分位 / 乖离率（集思录 / 韭圈儿，见 `tasks.py:66`、`sync_cli.py:87`）。
  - **个基估值分位**（单只基金 PE/PB 历史分位）大概率在**已同步的 Wind / 且慢外部数据**里
    （呼应 A′ 路径：消费已同步行情的只读本地工具）。
- **因此「估值型调仓参考」要真正成立，依赖 A′ 先落地**，或先把 `index_valuations` +
  持仓成本/市值接进一个新工具。在「估值」维度上，个基口径依赖外部同步数据，指数口径本地已有。
- **实现形态**：新增 `get_rebalance_reference`（暂定名）只读工具 —— 输入持仓快照 +
  估值/集中度口径，由代码算出结构化「参考」（如单一标的占比、行业集中度、与历史均值偏离、
  客观再平衡提示），叙事轮只转述。这与现有 9 个工具同构，**不碰防幻觉护城河**。
- **工作量**：S~M（一个工具 + schema + 叙事转述 + eval），远低于 P&E；且**风险更低**
  （无需改循环 / trace / 取消检查点）。

### 10.2 用户价值：高，但边界要卡死

- **价值高**：用户要的是「我该怎么办」而非「我的数字是多少」。给「客观参考」是高频刚需，
  比纯数据查询更贴近决策场景。
- **契约冲突（必须正视）**：现有设计**刻意避开好坏评价** —— `get_trading_behavior` 明示
  「只给客观统计，不做好坏评价」；叙事契约 `:690` 禁「超出数据本身发挥」。给调仓建议本质是
  **投资顾问行为**，对一个记账 / 分析工具而言踏入「投资建议」边界。
- **安全框定（推荐话术）**：用「数据化参考」而非「你应该」——
  「单一标的占比 X% 已超你历史均值 Y%；行业集中度 Z%；以下为客观再平衡参考，**非投资建议**」。
  既保留「只给客观统计」立场，又交付用户想要的价值。

### 10.3 与 P&E 的关系：正交，勿捆绑

- Q3 不是编排问题（§9 已证），**P&E 单独解不了 Q3**。
- Q3 的正确实现是一个计算型工具，与 P&E 决策**无关**；该工具落地后，P&E（或单调用）也能直接编排它。
- **诚实边界**：若把 Q3 实现成「模型自由生成建议」（放开叙事「不发挥」护栏），则撞 L1 数据真实性
  铁律 + 投资建议责任，**高诚实风险**；正确路径是**代码算、模型只转述**。
- 因此「加 P&E 就能答这 4 问」是错误卖点；Q3 应作为独立能力项单列（可先于 P&E 推进）。

## 3. 候选方案

### 3.1 方案 A：维持主动定时抓取（现状）

- 做法：recurring 自动化（当前周一/六/日 0:00）云端 WebFetch（微信原文，fallback 雪球）→ 火山 Ark 结构化 → `erniao_sync.py` 写 `docs/er-niao/index.json` → git push → 微信推送 + 邮件摘要。
- 优点：零用户操作；PC 关机照常；已部分跑通；延迟可控（当前最多隔 2~3 天，调到每日可降到 1 天内）。
- 缺点：只能抓"最新一期"，无法处理你临时想归档的历史/任意链接；发布日若在两次调度之间会有延迟。
- 适配性：**主场景最佳**。

### 3.2 方案 B：邮件轮询触发（你提的）

- 做法：recurring 自动化每 1~3 小时 `list_messages` 收件箱，筛 `from=emailme8@163.com` 且未读 → 正文正则抽首个 URL → WebFetch 抓取 → 结构化 → 写 JSON → git push → 回确认信 → 标记已读。
- 优点：从任何能发邮件的地方触发（含离开 App 时）；PC 关机照常；能注入任意链接（补抓历史/其他文章）。
- 缺点 / 风险：
  - 平台无邮件事件触发器，必须轮询（浪费配额，10/min·200/hr·50/天封顶）。
  - **安全**：邮箱可被伪造 → 往你仓库写东西。必须 `sender 白名单（仅 emailme8@163.com）+ 指令词（如标题含`ARCHIVE:`）`。
  - **解析歧义**：邮件可能无链接 / 多链接 / 非手抄报链接，需规则或二次确认。
  - 配额 50/天，频繁轮询+回信易触顶。
- 适配性：**作为按需辅助通道有价值，但不该当主触发器**。

### 3.3 方案 C：聊天消息触发（被低估的更优解）

- 做法：你在 WorkBuddy App（手机/网页）直接发链接给 agent → agent 抓取、结构化、入库、推送。
- 优点：
  - **天然身份认证**（登录态，无 spoof 风险）；
  - **无解析歧义**（明确"处理这条"）；
  - 无额外配额消耗；
  - PC 关机照常（agent 在云端，手机随时可发）；
  - 实现最省（无需轮询、无需白名单）。
- 缺点：必须打开 WorkBuddy App（但手机随时可开，比"开电脑"容易得多）。
- 适配性：**比邮件更优的"按需"通道，应优先于邮件**。

### 3.4 方案 D：wewe-rss 托管 + HTTP 拉取

- 做法：在免费云平台（Zeabur / Railway / HuggingFace）或常开 NAS 托管 **wewe-rss**（基于**微信读书接口** v2.x，比直接爬微信稳）。它输出 JSON/全文、定时更新、支持 `?update=true` 手动触发。agent 定时 HTTP 拉取 feed JSON → 写 GitHub。
- 证据（2026-08 检索）：wewe-rss 仍活跃维护（2026-03 提交）；支持全文输出、OPML、标题过滤；需**微信读书扫码登录**，存在偶发"小黑屋"封控风险（添加过快 / 转发服务 weread.111965.xyz）。
- 优点：拿到**干净全文 JSON，去掉 LLM 依赖**，内容保真最高；可做历史回溯。
- 缺点：需常驻托管（免费云或 NAS，违背"零运维"）；微信读书账号风险；部署+维护成本。
- 适配性：**长期增强/可选**。边际收益主要在"稳定全文 + 历史回溯"，而非"能不能抓"——因为云端 WebFetch 已能直接抓微信原文。

### 3.5 方案 E：混合架构（推荐）

- **主链路（零用户操作）**：每日（或保持周一/六/日）定时 → 云端 WebFetch（微信原文，fallback 雪球）→ 火山 Ark 结构化 → `erniao_sync.py` 写 `docs/er-niao/index.json` → git push → 微信推送 + 邮件摘要。
- **按需辅链路（任选其一/都上）**：
  - 聊天触发（**首选**，最安全省事）：WorkBuddy 发链接即归档。
  - 邮件触发（可选）：recurring 轮询 + 白名单 + 指令词，仅作"离开 App 时"的兜底入口。
- **长期可选**：wewe-rss 托管做高保真全文备份 + 历史回溯。

### 3.6 存储 / 分发增强（独立于上述）

- **腾讯文档镜像**：你已连 `tencent-docs` 连接器，可把 `index.json` 同步成在线表格/文档，阅读分享更友好（GitHub JSON 仍是真相源）。
- **微信推送**：现有自动化已 `push_to_wechat`，保留。
- **邮件摘要**：已验证可用，保留。

## 5. 推荐方案与落地路线

**主推方案 E（混合）**，分阶段落地，每阶段可独立交付：

- **P0 — 主链路提频**：把主动抓取从 3 次/周 提升到**每日**（或保持每周但加每日校验），降低发布日延迟。复用现有 WebFetch+Ark+sync，改动极小。
- **P1 — 聊天触发（首选按需通道）**：在 Agent / 自动化里加一个"收到链接即归档"的处理分支。实现最省、最安全，建议优先于邮件。
- **P2 — 邮件轮询（可选）**：仅当你确实需要"离开 App 也能触发"时做。务必 `sender 白名单 + 指令词 + 写前 Dry-run/二次确认`。
- **P3 — 腾讯文档镜像**：把 `index.json` 同步到腾讯文档，便于阅读和分享。
- **P4 — wewe-rss 托管（长期可选）**：若追求全文保真 + 历史回溯，再用免费云托管 wewe-rss 替换/补充 WebFetch+LLM。

**健壮性基线（所有方案共用）**：
- 按 `issue_no` 幂等，已存在则跳过；
- fallback 链：微信原文 → 雪球镜像（微信偶发验证页时）；
- 失败告警（邮件/微信通知，带错误原因）；
- LLM 解析校验（系数范围 0~10、issue_no 数字、日期格式），异常不脏写。

## 6. 风险与开放问题

**风险**
- 微信偶发验证页 / 环境异常 → 已有雪球 fallback，需监控命中率。
- wewe-rss 微信读书账号"小黑屋"封控 → 仅当走方案 D 时需应对（降频、多账号）。
- 邮件 spoof 写入仓库 → 白名单 + 指令词 + 二次确认。
- 火山 Ark 解析漂移 → 字段校验兜底，失败退 WebFetch 直抽。
- 配额（邮件 50/天、GitHub push 频率）→ 按需通道控制频率。

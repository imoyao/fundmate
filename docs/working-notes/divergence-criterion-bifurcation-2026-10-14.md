# 分叉判据二分 + 交叉合并假阳性（CNB #179）

日期：2026-10-14　关联：CNB #179 / #167 / #171 / #123 / #148　状态：待合入 `dev`

本轮做的是 #179 卡面第一条验收：**`check_branch_divergence.py` 判据二分 —— 合规发版不报红，
纪律违规仍红**。顺带把 #179 的其余三条验收一并做了（详见 §五）。

## 一、问题的形状：报警在喊狼来了，而它喊的其实是羊

`check_branch_divergence.py` 的初版判据是「`main` 独有提交数 > 0 ⇒ 分叉，红」。
本仓的模型决定这条**恒为真**：

```
dev 发完版继续往前走 ⇒ main 既不领先、也不是 dev 的祖先 ⇒ 永远红
```

实测（2026-10-14）`origin/main` 独有 **2** 个提交，逐笔核对**两个都是合规发版 merge**：
`fc49e500`（合并来自 dev 的合并请求 #162）与 `8fa55fe6`（合并来自 dev 的合并请求 #177）。
第二父分别是 `0b2b127f` / `c76b7621`，**都是 `dev` 的祖先**。没有一笔纪律违规，
而报告在喊红灯。

这就是「做了好多事还是很乱」的真实来源：**红灯喊的风险越大，越没人当回事。**

## 二、修法：两层判据，任一层成立才红

| 层 | 判据 | 红？ |
|---|---|---|
| **提交级** | `main` 独有提交是 merge，且其**第二父**是 `dev` 的祖先 | ✅ 合规发版，**不红** |
| | 是**普通提交**（非合并） | ⚠️ **红**（绕过 `dev`） |
| | merge 的第二父**不是** `dev` 的祖先（`feature` → `main` 直通车） | ⚠️ **红** |
| | 提交类型**读不出** | ⚠️ **红**（拿不到 ≠ 正常，#171） |
| **内容级** | `git cherry <right> <left>` **无 `+` 行** | ✅ **不红** |
| | 有 `+` 行，逐条列出 sha 与路径 | ⚠️ **红** |

退出码：`0` 无新形态；`1` 有新形态；`2` 取不到分支。（`2` 与「有新形态」分开。）

### 方向：**第二父**，不是第一父

`git log --format=%P` 的**第一父**是当前分支自己的历史（`main` 上继续的那个），
**第二父**才是被合入的一侧。取第一父判「是不是 `dev` 的祖先」会把**每一笔合规发版
都判成违规** —— 「判据方向错等于报告不可用」。

## 三、第二个坑：`git diff` 在交叉合并下假红

上一版内容级判据是「`git diff <left> <right>` 非空 + 非祖先 ⇒ 有独有内容」。
在**交叉合并**后失灵：

```
main 合过 dev@c76b7621，dev 又往前走了 2 个提交
⇒ 两侧都不是对方的祖先（--is-ancestor 双向 false）
⇒ 旧实现报 ⚠️「main 有 7 个文件 dev 没有」
```

**实测这 7 个全是假阳性**：`git cherry dev main` **为空** —— `main` 上每条提交都能在
`dev` 找到补丁等价的对应，`main` **一个字节的独有内容都没有**。diff 非空只是因为
`dev` **更靠前**，而「更靠前」在交叉合并下**不能**由「非祖先」推出来。

故内容级改用 `git cherry`（补丁等价）——**一个判据直接回答被问的那个问题**，
不再拼「diff + 祖先关系」那条要两个条件同时成立的两步路（交叉合并恰好卡在中间）。

## 四、探针：7 个变异，全部 CAUGHT

| 变异 | 结果 |
|---|---|
| M1 第二父改成第一父（方向错） | ✅ CAUGHT |
| M2 普通提交也当 release（不判违规） | ✅ CAUGHT |
| M3 内容级退回 `git diff`（假阳性） | ✅ CAUGHT |
| M4 `needs_red` 忽略 violations | ✅ CAUGHT |
| M5 拿不到输入当正常 | ✅ CAUGHT |
| M6 内容级判据不可用当正常 | ✅ CAUGHT |
| M7 release 也报红（二分反了） | ✅ CAUGHT |

**M1 / M4 / M5 首轮 MISSED**，逐个查清后补的是**用例设计**（不是改断言去迎合）：

- **M4 / M5 为什么不红**：真实仓库里「绕过 `dev` 的提交」几乎必然**同时**被内容级
  （`git cherry`）抓到 ⇒ 两层冗余，仓库型用例咬不住「只改一层」。修法：
  `test_needs_red_reads_both_layers` 直接用 dict **分别**喂两层，让它们各自可被验伪。
- **M1 为什么不红**：既有 fixture 的 merge 第一父恰好也是 `dev` 的祖先，
  取哪一父都判 release ⇒ 测不出方向。修法：`test_classify_commit_release_uses_second_parent`
  造「第一父**不是** dev 的祖先、第二父**是**」的发版合并，并在用例里断言该前提成立。

## 五、同卡其余三条验收

- **`allow_branches` 建议落到模板**：`docs/ops/git-sync-secret-vars.example.yml` 从
  `[main, dev]` 扩为 `main / dev / feat/ / fix/ / docs/ / chore/ / refactor/ / rescue/`
  （**不写裸 `*`**，CNB glob 下 `*` 能跨 `/`，等于拆掉权限检查）。
  ⚠️ **未验证**：单层通配是否覆盖 `feat/a/b` 多级分支名，需在 CNB Web 实测（本环境跑不了流水线）。
- **`_is_secret_url` 最小合法化**：原实现只认「URL 含 `secret`」，而 `fundmate-secret`
  恰好叫这个名字 ⇒ 密钥仓改个名，**安全判据静默失效**（漏报比误报贵）。
  改为同时认「文件名形如 `vars.yml`」，并补两条探针（改名后合法形态不误报 /
  改名后流水线级引用**仍报错**；反向：`vars.example.yml` 是文档，引用它**不**误判）。
- **发现并修掉第二处「拿不到 ⇒ 报正常」**（#179 验收 ②）：`github_cnb_issues.py` 的
  `fetch_github_open_issues()` 原先只返回 list，**分页中断 / 翻页触顶与「真的 0 张」
  无从区分** ⇒ `run()` 会打印「✅ 无新增，两侧已对齐」。这正是 #171 那个假绿
  （状态回流作业）**换了个作业复发**。改为返回 `(issues, complete)`，不完整时
  禁止宣称对齐并以退出码 1 结束；新增 5 条回归用例。
- **文档口径同步**：`AGENTS.md` 里那段「`main` 领先 0 …… 出现 `main` 领先 `dev` 就是分叉」
  **与真实正常态相反**（发版后 `main` 必然多一个 merge commit），已改写为二分表；
  `docs/dev/github-cnb-mirror.md` §11 判据段重写，补「为什么用 `git cherry` 不用 `git diff`」
  的实测留证。

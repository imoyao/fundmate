## 1. 需求一句话

系统在**每个自然周期（周 / 月 / 季 / 年）的净值数据就绪后**，自动算好这一期的复盘结果并**落库成快照**，
通过**消息箱**推送一条提醒；用户点开提醒，深链到复盘页，以**周 / 月 / 季 / 年**四种自然周期，回答三个问题：

1. **这段赚了多少**（区间收益额 / 收益率）；
2. **和基准比怎么样**（同期沪深300 等指数的涨跌 vs 我的超额）；
3. **谁拖后腿了**（区间内逐品种盈亏排行，正负榜）。

> **定位说明（O5 已拍板）**：本页**即 issue #875「核心分析报告生成」的落地形态**。
> #875 原设想是「图文报告 + 邮件推送」，本次只做「交互式页面 + 站内消息提醒」，**邮件推送延后**（见 §9）。
> 因此本方案是 #875 的**第一期实现**，不是 #875 之外的新东西。

## 2. 现状：后端地基已铺好一大半（本文最重要的结论）

这次需求**不是从零造数据管道**，而是把四个已经存在、但各自独立、且都只支持「滚动窗口」的能力，
**用「自然周期」这个新维度串起来**。逐项核对如下：

| 需求能力 | 后端现状 | 位置 | 缺口 |
|---|---|---|---|
| 区间收益额 | ✅ `range_pnl` / `month_total`（元，唯一口径） | `pnl_calendar.build_daily_pnl_series` | 无 |
| 区间收益率 | ✅ `range_rate`（区间盈亏 ÷ 区间前一天净资产） | 同上 | 无 |
| 基准区间涨跌 + 超额 | ✅ `excess_return`，基准自动选取/诚实降级 | `analytics/benchmark_excess.py`（#2134） | 无 |
| 逐日累计曲线（我的 vs 基准） | ✅ `series` 双线（末点 ≡ 单值） | 同上 `_build_cum_series` | 无 |
| 品种盈亏归因（拖后腿） | ✅ `positions[]` 按 |pnl| 降序 + `categories` 大类 + `pct` 占比 | `pnl_calendar.compute_range_attribution`（#2135） | 无 |
| **周 / 季 自然周期** | ❌ 只有 `day` / `month` / `year` 三粒度 | `pnl_calendar.build_pnl_series`（#1925） | **新增 week / quarter** |
| **前后翻页（上一期 / 下一期）** | ❌ 现有端点只认 `start_date`/`end_date`，无「按周期键翻页」概念 | — | **新增周期键语义** |
| **净值就绪判定** | ⚠️ 有 `is_rest_day`/`runs_on_rest_day`，但无「本周期最后交易日净值已齐」判定 | `daily_scheduler.py` | **新增就绪判定** |
| **报告快照落库** | ❌ 无 report/periodic_review 表 | — | **新增表** |
| **定时调度（排在净值 job 之后）** | ✅ 进程内 APScheduler，已有「净值 21:30 → 现价 22:15 → 回填 22:35」的时序编排 | `daily_scheduler.py`（#1467） | 新增一个 job |

**结论**：真正的**新增工作**集中在四点——
① 后端 `pnl_calendar` 加 `week` / `quarter` 粒度（纯增量）；
② 前端加「自然周期选择 + 前后翻页」导航与周期键 → 起止日换算；
③ 一个「周期数据就绪」判定 + 定时生成 job + 报告快照表；
④ `category` / `source_type` 两个字段收敛成枚举真相源（顺手把现有松散分类统一，见 §5.2）。

其余（收益 / 基准 / 超额 / 品种归因）都是**把现有函数用自然周期区间再调一遍**，不重写口径。

## 3. 方案骨架

### 3.1 后端：新增 `week` / `quarter` 粒度

在 `pnl_calendar.py` 上做**纯增量扩展**，不碰现有 `day/month/year` 的任何口径：

- `GRANULARITY_WEEK = 'week'`、`GRANULARITY_QUARTER = 'quarter'`，并入 `GRANULARITIES`；
- `_period_key` 新增两个分支：
  - `week` → ISO 周键（`YYYY-Www`，如 `2026-W47`）；
  - `quarter` → `YYYY-Qn`；
- `_aggregate_periods` 的 `rate` 分母逻辑**无需改**（它已经用「上一期间末净资产」推进，与周 / 季天然兼容）。

**周报边界（已拍板 O1）**：采用**自然周（周一~周日）**，与国内投顾语境一致。
周期键用 ISO 周序 `YYYY-Www` 命名，但起止日按自然周换算（周一 ~ 周日）。

### 3.2 前端：自然周期导航（替换滚动窗口）

现有 `utils/chartRange.ts` 是「近 1 月 / 近 3 月 …」的**滚动窗口**，与「周报 / 月报 / 季报 / 年报」
是**两套东西**，不能硬塞。方案是**新增一个独立的周期导航组件**，而不是改 `chartRange`：

- 周期切换器：`周` / `月` / `季` / `年` 四个分段按钮；
- 前后翻页：`<` `>` 箭头 + 当前周期标签（如 `2026年5月`、`2026年第20周 (05/11-05/17)`、`2026年Q2`、`2026年`）；
- 点击周期标签弹出日期选择器快速跳转（沿用 asset-review.md 组件 1 的交互）；
- 周期键 → 起止日换算集中在一个纯函数里（可单测），**不散落**在组件里。

### 3.3 页面组装：复用现有区块，新铺「区间绩效」层

现有复盘页 `/analysis`（`IntelligentAnalysis.vue`）已经有：收益概览 / 货基收益 / 清仓周期复盘 / 净值走势。
本方案**不删这些**，而是在其上**新增一个「区间绩效复盘」区**，或者——更干净的做法——**作为该页的一个
顶部主区块**，因为「这段赚多少 + 和基准比 + 谁拖后腿」正是复盘页标题「时间维度上的表现」的**自然延伸**。

区块内部结构（对齐 asset-review.md 的组件 2 / 3）：

1. **三张摘要卡**：区间收益额 / 收益率（含年化换算，仅月/季/年报显示）/ 超额收益（跑赢跑输基准）；
2. **走势图**：柱状（周期内总资产/盈亏）+ 双折线（我的累计收益率 vs 基准累计收益率）——复用 `series`；
3. **盈亏排行榜**：`盈利先锋` / `亏损大户` 双榜，按品种 |pnl| 降序，点击跳转持仓详情——复用 `positions`；
4. **收益日历**（O3 已拍板并入）：复用 `PnlCalendar` 组件（`host-header` 模式），展示周期内的逐日 / 逐月
   收益热力，与「区间绩效」形成「宏观三卡 + 微观日历」的呼应。

> 注意：asset-review.md 里「击败 X% 投资者」卡片已在原始设计中被移除（需外部大样本数据），
> 本方案**不恢复**。

#### 3.3.1 收益日历并入的一个真实约束（需在实现时解决，不是拍板项）

`PnlCalendar` 现在只支持 `day / month / year` 三粒度（`PnlCalendarGranularity`），而本页的周期是
`week / month / quarter / year`。两者**粒度集合不完全一致**（本页多 `week`/`quarter`，缺 `day`）。
并入时有两种取法，实现时择一（见 O3 的补充说明）：

- **A（推荐）**：本页的周期切换器与日历**各自独立**——周期切换器管「区间绩效」的 week/month/quarter/year，
  日历仍用自己那套 day/month/year 粒度，互不耦合（日历是「区间内的明细热力」，不是「区间的另一种切法」）。
- **B**：给 `PnlCalendar` 也加 week/quarter 粒度，两处共用同一套周期。**不推荐**——会让日历这个已稳定的
  通用组件背上「自然周期」的额外语义，扩大改动面、风险外溢到 welcome/panorama 两个既有宿主。

## 4. 触发链路：净值就绪 → 定时生成 → 消息箱提醒

这是本次新增的、区别于「纯页面」的关键一环。数据流如下：

```
净值落库 job（已有，21:30，daily_scheduler #1467）
        ↓ 数据就绪信号
「本周期最后交易日净值已齐」判定（新增）
        ↓ 满足即触发
周期报告「生成」job（新增，排在净值 job 之后）
        ↓ 生成结果落库（新增 report 快照表，§7）
        ↓
写一条 category=report 的站内通知（复用 emit_many）
        ↓
用户点开消息盒 → 深链到复盘页 → 读到那一期的落库快照
```

### 4.1 净值就绪判定（这是最容易想当然、必须钉死的点）

报告的触发**不是「时钟时刻」**，而是**「该周期最后一个交易日（且基金净值已披露落库）」这个数据就绪信号**。
理由：报告不能按时钟生成，而要看数据就绪——只有等**这个周期里最后一笔可算的净值**落库了，
统计出来的数字才完整、不会漏掉最后一天的涨跌。

- **周报**：当周最后一个交易日（通常是周五，但节假日顺延）的净值披露落库后触发；
- **月报 / 季报 / 年报**：同理，是「该周期最后一个交易日」的净值就绪，而不是自然月/季/年的最后一天。
  - 关键场景：月末/季末/年末恰好是**周末或节假日**时，触发点顺延到**最后一个实际交易日**的净值就绪。

**净值披露口径**（owner 已纠正）：场外公募基金净值是 **T 日晚间（约 20:00 后陆续披露）~ T+1 就出来**，
不是「等到下周一」。因此「周五汇总」的落地时点是**周五收盘后净值披露落库完成**，周五晚到周六即可发生。
（QDII 类净值披露更慢，T+2~T+3；owner 拍板 O6：QDII 不常见但肯定会有，故就绪判定需容忍其延迟，
未齐时对该周期做**诚实降级标注「含 QDII 未齐」**，而非忽略或误报完整。）

### 4.2 复用 daily_scheduler，不引消息队列

现有 `daily_scheduler.py`（进程内 APScheduler，`BackgroundScheduler` 薄封装，#1467）已经精确解决了
「净值 21:30 / 现价 22:15 / 回填 22:35」这类「必须晚于某类 job」的时序编排。本需求要的
「净值落库后汇总」，本质就是**往这个调度器里加一个 job**，让它排在「净值落库 job」之后触发。

**为什么明确不引入消息队列（RabbitMQ / Celery / Redis Stream）**：

1. **规模不匹配**：消息队列解决的是高吞吐异步解耦、削峰填谷、跨服务投递。本场景是「每个家庭每周/月/季/年
   各 1 条站内通知」，量级极小，且本就同步落在本地 SQLite/PG 的 `notifications` 表，无跨服务、无高并发。
2. **引入成本远大于收益**：引入队列 = 加 broker（部署依赖）+ worker 进程 + 重试/死信机制。而项目当前是
   **单实例 + 进程内 APScheduler**（记忆里有 `instance_guard` 持进程锁、`Dockerfile workers 1` 的单实例硬约束）。
   为一个「每周几条站内消息」的需求引入分布式队列，是典型的过度设计。
3. **现有的懒生成路线已经足够**：`notification_service.py` docstring 明确「站内消息只在用户在线时才消费，
   真正的定时任务要等站外推送（#508）才需要」。本需求虽引入了「定时生成报告」，但**报告快照的落库是同步的**，
   站内通知也是同步写表，全程不需要跨进程投递。

## 5. category 收敛成枚举真相源（解决「通知没分类解耦」）

### 5.1 现状：分类是「松散字符串约定」，不是「枚举真相源」

`Notification.category` 是 `String(20)` 自由字符串，注释写 `strategy / watchlist / system / rebalance`，但：

| 生产方 | 写入的 category | 位置 |
|---|---|---|
| 策略引擎 | `'strategy'`（裸字符串） | `allocation.py` |
| 自选提醒 | `rules.NOTIFICATION_CATEGORY = 'watchlist'` | `alerts/rules.py:43` |
| 分红税 | `'system'`（裸字符串） | `dividend_tax_service.py` |
| 调仓提醒 | `CATEGORY_REBALANCE = 'rebalance'` | `rebalance_alert.py:48` |

前端 `lay-notice/data.ts` 的 `noticeTabs` **写死了 4 个 Tab**，每个硬绑一个 category 字符串。三层耦合：

1. **后端无集中定义**：每个生产方各写一个字符串字面量，新增一种消息就得「自己决定填什么 + 前端手动加 Tab」。
2. **`category` 与 `source_type` 边界不清**：`category`（来源分类）与 `source_type`（产生来源）高度重叠，
   两列并存本身就是「分类没想清楚」的症状。
3. **前端 Tab 硬编码映射**：一旦出现第 5 种 category（如 `report`），前端没有对应 Tab，消息要么落错 Tab、要么不显示。

### 5.2 方案：两个字段一并厘清（O7 已拍板「厘清」）

先厘清两者的**真实语义边界**（这是 O7 的核心，证据来自代码消费端）：

| 字段 | 语义 | 粒度 | 取值（现状） | 消费端职责 |
|---|---|---|---|---|
| `category` | **来源大类** | 粗（5 类） | `strategy` / `watchlist` / `system` / `rebalance`（+ 新增 `report`） | 前端**分 Tab**（`noticeTabs`） |
| `source_type` | **具体产生来源** | 细（6 类） | `allocation_deviation` / `trend_signal` / `watchlist_alert` / `dividend_tax_pending` / `dividend_tax_suspect` / `advisor_rebalance` | 前端**分色 + 深链判断** |

**结论：两者不是并列的模糊语义，而是「大类 → 细类」的严格层级**——一个 `category` 对应一到多个
`source_type`（如 `strategy` 大类下含 `allocation_deviation` + `trend_signal` 两个来源）。
证据：`dividend_tax_service.py` 的测试明确「`proportion` 异常与 `未扣税` 是两种诉求，不能共用一个
`source_type`，否则前端无法分色」——即 `source_type` 承载「细分诉求」，`category` 承载「归桶」。

因此 O7 的厘清落点是**两个枚举真相源，各自收敛，并声明映射关系**：

- **后端建唯一常量集** `category`（`system / strategy / watchlist / rebalance / report`）与
  `source_type`（上述 6 个 + 本次新增 `periodic_report`）各一份，所有生产方只能取枚举、禁裸字符串；
- **声明映射**：`category` 是 `source_type` 的上层归桶（`report` 大类下目前只有 `periodic_report` 一个来源）；
- **前端**：`noticeTabs` 与「分色/深链」两个消费点各自按对应枚举驱动，新增一类消息只需加枚举值 + 映射，
  不再散落改前端结构；
- 新增 `report` 大类 + `periodic_report` 来源，承载「周报/月报/季报/年报已生成」通知。

## 6. 数据就绪与「自然周期」的技术细节（§3.1 的补充）

### 6.1 自然周期 vs 滚动窗口

「周报 / 月报」是**自然周期**（有明确起止、能前后翻页到历史任意一期），区别于现有前端的「近 1 月 / 近 1 年」滚动窗口。
后端 `build_pnl_series` 目前只有 `day / month / year` 三粒度，**没有 week / quarter**，需新增。

### 6.2 周期键 → 起止日的换算

- `week` → ISO 周键 `YYYY-Www`，起止 = 自然周（周一 ~ 周日，已拍板 O1）；
- `month` → `YYYY-MM`，起止 = 1 日 ~ 月末；
- `quarter` → `YYYY-Qn`，起止 = 季首月 1 日 ~ 季末月末；
- `year` → `YYYY`，起止 = 1 月 1 日 ~ 12 月 31 日。

这套换算**前后端各需一份**（后端做区间查询、前端做标签展示），前端版本集中在纯函数可单测，后端版本集中在
`pnl_calendar` 的 `_period_key` / 一个 `period_bounds(key)` helper。

## 7. 报告快照表（新增，推翻初版「零新增表」）

### 7.1 为什么要落库

引入「定时生成 + 消息提醒」后，「这一期的报告」就**不能是每次打开页面时现算**了。否则：

- 消息提醒点进去看到的数字，可能和「生成那一刻」不一致（用户之后改了持仓 / 补了流水）；
- 「定时生成」的语义就是「把那一刻的账定格下来」，不落库则提醒失去意义。

故**报告结果落库成快照**，消息提醒只引用快照，页面读取快照展示（必要时对「当前最新一期」仍可现算兜底）。

### 7.2 表设计草案（待定，非冻结）

```
periodic_review_reports
  id                    (PK)
  family_id             (家庭隔离键，家庭级报告)
  period_kind           (week / month / quarter / year)
  period_key            ('2026-W47' / '2026-11' / '2026-Q4' / '2026')
  period_start          (Date，周期起始)
  period_end            (Date，周期结束)
  generated_at          (DateTime，生成时间)
  caliber_version       (口径版本，口径一变即作废重算，对齐 PnlDailySnapshot)
  payload               (JSON，快照主体：区间收益额/收益率/超额/品种归因/基准曲线)
  unique(family_id, period_kind, period_key)
```

### 7.3 关键设计约束（对齐 AGENTS.md 数据策略与 PnlDailySnapshot 范式）

- **快照 vs 现算的边界**：快照只存「报告结论 + 图表序列」，**不替代** `pnl_calendar` 的现算口径。
  用户点开「历史某一期」时读快照；点开「当前进行中的一期」时可用现算兜底（因为当前期还没「就绪」）。
- **口径版本号**：沿用 `PnlDailySnapshot.caliber_version` 的范式，`pnl_calendar` 口径一变，旧快照全作废重算，
  避免「口径改了但快照还是旧口径」的静默漂移。
- **幂等 upsert**：`(family_id, period_kind, period_key)` 唯一，重复生成不产生重复行。
- **读者明确**：快照的读者 = 复盘页「历史期读路径」+ 消息箱深链。没有别的读者，不造冗余列。

> **已拍板 O8**：`payload` 用**单列 JSON**（报告结论是可变的展示层数据，不是查询维度）。

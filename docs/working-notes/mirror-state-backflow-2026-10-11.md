# 镜像卡状态回流（2026-10-11）

> 脚本：`scripts/bridge/mirror_state_sync.py`　流水线：`.cnb.yml`（cron 收尾阶段）
> 回归网：`scripts/tests/test_mirror_state_sync.py`（**54** 条，2026-10-13 增 `TestIncompleteDataNotGreen` / `TestCloseIssueEndpoint` / 补关用例）　决策：`docs/spec/decisions.md` D48 → **D55（现行）**

## 1. 问题：正文对齐了，状态还停在建卡那一刻

`github_cnb_issues.py` 只做**建卡**，建完即止。于是镜像卡溯源块里的「状态：`open`」
是**建卡当时的快照**——GitHub 之后把卡关了，CNB 侧一个字都不变。

读者在 CNB 看到一张「还活着」的卡，实际那件事早已结案。这比两侧**明显**不一致更难察觉：
它看起来权威、没人会去核，下一个人照着它继续讨论。

cnb #117 的原话是「正文对齐了，讨论仍然分叉」，本卡补的是同一族里更靠前的一环——
**连状态都没对齐**。

## 2. 先核对了既有边界：#117 的硬要求 ① 已由 #120 收尾

开工前逐条核对，避免重复造：

| #117 的要求 | 现状 |
|---|---|
| **硬要求 ① 人工回路必须保留** | **已完成**——#120 的方案 A（溯源块时效声明）+ 方案 B（`mirror_correction.py` 评论区更正台账）已落地并关闭该卡 |
| **硬要求 ② 元数据必须同步** | **本次补**——标签 / 优先级 / 里程碑建卡时已同步（§4 字段映射），缺的是**状态** |

所以本次只做状态，不重做更正通道。

## 3. 裁决：状态同步为「**标记**」，不是「自动关」（⚠️ 已由 §13 的 D55 推翻，保留原样以备回溯）

原取舍写「不同步关闭态」，理由正当：**「CNB 关了」会被误读成「这事不做了」**，
而关闭与否该由人拍板。这条理由**现在仍然成立**——CNB 侧的追问往往发生在 GitHub 关掉
**之后**，直接把卡关掉会把那些讨论一起埋掉（那正是硬要求 ① 要保的人工回路）。

但「一个字都不说」同样会误读。故本作业采取**标记法**：

- 在该卡评论区追加 `## 状态回流（日期）` 评论（含事实、依据链接、隐藏幂等键）；
- 给该卡挂 `GitHub 已关闭` 标签（看板可筛）；
- 评论正文**明写**「本卡**不会被自动关闭**」，并给出人工入口
  `cnb issues close --number <n>`。

**把关闭事实说清楚，但不替人做关闭这个决定。**

## 4. 漂移只认一个方向

| GitHub | CNB | 判定 |
|---|---|---|
| closed | open | **漂移** → 回流标记 |
| closed | closed | 已对齐 |
| open | open | 已对齐 |
| open | closed | **不回流** |

最后一行是刻意的：**CNB 侧关卡是人的决定**（讨论已结束），GitHub 后来重开原卡不代表
CNB 侧那些讨论又活了。若反向回退，脚本就变成「GitHub 只要还开着，CNB 就不许关」——
等于取消人工回路，正是硬要求 ① 要防的。

## 5. 幂等键带上 `updated_at`

```
状态键 = sha1(CNB 编号 | GitHub 编号 | 状态 | GitHub 侧 updated_at)[:12]
```

带上 `updated_at` 是为了让「**关闭 → 重开 → 再关闭**」各发一条——
否则第二次关闭会被当成重复而**静默吞掉**（正是本仓反复治的「静默失败」形态）。

## 7. 边界

- **标签 / 优先级 / 里程碑建卡后的漂移本作业不处理**：「只增不覆盖」的直接推论。
  改它需先拍板「镜像卡是只读副本还是允许修正的本地副本」——口径仍归 CNB #117。
- **拉不到 GitHub 载荷的卡跳过而不是猜**（限额 / 卡被删）：`plan()` 显式返回空，不臆测状态。
- **`.cnb.yml` 用 `|| true`**：建卡才是主任务，状态回流是收尾信号，不该把建卡一起拖红。

## 8. 真实数据核对与「演练」的诚实边界

**跑在真实数据上**（`--report`，真 GitHub + 真 CNB）：

```text
⚠️ GitHub 限额用尽（403），只拿到前 1 页共 56 张；本轮的卡可能漏标。
📥 GitHub issue 56 张；CNB 镜像卡 107 张
✅ 无状态漂移，两侧已对齐
```

- **真实闸门判得对**：`is_mirror_card(106)=True`、`is_mirror_card(117)=False`、
  `is_mirror_card(120)=False`——镜像卡与人工卡在真实接口上区分正确（`mirror_correction`
  依赖同一条闸门）。
- **真实评论解析**：#106 拉到 **14** 条评论，`existing_state_keys` 为空集（当前无状态回流）。
- **两个 POST 端点的形状经真实接口验证**：对不存在的卡号调用，`/comments` 与 `/labels`
  都返回业务错误 `{"errcode":404,"errmsg":"not found"}`——说明 URL / 方法 / 鉴权头 /
  载荷都被 API 接受（若写错会得到 401 / 405 / HTML 而非规范 JSON）。**即：没有产生任何写入。**

**为什么没做「真实写入演练」**：`--report` 跑完全库后确认**当前零漂移**——
107 张镜像卡对应的 GitHub issue 全部仍是 `open`，而被关闭的 GitHub issue（69 张）
在镜像时就已经关着、从未被镜像。**没有自然的演练目标。**

刻意**不**在别人的镜像卡上试写：CNB 的 issue 评论**没有删除接口**
（`cnb issues --help` 只有 `post` / `get` / `patch`，无 `delete`），
一条演练评论会**永久留在**真实卡上。#120 当时能在 #106 上演练，是因为那条评论
**本身就是产物**（第一条真实更正）；状态回流没有这个便利。

故本卡的「演练」停在**端点形状 + 闸门 + 解析**三者的真实接口验证上，
**首次真实写入将发生在下一张 GitHub 卡被关闭时**——那时 `cron` 会自动做，
且幂等键保证不会重复。要提前手动演练，用：

```bash
# 先看漂移（不写）
python scripts/bridge/mirror_state_sync.py --report
# 确认目标卡后再单张执行
python scripts/bridge/mirror_state_sync.py --cnb <编号> --apply
```

> 这条边界写下来，是为了不让下一个人把「单测全绿 + 端点探过」误读成「线上跑过了」。
> 本仓对「守门通过 ≠ 守门有效」有明确纪律（`AGENTS.md`），这条是它在**写入路径**上的对应物。

## 12. 上线后失效复盘：它是绿的，但它一次都没干活（#171，2026-10-13）

> 本节是**上线即失效**的复盘。原「真实写入演练有意未做」那条边界（见上节）——
> 我们当时以为风险是「没演练过所以不放心」；实际发生的是**它根本跑不起来，而且不报错**。

### 症状

用户反馈「GitHub 关掉的 issue，CNB 这边不同步关闭」。本地跑 `--report`：

```text
⚠️ GitHub 限额用尽（403），只拿到前 0 页共 0 张；本轮的卡可能漏标。
📥 GitHub issue 0 张；CNB 镜像卡 107 张
✅ 无状态漂移，两侧已对齐          ← 一张 issue 都没拉到
```

**0 张输入，输出「已对齐」。** 这是假绿里最贵的一种形态：

- 假红有人去修；**假绿没人去看**；
- 它还带 `|| true` 收尾 ⇒ 连红灯都不会有；
- 于是这张网从上线起**一直绿、一直没干活**，而所有人都以为它在织。

### 根因（两层叠加，缺一不成立）

1. **额度不够**：`fetch_github_issues_by_number()` 用 `state=all` 翻页（含已关闭卡），
   而 `.cnb.yml` 的 `env` 只写了 `GITHUB_REPO`——`GITHUB_TOKEN` 是「可选，不设则匿名」。
   匿名 **60 次/时/IP**，且同一条流水线里**建卡 job 先跑、先吃额度**；
   仓库 issue 已 200+ ⇒ `state=all` 要 3 页 ⇒ 第 3 页 403。
   （实测：本机 2026-10-13 连续跑两次，均在第 1~3 页之间撞 403，`rate_limit` 显示 `remaining: 0`。）
2. **「拉不到」被当成「没漂移」**：403 时函数 `break` 返回**空映射**，
   而 `run()` 里 `if not todo: print('✅ 两侧已对齐')` ⇒ 空映射 = 空 todo = 报告对齐。

文件头当时写的「少拉只是少标记、不会误标」**对误标是对的**（`plan()` 确实跳过而非猜），
但它漏了另一面：**少拉到 0 时，报告会给出一个完全错误的结论**。
「不会误标」不等于「结论可信」——这正是这次翻车的地方。

### 修法

| 改动 | 位置 |
|---|---|
| 返回 `(映射, 是否完整)` 二元组，把「完整性」当一等值 | `fetch_github_issues_by_number()` |
| `complete=False` 时**一律不得宣称对齐**，打印「数据不完整，本次结论不可信」 | `run()` |
| `complete=False` ⇒ **退出码 1**（让 cron 看得出没跑成） | `run()` |
| 部分数据**照做但不背书**（`plan()` 本就跳过拿不到的卡） | `run()` |
| `|| true` 改为回显退出码（不吞「数据不完整」） | `.cnb.yml` |

回归网 `TestIncompleteDataNotGreen`（3 条），**2 轮反向探针 CAUGHT**：

- S1 去掉 `not complete` 分支 ⇒ 退回假绿 ⇒ CAUGHT；
- S2 永不置 `complete=False` ⇒ 永远「完整」⇒ CAUGHT。

### 仍未做（留给后续）

- **注入 `GITHUB_TOKEN`**：这是根因里最省事的一半（60 → 5000 次/时）。凭据在
  `fundmate-secret` 仓库，API 一律 403，**只能人工在 Web 界面改**，改不进 PR。
  在补上之前，即使修好了假绿，`--report` 也会**如实报「数据不完整」**——
  那是**正确的红**，不是噪声。
- **按编号直查替代翻页**：107 张镜像卡对应的编号已知，`GET /issues/{n}` 可绕开
  「拉全量再筛」的窗口错配（`sort=updated` 会把老卡挤到后面，老卡可能根本不在拉取窗口里）。
- **关卡口径**：维持 D48 的「标记不关」，还是要改成自动关，见 #171 的讨论。


### 12.5 修复后复跑：三个新事实（2026-10-13 实测）

修好假绿后立刻复跑 `--report`（真 GitHub + 真 CNB），**它当场吐出了原先被掩埋的全部真相**：

```text
❌ GitHub 返回 422，中断在 page 11；本轮已拿 418 张 —— 数据不完整。
📥 GitHub issue 418 张；CNB 镜像卡 107 张
❌ 数据不完整，本次结论不可信（已判定漂移 15 张…）
🆕 待回流 15 张
  ⏭️  …（13 张）状态已回流过，跳过
  [DRY-RUN] CNB `#91` ← GitHub `#1968` closed
  [DRY-RUN] CNB #35 …（另一张）
```

**事实一：确实存在 15 张漂移卡。** 原先的「✅ 两侧已对齐」是**彻头彻尾的假话**——
改一行判据，15 张卡当场现形。这是本次修复最直接的证据。

**事实二：机制其实工作过，13/15 已经回流了。** 逐张查评论区：`CNB #110`（GitHub #2044）、
`CNB #106`（#2034）、`CNB #35`（#965）评论区都有 `## 状态回流` 评论 + 幂等键。
即 D48 的「标记不关」**执行过**，卡上挂着 `GitHub 已关闭` 标签——但卡**仍是 `open`**。

> 这解释了用户最初的观感：「GitHub 关掉的 issue，CNB 这边不同步关闭」。
> **行为符合 D48 的设计**（标记不关），只是用户期待的是**真的关上**。
> 故「修网」与「改口径」是**两件事**：#171 的假绿是缺陷（已修），
> 「要不要自动关」是产品决策（待拍板，见 §12「仍未做」）。

**事实三：page 分页在 1000 条处硬停（422）。** 修复前只暴露了 403；修复后露出了第二个
独立的坑——GitHub 已对**大结果集禁用 page 参数**：

```json
{"message":"Pagination with the page parameter is not supported for large datasets,
 please use cursor based pagination (after/before)"}
```

实测 page 9/10 正常（各 100 条），**page 11 直接 422**——即阈值是 **1000 条（page 10）**。
这对本作业是**第二个「永远够不到老卡」的原因**：镜像卡是 `#783`~`#2050` 的**老卡**，
而 `sort=updated` 会把它们排到 1000 名之后。《修法》里列的「按编号直查替代翻页」
不再只是优化，而是**必须**——否则 107 张镜像卡里靠后的那些**永远落在可达窗口之外**。

**结论：假绿不只是一个报错问题，它是一个观测窗口。** 判据一旦会红，
埋在底下的两件事（15 张真漂移、page 上限）**当场自己浮出来**——
这就是为什么「修好假绿」必须先于、且独立于「改口径」。

### 教训（值得单独记一条）

> **任何「拿不到输入就当没有」的判据，都是假绿生产线。**
>
> 判据的失败语义必须显式：拿不全 ⇒ 说拿不全，**不得**退化成一个看起来正常的结论。
> 这条对守门脚本同样成立——`AGENTS.md` 的「守门通过 ≠ 守门有效：必须用探针自检」
> 治的是「判据写错方向」，本条治的是「判据没有失败态」。

## 13. 口径变更：「标记不关」→「自动关」（B 口径，2026-10-13，源 #171 用户拍板）

### 为什么改

§12 修完「假绿」之后，才**第一次真实看到**问题全貌。用户随即在 CNB #171 选了 **B**：

> B：改成 GitHub 关了 CNB 就自动关——最干净，两边彻底一致，代价是可能埋掉 CNB 侧后续讨论。

**不是「D48 的理由错了」，而是权衡变了。** D48 说「CNB 侧追问常发生在 GitHub 结案之后，
关掉会埋掉讨论」——这话仍成立；但它换来的是另一个更贵的状态：
**「卡片状态」与「事实状态」永久劈成两半**。看板上是一张「还活着」的卡，
GitHub 上早已结案；读者得打开卡、翻到评论区，才可能看到那条回流评论。
**看板越用越不可信 —— 这个代价高于埋掉讨论。**

### 没有丢的东西

| 原本担心 | 现行的兜底 |
|---|---|
| 讨论被埋 | **评论不删**，卡片只是变灰；`cnb issues open --number <n>` 一条命令重开 |
| 人工回路被取消 | **反向仍不回流**（GitHub open + CNB closed ⇒ 不动），CNB 侧关卡仍是人的决定 |
| 想先人工看一眼 | **`--no-close` 逃生阀**：只标记不关 |

### 切口径最容易被忽略的一步：补关存量卡

D48 时代已有 **13 张卡**发过回流评论、却仍是 `open`（那正是旧口径的本意）。
切到 B 后**必须补关**，否则就是「口径改了、那些卡继续漂着」——换个说法继续不一致。

故 `run()` 里两条判据**分开**：

| 动作 | 判据 |
|---|---|
| 发评论 | 幂等键 `状态键：<sha1>` 是否已存在（同一事实只发一次） |
| 挂标签 | 总是尝试（CNB 侧幂等） |
| **关闭卡片** | **与评论无关** —— 漂移卡就应该关 |

### 真实数据核对（不是纸面绿）

```text
📥 GitHub issue 418 张；CNB 镜像卡 107 张
🆕 待回流 14 张（自动关闭：开）
  [DRY-RUN] CNB `#110` ← GitHub `#2044` closed：关闭卡片      ← 评论已存在，只关
  ...
  [DRY-RUN] CNB `#91`  ← GitHub `#1968` closed：发回流评论、关闭卡片   ← 唯一需要补评论的
```

- `--report`：14 张漂移卡里 **13 张只需「关闭卡片」**、1 张（#91）评论 + 关闭 —— 分离判据生效；
- `--cnb 35 --apply`（真实写入）：CNB #35 由 `open` → `closed`，`state_reason=completed`；
- 二次执行：**0 漂移**（幂等）；
- 端点形状经 `cnb-cli` 的 `dist/index.js` 核实为 `PATCH /{repo}/-/issues/{number}`。

### 探针咬不住的那条判据，在做假装的工作（S5 实录）

第一轮反向探针里，**S5「已关闭的卡再关一次」是 MISSED**。原因是 `run()` 里写着

```python
need_close = auto_close and card['cnb_state'] != 'closed'
```

而 `plan()` 只交出漂移卡、`state_drift()` 已排除「两侧都关」⇒ 该条件**恒真**，
是**死代码**：它不承担任何职责，探针也咬不住它（改掉它不改变任何行为）。

处置：**删掉这条冗余判据**，把幂等契约**钉在 `plan()`** 上，并新增
`test_plan_永不交出已关闭的卡` 独立钉住它。这是 `AGENTS.md`「守门通过 ≠ 守门有效」
的又一次实证——**探针咬不住的分支，往往是在做假装的工作**。

### 教训（第二条）

> **切口径时，先问「存量数据按新口径该怎么办」。**
>
> 口径变更只改代码是**一半**的活。旧口径已经产出过的事实（13 张「评论已发、卡没关」）
> 必须被新口径**收编**，否则系统会分裂成「新卡按新规矩、老卡按老规矩」两套真相——
> 而这恰恰是本次要消灭的形态。

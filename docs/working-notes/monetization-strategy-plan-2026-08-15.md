## 0. 为什么现在就要规划（两个核心顾虑）

当前没有商业化计划，但开发阶段就要给功能打"付费/免费"标签。驱动这次规划的只有两件事：

- **防止背叛感**：如果一个功能用户现在免费用得顺，以后变成付费，用户会觉得被背刺。
  这正好对应 `pricing-tier.md` §1 准则 3：**免费→付费禁止**（损失厌恶，已免费的功能不得转收费）。
- **覆盖成本**：功能要算边际成本，否则即使收费也覆盖不住。AI 识别这类真 API 计费功能
  必须有配额/护栏（见 §5 与 `pricing-tier.md` §5）。

结论先行：这两点**已经被现有规范的结构性设计解决**，本计划只是把它们从"准则"落成"定价数字 + 支付 + 冷启动动作"。

## 1. 核心原则（不可妥协）

1. **免费功能永不转收费，免费额度地板永不收缩**。
   现有免费功能（核心记账、导入导出、探市、温度计、自选基础、每日收益日历）永远免费不限次；
   OCR 的"免费 5 次/天"兜底**永不收回**——只增不上收。Pro 只做"加法"（更高/无限额度、深度分析），
   绝不做"把免费改收费"。这是从架构上根除"老用户不如狗"的唯一正道，也是准则 3 的实操化。
2. **老用户价格锁定，新用户随行就市**。
   未来上线付费层时，采用"早鸟锁定价"：早鸟期购买的用户，续费价格永久锁定；正式期新用户按新价。
   锁价由**支付网关的订阅价格锁定**实现，不在应用代码里写"判断老用户"的逻辑（见 §3、M-2）。
3. **高成本功能用"软配额"而非"硬拦截"**。
   免费额度用尽时，用浅灰横幅引导升级，**绝不弹阻断式报错弹窗**（对齐导入页评审 I-5 的"得体配额制"）。
4. **复杂度最小化**：当前只做 免费版 + Pro 版 两档；不引入 Ultra / 家庭独立档 / 加油包（见 §7 决策）。

## 2. 会员分层（只做两级）

| 档位 | 定位 | 是否现在做 |
| --- | --- | --- |
| 免费版 | 核心记账 + 免费额度兜底（吸引留存、控制成本） | 已存在（基础功能本就免费） |
| Pro 版 | 无容量上限 + 深度分析 + 更高 AI 额度 | 待 M-1/M-2 落地 |

明确**不做**第三层（Ultra/专业版）与"家庭独立档""加油包"——个人开发者精力有限，多一层就多一套
解释成本 + 开发负担。未来真有家庭需求，把"家庭席位"作为 Pro 的附加包挂上去，不新增页面档位（§7）。

## 3. 定价提案（待定稿，需写入 pricing-tier.md）

> 以下为提案数字，**尚未写入 `pricing-tier.md`**（该规范目前只有分层与归属，无具体价格）。
> 落地须走 M-1，并与 #826 分层定稿保持一致。

| 阶段 | 连续包月 | 连续包年 | 说明 |
| --- | --- | --- | --- |
| 早鸟期（Beta/公测） | ¥9.9/月 | ¥99/年 | 早鸟用户**永久锁定**此价（不中断订阅前提下） |
| 正式期（功能稳定后） | ¥19.9/月 | ¥199/年 | 仅对新用户生效，老早鸟不受影响 |

**锁价机制（关键，避免"杀熟"代码）**：在支付网关（见 §8）上架两个订阅商品——早鸟商品（9.9）与正式商品（19.9）。
早鸟期结束后下架早鸟商品、上架正式商品。老用户续费走原订阅，网关自动按原价扣款；应用侧**只读 `user.plan` 状态，不判断新老**。
这样"早鸟锁定价"零自研逻辑，且天然符合准则 3（不写自定义涨价逻辑 = 不会误伤老用户）。

## 4. 权益与配额边界（对齐 pricing-tier.md §2）

| 能力 | 免费版 | Pro 版 | 依据 |
| --- | --- | --- | --- |
| 核心记账 / 导入导出 / 探市 / 温度计 / 自选基础 | 无限 | 无限 | `pricing-tier.md` §2 免费不限次 |
| 自选数量上限 | 100 个（超出触发 Pro 引导） | 无限 | issue #1000 |
| AI 截图/文本识别 | 5 次/天（兜底，永不收回） | 更高额度 / 无限（卖点） | #823、`pricing-tier.md` §5 |
| 深度分析（归因/风险/乖离率/XIRR 分段） | 不开放 | 开放 | issue #994 |
| 行业拥挤度 / 一键自动源 | 不开放（付费候选） | 开放 | #892/#891、#939 |

**配额口径校正**：讨论稿写"免费 5 次/月"，但本仓库 spec 与 #823 是**每日 5 次**。保持**每日**——
成本更可控，且 §5 的 ~74 元/月测算基于每日口径。上线 Pro 时卖"更高/无限额度"，**不削减**现有免费每日额度。

## 5. 成本控制（已有护栏 + 一处新增降本）

`pricing-tier.md` §5 已算清：OCR 单次 ≈ 0.0037 元；1000 用户 × 5 次/天顶格 ≈ 555 元/月，
现实 20% 活跃 ≈ **74 元/月，可承受**。再加上后端已落地的多层护栏（`guards.py`）：每日配额、每分钟限流 3、
连续失败熔断、全站 token 预算 30 万/日。成本控制基本面已具备。

**唯一新增降本点（工程尚未做）**：前端上传前压缩图片（≤1080px / quality 0.8）。
这能把单次 AI 输入 token 再降一截，是个人开发者防爆单的"物理二道防线"。已内联为导入页评审的 I-4
（关联 #823、#935），本文不重复拆 issue，仅作成本章节引用。

## 6. 冷启动策略（先有用户，再谈转化）

1. **免费核心做磁铁**：手动录入、基础记账、100 自选内实时数据、基础净值曲线 100% 免费、零墙，先把口碑和数据沉淀做起来。
2. **限量早鸟码**：社区（小红书 / V2EX / 少数派）发 50 个"终身早鸟码"，承诺当前价永久锁定。前 50 个付费即产生启动资金，覆盖初期算力。
3. **反馈奖励**：给提高质量建议的种子用户直接赠送 1 个月 Pro 时长，形成正向口碑循环（轻量"意见反馈"入口常驻个人中心，幽灵态不显眼）。
4. **软引导而非硬墙**：免费额度用尽时，顶部浅灰横幅"[ 升级 Pro 获得无限额度 ]"，不弹报错。

## 7. 支付、周期与"家庭版/礼品卡"的极简处置

- **付费周期**：只保留 连续包月 + 连续包年，**去掉季付**（降低订单/续费逻辑复杂度）。年付等价于"买 10 送 2"。
- **支付对接（0→1 基础设施）**：当前仅有 Supabase Auth，**无任何支付网关**。对接第三方订阅服务
  （Lemon Squeezy / Paddle / 国内支持订阅的支付商），用其 Checkout 跳转；后端**只处理 Webhook**：
  收到回调 → 定位 user_id → 置 `user.plan=pro` + 记录 `pro_expire_at`。不自建计费中心。
- **数据字段（极简）**：`users.plan(free|pro)`、`users.pro_expire_at`、`users.ai_usage_month`
  （或复用 `pricing-tier.md` §5 的通用 `user_usage` 表，二选一，不双写）。
- **家庭版**：当前**明确不做**独立档。若出现夫妻共用，朴素方案 = 同一账号登录共享。未来需求明确后，
  把"家庭席位"作为 Pro 附加包（主账号 + N 成员共享权益），不在页面做成第三层。
- **礼品卡**：支付页放"生成 8 位兑换码"功能，受赠人在 Pro 购买页输入激活，**无社交关系链、无好友系统、无动态广场**
  （保持软件纯净边界）。兑换码一次性激活，赠送者账户不受影响。

## 8. 关键校正（粘贴讨论与仓库现实的偏差，避免误落地）

1. **配额口径**：讨论"5 次/月" ≠ 仓库"5 次/天"。以仓库为准（每日，更控成本）。
2. **定价未定稿**：讨论的 9.9/19.9 是提案；`pricing-tier.md` 目前无价格数字，须经 M-1 落定，且不得突破准则 3。
3. **支付尚未接入**：讨论假设"2 天对接 Lemon Squeezy"，但本仓库无支付模块，M-2 是从零建设施。
4. **成本量级**：spec 单次 ≈ 0.0037 元（未压缩）；讨论"压缩后几厘"属乐观估计，压缩是额外降本（I-4），不改变总量级。
5. **"早鸟锁定价"边界**：锁的是"未来付费层的价格"，不是"把现有免费功能变付费"。现有免费功能与 5 次/天兜底永远在。

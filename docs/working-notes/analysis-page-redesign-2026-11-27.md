### 4.2 P2b 落地记录（2026-11-27，资金流动家庭级）

- **`scope=family` 显式才能进**：两个 id 都不传仍是 400。原因不是洁癖——「漏传参数就
  静默变成全家数据」比报错更坏（用户会以为自己筛过了）。`scope` 与 id 自洽校验也在
  后端（`scope=family&ledger_id=` 回 400）。

  「任一成员缺数据当天整体置缺」，与日历对不上。
- **顺带修掉一个存量 bug**：`build_layers` 默认 `include_cash_equivalents=False`（XIRR 的
  口径），资金流动误用了它 ⇒ `asset_type ∈ {cash, money_fund, reverse_repo}` 的流水被

- **家庭级不推导现金残差**：残差的前提是「集合里每个账户的入金都记全了」。账户级能靠

  `cash_residual / end_asset / total_return` 一律 `null`，卡面第 4 张改报**持仓市值**

- **页面位置**：独立区块放在净值走势之后——曲线的台阶就是入金/出金，放下面才对得上

### 4.3 那 22 万是什么（2026-11-27 追查结论）

**一句话：收益概览把 93 条 E账户影子持仓当成了真实持仓，虚增的是纯收益不是市值。**

逐持仓对账（真库，三项合计 223 622，与实差 223 624 只差 1.81 的取价窗口舍入）：

| 成因 | 金额 | 性质 |
|---|---|---|
| 93 条 `shadow` 镜像行进了 XIRR 市值侧 | **+214 911.35** | 真 bug，已修 |
| `net_worth = Σ市值 + Σrealized`（已实现为负） | +6 470.14 | 既有口径缺口，#3039 阶段 A 待修 |
| 5 行取价源不同（净值表最新 vs 窗口内最新/停牌锚点） | +2 242.41 | 两引擎取价口径差，量级可接受 |

镜像行 `ledger_id`/`portfolio_id`/`snapshot_quantity` 全 NULL、零流水、`quantity>0`：它没有
买入现金流，市值在现金流表里只能以「期末虚拟卖出」出现 ⇒ 42.5 万累计收益里有 21.5 万是
凭空来的。修法是 `calculate_portfolio_xirr` 接上 `position_scope.exclude_shadow`（该模块
docstring 早就点名了 XIRR 场景，只是这里没接线）；收益日历走 `_positions`（只取 active）
一直是对的——**同一个库里两种「什么是持仓」，两页才会打架**。裁决记 D128。

修后：当前市值 575 519.80 / 累计收益 210 322.35 / XIRR 19.95%，与资金流动的 566 749.51
只剩 8 770（= 6 470 + 2 242 + 58 舍入），残差全部可解释。

## 5. 是否与「持仓分析」合并（评估）

**结论：应当合并，但以「口径切换器」为前提，且不能一步到位。**

两页现在按**实现**划分，不是按**用户任务**划分：

| 页面 | 实际内容 | 划分依据 |
|---|---|---|
| 投资复盘 `/analysis` | XIRR / 净值曲线 / 清仓周期 | 时间维度（#2150 决策） |
| 持仓分析 `/asset/position-analysis` | 口径切换 + 区间超额 + 日历 + 归因 + 持仓结构 + 穿透 | 「把已实现的分析端点聚到一个入口」（作者原话） |

用户打开「分析」时问的是三类问题：**我现在怎么样 / 我过去经历了什么 / 我的做法对不对**。
现状把"现在"和"过去"拆到两页，而"对不对"（超额）只在一页、"赚了多少"（XIRR）只在另一页——
用户无法预测信息在哪，只能两页来回翻。这是 endpoint-driven IA 的典型症状。

更强的证据来自第 9 条本身：一旦结构图画进复盘页，两页就有**三块重复**（结构 / 穿透 / 归因）。
**当两页开始重复，说明划分维度选错了**——重复不是第 9 条的副作用，是边界的证伪。

反方（必须承认的代价）：

- 复盘页现有 4 区块、持仓分析 6 区块，合并后 9–10 块，一屏装不下 → 需要分区懒加载 +
  目录 rail（已有 `usePageNav`），否则首屏接口从 2 个涨到 10 个；
- 口径切换器目前只在持仓分析，合并后要成为**整页**主控（净值曲线也要支持"只看某账户"），
  这会改动 `useNetWorthTrend` 与 XIRR 的入参；
- 两条路由都有外部书签（`/analysis` 是明写的锚点）→ 合并必须保留旧路径做重定向，
  不能删 URL。

迁移路径（建议）：

1. ✅ 先把复盘页补齐到"能和持仓分析对话"（P1 + P2），期间两页重复是有意的过渡态；
2. ✅ 再以 `/analysis` 为主页，把持仓分析的块搬入并把口径切换器提到页头（§5.4）；
3. ✅ `/asset/position-analysis` 保留为重定向（口径 query 原样带走），侧边栏少一项。

**执行时的修正**：原计划写「搬四块」，实际只搬三块（区间表现 / 收益日历 / 收益归因）。
第四块「持仓结构 / 穿透」两页此前**各有一份同源同组件**——搬过去只会变成三份，
正解是删掉旧页那份、只留复盘页的。侧边栏是 4→3（概览下只剩投资概览 / 资产总览 /
投资复盘），不是 5→4。

不建议现在直接合并：合并的最大成本不在搬代码，而在「口径切换器要贯穿全页」和
「9 块内容的首屏取舍」，这两件事没有结论就动手，只会做出一个更长的页面。

### 5.1 P3 分期与落地记录（2026-11-28）

按「先做切换器、后搬内容」拆成四步，前两步必须先于主题搬迁：

| # | 内容 | 状态 |
|---|---|---|
| **A** | 口径契约层：`useAnalysisScope`（页级 state + URL 同步 + epoch）、`ScopeBar`、`toScopeProps`/`toScopeQuery` + 单测 | ✅ PR #3282 |
| **B0** | XIRR 补账户档（后端）——B 的前置阻塞 | ✅ 见下 |
| B | 复盘页接切换器（家庭 / 账户两档）、7 区块接 scope、降级条、拆 `NetWorthTrendSection` | ✅ 见 §5.2 |
| C | 搬内容：持仓分析 5 块迁入、分区 + 懒加载、旧路由重定向 | 待做 |

**B0 的由来（动手时才发现，不是计划内的）**：准备给「收益概览」接账户档时核对端点，
发现 `GET /api/performance/xirr/?scope=ledger&ledger_id=3` **返回 200 + 全家庭数据**。
`calculate_xirr_by_scope` 只分派 position / portfolio / symbol，其余落到末尾
`calculate_portfolio_xirr(family_id=...)`；包门面根本没接 `ledger_id`。

最隐蔽的是：**同端点的 `method=twr` 早就有账户档**（`calculate_twr_by_scope` 收
`ledger_id`，文档还明写「与 xirr 的 scope 语义对齐」）——换个 method 行为就变，
而默认 method 恰好是 xirr。一直没暴露是因为前端没有账户档入口：复盘页写死家庭级，
持仓分析页的档位只喂 `benchmark-excess`，不喂 xirr。

修法见决策 D129。两条判据值得记：

1. **归属校验不能靠 `restrict_visible` 兜底**——它对 `ledger_id IS NULL` 是**放行**的
   （无主行按家庭共有），传外家庭 id 不报错，而是返回「无主行 + 空集」的半截数据。
   必须查 `family_ledger_ids`，不属于则 `ValueError` → 404。
2. **可加性是最强的验收**：真库 Σ16 个账户市值 = 家庭市值 = 586,850.69，差 **0.00**。
   如果账户档还混着家庭数据，这个和不可能闭合。

后续 B 的 7 个区块里，XIRR 现在真的支持账户档了；仍有 4 个组合档空洞
（净值曲线、清仓复盘、浮亏回本、收益日历），按 D1 的取舍留到三期。

### 5.2 B 落地记录（2026-11-28）

**做了什么**：切换器进复盘页顶部、成为页级主控；7 个区块全部接 `:ledger-id`；
`NetWorthTrendSection` 拆出页面。

**档位是算出来的，不是写死的**。`analysisScopeSupport.ts` 登记「每个区块真的能算
哪几档」，页面可开 = 所有区块的交集。理由不是洁癖：多开一档的代价是**静默错数**
——不支持的块拿 `undefined` 当 props，面板侧把 `{}` 读成家庭级，于是「组合」标签下
摆着全家庭的钱（#2595 的原形态）。硬编码 `["family","ledger"]` 则会在某块补上组合档
之后过期，而没人会记得回来改。配套单测钉住「表内标签 == `NAV_LABELS`」和「7 个区块
都带 `:ledger-id`」，防「表里登记的」与「页面真渲染的」漂移。

**未选账户时一个区块都不渲染**，只给一句话。给面板传 `undefined` 就是家庭级，
那正是这张卡要消灭的形态——宁可让人对着一句话，也不要让人对着错数。

**两个只有真机走查才会暴露的问题**：

1. **骨架屏死锁**。`PageSkeleton` 用 `v-if="initialLoading"` 与内容 `v-else`
   互斥，而负责关骨架的是净值区块——它在骨架里面，永远挂不上。表现是首屏全空、
   `pageerror` 0、零 canvas，控制台一片干净（Vue 的包容性让人以为「加载慢」）。
   修法：骨架关闭等父页自己的 `loadLedgers()`，它是父页唯一自发的请求。
2. **切换条变成 3 行 105px**。`el-select` 默认宽度 100%（EP 2.4+ 的
   `--el-select-width`），在 flex 行里把整行吃掉，档位与说明被挤成上下两行。
   改 `flex: 0 0 auto; width: 200px`。这条是看截图才发现的，`computed` 链上加
   什么断言都拦不住。

**走查判据里最容易写错的一条**：「账户档数据 ≠ 家庭档数据」。中间踩过一次——
先 curl 后端确认正确（账户档 12 笔 / 107,450.78，家庭 1890 笔 / 586,850.69），
再打印请求 URL 确认 `scope=ledger&ledger_id=3` 真的发出去了，最后才发现 **vite
代理默认指向 8000 端口，那里跑的是旧后端**（对同一请求返回 1890 笔）。走查脚本
必须钉住「前端打到哪个后端」，否则会拿旧后端的行为去否定新前端。

吸附测试的同型误报两次：① `document.querySelector(".el-scrollbar__wrap")` 拿到的是
**侧栏**的滚动容器，滚它等于没滚；② 测试点落在「未选账户空态」上，页面极短，
`scrollTop = 1600` 被 clamp。改法：从切换条向上找真正的滚动容器，判据用
「元素 top == 滚动容器 top」（不是视口 0，顶栏占 ~81px），且测试必须在家庭档
内容完整时跑。

**当前结论**：家庭档 `20.70% / +¥221,653 / 市值 586,851`，账户「微众银行」
`0.00% / +¥64,451 / 市值 107,451`；rail 7 项顺序正确；深链
`?scope=ledger&scope_id=3` 正确恢复档位与「只看 微众银行」；`pageerror` 0。

### 5.5 C2 落地记录：分区懒加载（2026-11-28）

页面合并后 10 个区块全在首屏一起挂载：每块都在 `onMounted` 里自己取数，4 块还要建
echarts 实例。首屏实际只看得到前 3 块，后 7 块的请求和图表初始化却挤在同一帧发出
（后端单 worker，10 个并发排队）。C2 就是把这 7 块延后。

**真正难的不是懒加载，是锚点。** `usePageNav` 的导航项来自**扫 DOM 里真实存在的
`nav-` 锚点**（§见 `composables/usePageNav.ts` 文件头：「静态清单必然长出死链」）。
未挂载的区块没有锚点 ⇒ rail 少几项、scroll-spy 认不出、点进去原地不动。

两个错误解法先排掉：

| 解法 | 为什么不行 |
|---|---|
| 给 `usePageNav` 传静态锚点清单 | 清单与真实渲染脱钩必然长死链。本页「浮亏回本」「货币基金收益」是 `v-if` 数据驱动（无浮亏 / 无货基时整块不渲染），静态清单会把它们钉在导航里点不动 |
| `content-visibility: auto` + `contain-intrinsic-size` | 它只跳过**渲染**：组件照样挂载、`onMounted` 照样跑、请求照样发出。省的是绘制，不是首屏并发——而这里的瓶颈恰恰是后者 |

正解是**把两件事拆开**：锚点由「这块该不该有」决定，内容由「看不看得见」决定。
`components/LazySection` 因此是「`<section id>` 常驻 + 内容懒挂」，DOM 扫描仍然是
唯一真相源，`usePageNav` 一行没改。

四条实现约束：

1. **激活后不回收**——回收会让用户往回滚时内容消失、整页高度变化，滚动位置与
   scroll-spy 同时错乱，比一直挂着更糟；
2. **跳转前先激活**（`useLazyNav`）——否则点一个没滚到的区块，跳过去只有空白，
   内容随后长出来把页面顶下去。激活可以**同步**做、不必 `await nextTick()`：
   `goTo` 只把区块**顶边**送到定位线，而顶边只受上方内容影响，激活目标自身不改变
   它的顶边（`goTo` 内部逐帧重读 rect、`host.limit()` 每帧重算，会吸收页面变长）；
3. **占位高度必须按实测校准**——它是「下方锚点位置」的唯一依据。初版拍脑袋给的
   560/1200 与实际 1846/2465 差了 3 倍多，占位偏矮会让下方锚点整体上移；
4. **同一 id 只能出现一次**——外层 `LazySection` 挂了锚点，内层子组件若还写
   `id="nav-structure"`，`querySelectorAll` 扫到两次 ⇒ 导航里这一项出现两遍。
   `AnalysisStructureSection` 的写死 id 因此删掉（改注释说明为什么不在这）。

**实测**（1440×1000，走查 12 项全绿、`pageerror` 0）：

| | 首屏 | 滚到底 |
|---|---|---|
| `/api` 端点（去重） | **13** | 22 |
| rail 项数 | 10 | 10 |
| 未挂载占位 | 5 | 0 |

首屏被延后的 9 个端点就是那 5 块（资金流动 / 收益日历 / 清仓复盘 / 持仓结构的
3 个面板 / 收益归因）。点未挂载的「收益日历」：内容**立即**激活，落点距滚动容器顶
8px（即定位线 = 容器顶 + 胶囊高 + 8）；真实滚轮滚回顶部不回收、滚到底高亮落末项
「货币基金收益」。

**走查方法论上的一个坑**：验证「滚到底高亮落末项」时不能用
`evaluate(() => scroller.scrollTop = scroller.scrollHeight)`——那是程序化滚动，
不触发 wheel / touchstart / keydown，`usePageNav` 的 pin（点击意图）不会被解除，
高亮会一直钉在上一次点击的项上（实测停在「收益日历」，看着像 scroll-spy 坏了）。
必须用 `page.mouse.wheel`，这也才是用户的真实路径。

**已知边界**：占位高度取的是家庭档实测值（717 / 399 / 1846 / 2465 / 776）。账户档
数据少时占位偏高，挂载后页面变短——影响仅限「滚到该块之前」的滚动条长度与 rail
相对位置，滚过之后即收敛。真要消除得按档位给两套值，收益不抵复杂度。

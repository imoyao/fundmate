# MVP 上线阻碍分析 + Issues 治理收口（2026-08-18）

> 背景：用户两项诉求 ——（1）把 100+ open issues 按四象限 + 里程碑收口管理；（2）识别真正阻碍上线的任务，出最小可上线版本（探市页 + 温度计页可用、注册可用、能部署给自己用）。本文是第二项的分析结论，第一项执行结果见末尾「Issues 治理结果」。

## 一、MVP 必须可用的三条主链路

用户定义的 MVP 红线：**探市页可用、温度计页可用、注册功能可用**，并且要能从「本机 localhost」走到「部署上线自己先用」。据此拆出三条主链路 + 一条部署闸门。

### 1. 探市页（/explore，免登录沙盒）

追踪 issue：#808（设计基线）、#821（缺陷缺口）、#822（登录态/转化区）、#827（登录迁移桥）。

现状与阻碍（基于 #821 实证表格）：

- P0-1 免登录搜索 401 —— **代码已修复**。后端 `app/core/auth.py` 的 `PUBLIC_PREFIXES` 已补 `/api/securities/search`、`/api/funds/search`、`/api/utils/config`（修复 #821 P0-1，含中文注释说明）。生产 `AUTH_ENABLED=true` 下匿名访客现在能搜到标的。该 issue 仍 open 仅作跟踪，根因已解决。
- P0-2 热门资产硬编码假成本价（`hotAssets` 写死 `costPrice: 4.567/...`、`quantity:100`）—— **未修**。新用户点一下即看到编造收益，第一印象即虚假数据，须改为取当前价、份额默认 1。
- P0-3 登录后本地持仓被清空且不回读 —— **未修**。迁移完清 localStorage 后，探市页只从本地读，已登录用户刷新即空。
- P0-4 迁移丢弃成本价/份额 —— **未修**。迁移只写代码/名称，`costPrice`/`quantity` 未落库，盈亏归零。
- #822 登录态感知 + 底部转化区（注册 CTA、损失厌恶文案）—— **未做**。探市页无「立即注册」入口，商业转化目的未落地。
- #827 登录迁移桥（B1-B4 双端丢失）—— **未做**。

**结论**：探市页「能打开、能搜、能加观察」已具备（P0-1 已修），但要达到「零门槛添加 + 注册转化 + 迁移不丢数据」的可用标准，还差 P0-2/3/4 + #822 + #827，合计约 2-3 天。

### 2. 温度计页（/temperature，免登录）

追踪 issue：#966（公募持仓集中度）、#967（用户持仓拥挤度）。

现状：温度计本身是免登录白名单项（`/api/temperature` 在 `PUBLIC_PREFIXES`），页面与数据链路是通的，**页面可用**。#966/#967 属于「增强指标」（集中度/拥挤度），不是「页面打不开」类阻碍，归类为 Q1 偏高，可下沉到 Q2/Q3 作为上线后增强。

**结论**：温度计页 MVP 达标，无需阻塞上线；#966/#967 建议移到 Q2 增强队列，待 smoke test 确认数据展示正常即可。

### 3. 注册功能（Supabase Auth）

追踪 issue：#922（用户凭证加密存储 + 通用 MCP/Skill 调用 + 审计日志）。

现状：注册/登录走 Supabase Auth（前端 `@supabase/supabase-js`，后端 JWT 白名单中间件验签），注册链路本身是平台能力，**功能可用**。#922 是「凭证安全存储与调用规范化」，属安全增强而非注册阻断。

**结论**：注册 MVP 达标（依赖 Supabase 生产 project 实例已创建、region 选新加坡/东京、GitHub OAuth 登录应用已配好、env 仅填既定值，非选型决策）。#922 作为安全增强，上线后跟进。

### 4. 部署闸门（决定能否「上线给自己用」）

核心 issue：**#894 上线计划（M0 上线阻塞清单，约 4.5d + 观察期）**。这是 MVP 真正的时间瓶颈，与功能是否写好解耦。M0 任务：

| # | 任务 | 工时 |
|---|---|---|
| 1 | 后端生产 WSGI（加 `waitress`/gunicorn，`pdm run serve --prod` 入口） | 0.5d |
| 2 | 重写 V2 `backend/Dockerfile`（替换 V1 遗留 fundmate/webpack/supervisord） | 0.5d |
| 3 | 生产 env 清单 `.env.production.example` + Supabase 生产项目配置核对 | 0.5d |
| 4 | 前端 `VITE_PUBLIC_PATH=/app` 生产构建 + nginx 静态托管（同机或 Vercel） | 0.5d |
| 5 | 云主机初始化（域名/DNS/HTTPS/nginx 反代 /api → :8000） | 1d |
| 6 | 每日定时抓取 cron（`sync --all` + 温度计 + 净值增量） | 0.5d |
| 7 | 上线冒烟验证（登录/记账/探市/温度计/自选 + health + 错误信封） | 0.5d |
| 7a | 货币基金每日收益链路验证（万份收益落库 + 展示入口对账） | 0.5d |
| 8 | M0 验收（连续 2-3 天抓取稳定、无生产级严重 bug） | 观察期 |

相关：#918（应用站落地页构建链退役 + 导入页平台 logo 卡片 + 三平台部署配置，脚手架文件已存在）、#909（交易人格测试 H5 落地，属营销验证，非核心 MVP）。

**结论**：部署闸门是上线唯一硬性阻塞。选型早已在 `backend-hosting-fetch-selection-2026-08-03.md` / `db-cost-decision-2026-08-04.md` 定死（前端 EdgeOne Pages、后端腾讯云 SCF Web 函数跑 APIFlask + SCF 定时触发器、用户域 Supabase、市场域 Turso），非待拍板项。**云主机选型**一项已不成立——后端就是 SCF 函数，没有传统"云主机"采购问题；仅剩 nginx 反代/域名/HTTPS 这类接入配置（详见 #894 M0 第 5 项）。**备份一期**也已定：Supabase 免费档无自动备份，用 Neon 免费档（0.5GB/项目，容量与 Supabase 500MB 上限匹配）作外部 `pg_dump` 备份目标，由 SCF 定时触发器或 GitHub Actions（仅备份不碰东财）每日全量、保留 7 天滚动。

## 二、最小可上线版本建议范围

把上述拆成「上线前必须」与「上线后增强」两档：

**必须（MVP 上线门禁）**
- 探市：P0-2/3/4 修复 + #822 转化区 + #827 迁移桥（保证「能加、不丢、能转化注册」）。
- 温度计：smoke test 确认数据展示正常（无需新开发）。
- 注册：Supabase 生产 env 配置正确（无需新开发）。
- 部署：#894 M0 九项全跑通（后端生产服务器 + Dockerfile + env + 前端构建 + 云主机 + cron + 冒烟）。

**上线后增强（不阻塞）**
- #966/#967 温度计集中度/拥挤度 → 下沉 Q2。
- #922 凭证加密存储 → M1 安全。
- #909 H5 落地、Turso 双备份（#894 M2）、Sentry（#894 M1）等。

## 三、需用户确认的事项（非选型，均已有既定决策）

1. Supabase 生产 project 实例是否已创建并配置就绪：需确认（a）已在 Supabase 上创建了一个具体 project（非"要不要选 Supabase"——Supabase 早已选定），（b）region 选为新加坡/东京，（c）GitHub OAuth 登录应用已配好并拿到正确的 env 值。注册/登录的生产 env 依赖它，属事实确认而非选型拍板。

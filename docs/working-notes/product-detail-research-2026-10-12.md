## 2. 议题一：数据分层（持仓本地 vs 非持仓第三方）

### 2.1 结论

**「持有的存本地、没持有的走第三方」方向正确**，但第三方走后端代理 + 冷热分层缓存，前端不直连。

### 2.2 为什么本地全量落库是浪费

成本随「被看过标的数 × 历史深度」缩放。当前 3,419 只有净值的基金里，持仓+自选不到 10%——**90% 是无人持有的长尾，却在天天全量同步、全历史驻留**。全量铺开（26,938 只）外推 4~7 GB，只增不减。

### 2.3 「一次抓取多用户共享」会不会爆炸——两种情况

- **缓存永久驻留全历史 → 会**，成本结构与本地全量等价（只增不减，上限 = 全市场 × 全历史）。这种担心成立。
- **TTL 淘汰 + 冷热分层 → 不会**。关键性质：**日频历史点不可变**（去年某日净值永不变），到期删光是纯浪费（下次回访重拉）。正解：
  - 冷层：只留**月末点**永驻（12 点/年 vs 244 点/年，压缩 20 倍）。26,938 只全驻 ≈ 60 MB 封顶。画 5 年/成立来曲线只需 60 个月末点，800px 图表 ≈ 400 列，分辨率无损。
  - 热层：近一年日频，TTL 30 天淘汰，≈300 MB 封顶。
  - singleflight 合并并发 + 增量回源（只拉缓存没有的日期段）→ 回源次数与用户量解耦（直连方案是每用户每次线性：1 万用户 ≈ 20 万次/月；代理去重后 ≈ 5 千次/月封顶，数字为估算假设）。

### 2.4 为什么不前端直连（诚实版）

不是为省服务器成本（直连确实是 0，且 pingzhongdata 是静态 CDN 文件、扛得住量级，「限流爆炸」不成立）。真实理由三条：

1. **契约稳定性**：第三方接口形状暴露在前端，对方改字段/加校验，详情页当天白屏；后端代理是唯一封装点，可一键关停 + 静默降级（设计 §9.1 红线）
2. **共享红利**：回源与用户量解耦只有服务端做得到
3. **口径可控**：数据日期、来源脚注、缺数降级规则统一在后端

### 2.5 落地顺序（建议）

1. `fund_nav_job.py:37` 首取 30 天 → 改为按该基金最早交易日起取（交易流水取 `min(trade_date)`）
2. 本地持久范围收缩到持仓 + 自选
3. 非持仓长区间曲线走后端代理 + 冷热分层（含 §9.1 开关与降级）；`api/products.ts:309` 注释同步修订
4. 数字继续本地：`fund_performance` 区间收益基于本地 acc_nav 现算、历史不足降级「—」，这层不动；只有长区间**曲线**走代理
5. 建仓期区间（= 首笔买入日至今）本地实现——账本独有差异化，第三方没有这个区间

## 3. 议题二：持仓明细 50~100 行的优化

### 3.1 现状与问题

`ProductHoldingSection.vue`（#2029 卡 C）一张表渲染全部 rows。实测库内 avg 63.6 行、max 100 行——**50~100 行的表对一个页面是实打实的负担**：把走势、业绩等核心内容冲出首屏，且季报口径（`basis=top10` vs `full`）混排风险已被 `basis_label` 硬口径兜住，但表长没有兜底。

### 3.2 成熟产品做法（调研归纳）

- **天天基金**：走势大图在顶部；持仓在「基金档案」tab 下，重仓只展示前十大 + 季度切换；资产配置/行业配置用饼图不用表
- **支付宝财富**：业绩/持仓/档案分 tab；持仓页 = 重仓 top10 + 行业配置 + 「查看历史持仓」
- **雪球**：重仓 50 家用虚拟列表
- **Fidelity / Morningstar**：Top 10 + "View All" 分页表
- **共同模式**：① 首屏给聚合不给明细；② Top N + 渐进披露（展开全部/抽屉/分页）；③ 汇总行置顶（先看到「前十合计 45.2%」再逐行）；④ 维度切换着重看，不堆全量表

### 3.3 建议形态（按优先级）

1. **top10 紧凑表 + 卡内「展开全部 N 只」就地展开**（默认收起到 10 行，展开后表内滚动或自然伸长）。保留 `basis_label` 口径提示与 `shown_total_ratio` 合计行
2. 备选：top10 + 「查看全部」开 el-drawer 全表（页内不伸长，适合明确不想看长表的用户）
3. 维度切换 pill（重仓/全部）可做——无 role 手写胶囊是守卫合法形态，不撞 guard_segmented
4. 不建议：默认渲染全表 + 内部 max-height 滚动（把负担从「页面长」变成「表内滚」，手感更差）

## 4. 议题三：第三方兜底入口的位置

**结论：不做常驻区块，降级为走势卡内联入口。**

用户原话痛点「现在放到最下面，用户基本不会去点击」——问题不在位置在形态：只要它是常驻区块，放哪都有人看不见。且「基金资料」不适合收纳它：资料区块是静态档案（类型/经理/规模/费率），混入条件取数逻辑会破坏「懒加载、失败仅降级本区块」的边界，两者语义与触发时机都不同（资料无条件渲染；兜底只在本地无该区间数据时才有意义）。

正解：走势卡内部，本地数据只到 X 时，**卡内联一行「本地净值仅到 2019 年，查看成立以来完整走势 →」**，点击才按需拉第三方（懒触发、非常驻）。它出现在用户视线焦点内，且只在需要时出现。`ProductExternalLinksSection`（资金流/盘口等深度研究外链）保持底部，可后续再议是否与资料区块的「深度研究」行合并。

## 5. 议题四：导航形态（sidebar vs 顶栏 + 页内导航）

### 5.1 全局 sidebar 换顶部？——不换，三个理由

1. **装不下**：实测 sidebar 一级 5 项，但资产管理下二级 15+（股票/基金/贵金属/房产 + 智能分析/对账导入/手动记账/E账户对账等 7 个工具页）。顶部 nav 的可扩展上限就是 5~7 项（外部调研一致结论），二级只能上 mega menu，而 mega menu 在 1400px 内容区 + 85px 顶栏的既有格局下是净增复杂度
2. **顶部已经两层**：LayNavbar + LayTag 已占 85px（`--layout-topbar-height`），再加一层全局导航 = 三层头，垂直空间灾难。纯 admin 模板的 horizontal 布局整套断点/样式/交互都要重走查，且与 #1714「收敛双层头部」的既定方向相反
3. **趋势相反**：Vercel 2026-02 把 horizontal tabs 换成可隐藏 resizable sidebar；Linear 2026 继续保留 sidebar（更暗更紧凑）。行业在「顶部 tab → sidebar」，不在反向

外部调研判据（2026-10-12 检索）：sidebar 适合 6+ sections、频繁切换、持久方位感；top nav 适合 <6 sections 且每区是完整上下文；**页内 contextual navigation（tab bar / sub-nav inside content area）是标准做法**，不与全局导航抢位置。

### 5.2 详情页双栏（左 sticky 锚点栏）与全局 sidebar 打架吗？——打，不采用

- 视觉双左栏：NavVertical（240px/折叠 64px）+ 内容区内再一条 120~150px 竖栏，左边缘两条栏并列，认知负担重
- **宽度抖动**：sidebar 折叠/展开（`layout/index.vue:233-247` 断点自动切）时内容区宽度跳变，双栏布局跟着抖，sticky 栏与卡片断点全部要按「最窄内容区」设计
- Agent 页已有此先例（session-history 左栏 + 全局 sidebar 双左栏，#1719 默认折叠缓解），不值得在详情页复制

### 5.3 建议：页内导航响应式两级

| 断点 | 形态 | 依据 |
|---|---|---|
| < xl（<1280） | **内容区顶部锚点胶囊**（sticky 在页头下）：走势/持仓/业绩/明细/资料，点击平滑滚动 + scroll-spy 高亮 | design.md 已登记「水平滑动胶囊栏」合法形态（`.road-pills--scroll`，834 行）；移动端天然兼容（横向可滑）；不新增左栏 |
| ≥ xl（1280+） | **右侧目录 rail**（sticky，宽 ~180px）：「本页目录」式锚点列表 | 文档站通行形态；内容限宽时右侧本就空余，补空而非抢宽；不与左 sidebar 冲突 |

核心内容不全折叠（持仓明细是核心信息，可折叠的只有经理/关联/外链）；不做互斥 tab（guard_segmented 拦 `role="tablist"`，设计 §10 反 13-tab 研究形态，互斥视图与区块懒加载架构冲突）。

### 5.4 Agent 页双左栏问题（登记，未开工）

`views/agent/index.vue` 的 SessionHistory（左 260px sticky）与全局 sidebar 并存。已有缓解：默认折叠。后续如重构，候选方向：历史入口改顶部「历史」按钮 + popover/抽屉，或右栏。属独立议题，不在详情页卡内做。

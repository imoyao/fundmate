# 前端架构与移动端评估（未来考虑）（2026-08-04）

> 性质：内部备忘（`docs/working-notes/` 屏蔽出构建，不对外）。
> 评估日期：2026-08-04
> 性质：**未来考虑（非当前阻塞项）**。当前 Web 后台架构维持不变，后端部署优先推进（见 [deployment-implementation-guide-2026-08-04](./deployment-implementation-guide-2026-08-04.md)）。
> 背景：当前前端 Vue3 ＋ Vite ＋ TS ＋ Pinia ＋ ECharts，UI 基于 pure-admin-thin（Element Plus）。本轮讨论两点：(1) AI 编程（Cursor/Windsurf）场景下 Element Plus 的劣势；(2) 若要做移动端，技术选型。

## 一、当前前端架构评估

### 1.1 现状

- 技术栈：Vue3 ＋ Vite ＋ TypeScript ＋ Pinia ＋ ECharts，UI 用 Element Plus（pure-admin-thin 体系）。
- 产品形态：数据密集的**后台 / 看板**——表格（持仓、交易）、表单（添加交易）、图表（乖离度、净值）、增删改查。

### 1.2 AI 编程时代 Element Plus 劣势讨论（客观存在，但对本项目程度低）

业界对 Element Plus 在 AI 编程下的 5 个劣势维度：

1. 样式修改的 AI 幻觉（最致命）：Element Plus 依赖 SCSS 变量与 `:deep()`，AI 易生成不生效的覆盖代码。
2. 黑盒组件：源码在 node_modules，AI 只能"猜"内部 API。
3. 模板语法干扰：v-if/v-for 优先级、Vue2/3 写法混淆。
4. 设计语言僵化：视觉风格固定，难做轻量/现代风。
5. 组件粒度粗：改表头/单元格需大量插槽。

**但严重度取决于项目类型。** 对"标准企业后台 CRUD"，业界自评劣势约 **3/10**；对"重定制 C 端 / 快速迭代"，达 **8/10**。多倍贝属于前者——它的 UI 以标准表格 / 表单 / 图表为主，定制少、视觉不需要高度个性。因此本项目真实痛感约 **3–4/10**，不构成切换理由。

### 1.3 结论

当前架构对 Web 后台用途**合理，不推翻**。真正驱动前端架构变更的只有两个**未来因素**：

- (a) 重度依赖 AI 做 UI 精修（样式覆盖摩擦才会显著）；
- (b) 移动端需求（Element Plus 是桌面端库，天生不覆盖手机）。

两者均为"将来时"，非当前阻塞。

## 二、移动端方案对比（如未来要做）

### 选项 A：Vant（Vue 3 移动端 UI 库）

- 保持 Vue 技术栈：桌面 Element Plus ＋ 手机 Vant，技能完全复用。
- 代价：维护两套 UI（桌面 / 移动），需做响应式或独立移动页。
- 适合：移动端是"补充"，桌面仍是主场景。

### 选项 B：uni-app（Vue 语法，一套代码多端）

- 一套 Vue 代码编译到 Web ＋ 微信小程序 ＋ App（H5/原生）。
- 代价：现有 pure-admin 工程需往 uni-app 体系迁移（有一定改造量）。
- 适合：移动端 ＋ 小程序 ＋ App 都是硬需求，希望一份代码多出端（中文圈 solo 开发者常见诉求）。

### 选项 C：React Native / Expo（若转 React）

- 真正的原生 App ＋ Web 共用（React Native Web / Expo）。
- 代价：整段重写，与现有 Vue 积累割裂；换来的是 AI 编程体验最佳（JSX 纯 JS）。
- 适合：移动端是产品核心，且愿意换栈。

### 对比表

| 方案 | 技术栈变动 | 多端能力 | 改造成本 | 适合场景 |
|---|---|---|---|---|
| **Vant** | 最小（加移动 UI 库） | 仅移动 Web | 低 | 移动是补充，桌面为主 |
| **uni-app** | 中（迁体系） | Web ＋ 小程序 ＋ App | 中 | 多端都要，一份代码 |
| **RN / Expo** | 大（换 React） | 原生 App ＋ Web | 高 | 移动为核心，愿换栈 |

## 三、决策依赖（关键问题）

> **移动端是不是近期硬需求？要多端（小程序 / App）吗？**

- **否 / 未知** → 维持现状，未来要移动端时加 **Vant**（成本最小）。
- **是 ＋ 要多端** → 评估 **uni-app**（一份代码多端，比"桌面 Element Plus ＋ 手机 Vant"两套维护更省）。
- **是 ＋ 愿换栈** → 评估 **React Native / Expo**（AI 体验最佳，但重写成本最高）。

当前**不决策**，列为未来考虑。

## 四、建议

1. **当前不动前端**，优先推进后端部署（见 [deployment-implementation-guide-2026-08-04](./deployment-implementation-guide-2026-08-04.md)）——那才是本轮真正的硬骨头。
2. 移动端需求明确前，不投入任何前端重构。
3. 若未来要做且要多端：优先 **uni-app**（Vue 延续，一份代码）；若仅补移动 Web：用 **Vant**。
4. 仅当"AI 写 UI 反复与你打架"且"追求高度定制视觉"时，才考虑 **Vue ＋ Tailwind ＋ shadcn-vue**（AI 时代 Vue 解法）或转 React 三件套。对多倍贝这种看板，此优先级最低。

## 五、边界

- **事实**：Element Plus 为桌面端组件库；Vant 为 Vue 移动端 UI 库；uni-app 用 Vue 语法编译多端；以上为业界通行事实。AI 编程下 Element Plus 的样式/黑盒/模板劣势客观存在（社区共识）。
- **推断**：多倍贝属 admin / 看板类，Element Plus 痛感约 3–4/10，远低於重定制 C 端；后端部署才是当前高价值工作。
- **未知**：用户是否真要做移动端、多端范围（是否含小程序 / App）、AI UI 精修的实际频率——均待用户定，故本报告仅作未来参考，不进入当前执行计划。

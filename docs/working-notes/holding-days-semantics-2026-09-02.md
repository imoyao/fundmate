# 持仓「持有时长」计算口径决策（2026-09-02）

> 关联：issue #862（基金/持仓详情展示收益率·持仓成本·持有时长）、PR #1284
> 背景：用户就「同一标的反复买卖时，持有天数从首买还是最新一轮算」提出质疑，并贴了两段通用 AI 建议（FIFO 批次表方案）。本文基于 **fundmate 现有代码** 核实口径并固化决策，避免后续被「过度工程」带偏。

## 一、一句话结论

当前实现**已经正确**：持仓详情页的「持有时长」按 `positions.confirm_date`（本轮建仓日）到今天计日；清仓后重新买入会自动从最新一轮算起，**不会**从最早一次买入日累加。且 `holding_days` 是实时派生属性、**不落库、无需每日刷新**，与「只存起始日、派生字段自动算」的主张完全一致。

**决策：不引入 FIFO 批次表（holding_batches / lots）。** 现有「清仓即删行 + 重买即建新行 + 单一 confirm_date」已等价实现「本轮连续持仓」语义，且更契合本系统的加权平均成本模型。

## 二、代码事实依据（authoritative）

| 行为 | 代码位置 | 说明 |
|---|---|---|
| 清仓删除整行 | `position_service.py:761-766`（`process_sell_or_withdraw`） | 份额减至 0 时 `db.delete(existing)`，连同 `confirm_date` 一起消失 |
| 重买新建行 | `position_service.py:589-652`（`process_buy_or_deposit`） | 历史持仓已删，走新建分支，`confirm_date` = 本次买入日或 `date.today()` |
| 加仓不改建仓日 | `position_service.py:557-588`（合并分支） | 对**仍持仓**的同一标的追加买入时，只更新 `quantity`/`avg_price`/`import_hash`，**不碰 `confirm_date`** → 沿用首建仓日 |

| 流水重建一致 | `position_service.py:818-900`（`recompute_position_from_transactions`） | 删除/编辑首笔买入后按剩余流水重建，`confirm_date = 最早一笔流水的 confirm_date`，与「本轮起点」口径一致 |

## 三、当前口径精确定义

- **持有时长 = 今天 − 当前开放持仓(Open Position)的 `confirm_date`**。
- **Open Position（开放持仓）**：自「上一次从 0 到 >0 建仓」起，一直到「清仓归零」为止的连续持仓期。期间部分卖出、加仓都**不重置** `confirm_date`（因为本系统用移动加权平均成本，单一持仓即一个连续批次，而非多批次 FIFO）。
- **清仓即断裂**：份额归零 → 持仓行删除 → 下次买入是全新 Open Position，`confirm_date` 重设为买入日。故反复买卖场景下展示的是「最新一轮」的天数，符合行业「连续持股」统计惯例（税务/损益分析视角）。

### 用户场景推演（21买→22清→23买→24清→25买→26清→26再买）
每轮清仓删除持仓行，26 再买新建行 `confirm_date=2026` → 当前持有时长 = 今天 − 2026 买入日。**不会**累加成「从 2021 算起」。

## 四、与粘贴的 FIFO 批次方案对比（为何不采纳）

粘贴建议主张「维护 holding_batches 批次表 + 清仓归档 + 持有天数从批次买入日算」。该方案适用于**券商级逐笔 FIFO 成本计税**系统，对本家庭记账 App **过度工程**：

1. 本系统成本模型是**移动加权平均**（`avg_price` 加权、卖出不改均价、#1183 已实现盈亏按均价结转），天然是「单一开放持仓」语义，与 FIFO 多批次正交。引入批次表需同时改造成本/盈亏计算，收益不匹配复杂度。
2. 「本轮连续持仓天数」已由 `delete-on-clear + new-row-on-rebuy` 免费获得，无需额外表。
3. 历史全量交易流水**已永久留存**于 `transactions` 表（只插入不删改），想查「21 年那笔持有了多久」可直接按 `position_id`/symbol 聚合流水计算，**不丢历史**。展示层用「历史交易记录」承载，与「当前持仓页」分离——这正是粘贴建议里「不可变流水 + 当前视图」的正确内核，我们已具备，只是不靠 batches 表实现。

## 五、已知边界与待定项（不阻塞，记录备查）

1. **E 账户快照导入会覆写 confirm_date**：`upsert_from_holding`（`position_service.py:405`）对**已存在**持仓执行 SET 语义时 `confirm_date = snapshot_date`，即每次导入快照都会把建仓日重置为导入日。这是快照导入的固有特性（券商文件通常不携带真实首买日）。影响：导入类持仓的「持有时长」度量的是「距最近一次快照导入」，而非真实首买日。
   - 决策：**维持现状**（快照口径可接受），但若后续要精确，应在 `PositionImportMeta` 区分「快照日」与「建仓日」，导入不覆盖用户/首笔流水推导出的建仓日。列入 tech-debt，不本次处理。
2. **部分卖出后加仓的口径**：当前按「连续开放持仓」从首建仓日计（非 FIFO 分批次计）。这对家庭记账是合理的简化；若未来要做「按批次分别展示持有时长」，再评估是否引入轻量批次，不在本期。
3. **时区**：`holding_days` 用服务器本地 `date.today()`，未做用户时区修正；家庭记账场景误差 0~1 天，可接受。

## 六、给前端的契约

- 持仓列表/抽屉展示 `holding_days` 时，语义即「本轮连续持仓天数」，文案建议明确为「持有时长（本轮）」或在 tooltip 说明「清仓后重新计起」，避免用户误以为是总持有时长。
- `holding_days` 可能为 `None`（无 `confirm_date`，如纯导入未带日期的持仓），前端需兼容空值展示「—」。

## 七、决策摘要（Decision）

- ✅ 维持现有 `confirm_date` + `holding_days` 派生属性方案，不新增批次表。
- ✅ 反复买卖 = 清仓断点 + 重买重置，自动符合「本轮」口径。
- 📌 仅记录原子事实（建仓日），派生字段全实时算——与 AGENTS.md 金额/精度「换算走 Money、业务不存冗余派生」原则一致。
- 🔖 tech-debt：E 账户导入覆写 confirm_date 的精确化（区分快照日/建仓日）。

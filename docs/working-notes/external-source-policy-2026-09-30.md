## 结论先行

| 你的诉求 | 判断 |
|---|---|
| 高价值数据可以直接取用 | ✅ **可行，且已有先例**——`services/thermometer/fundfof_crowding.py` 已在跑，规范也是现成的 |
| 要礼貌、不要搞崩人家 | ✅ **同意，且这是硬要求**。真实风险不是「搞崩对方」，是「对方限流/封 IP + 法律风险」 |
| 不要暴露在 akshare 或 PR 里 | ⚠️ **一半可行，一半做不到**——见下，这条得改口径 |

**必须先纠正一个事实**：`imoyao/fundmate` 是 **public 仓库**（`gh api` 实测 `private=false`）。
所以「代码里能看到」= **全世界都能看到**。把来源藏进代码、只从 PR 描述里拿掉，等价于**公开**。

而且这件事**已经发生了**：`fundfof_crowding.py` 的模块 docstring 里，`www.fundfof.com`、
接口路径 `/api/market/crowding/latest`、参数名、字段映射、连「**未授权**使用」四个字都写在里面。

所以正确的边界不是「藏起来」，而是**分层**：

| 层 | 该怎么做 | 理由 |
|---|---|---|
| **代码 / 内部文档** | **明写来源 + 明写风险**（沿用现有 docstring 体例） | 藏来源会让后来者无法评估风险、无法在对外发布前替换掉它——这是**技术债的定时炸弹** |
| **对外产品文案 / 宣传 / 用户可见处** | **不提**（不说「数据来自 XX」） | ✅ **这才是该控制的地方**，也是唯一有实际意义的地方 |
| **对外发布 / 商业化前** | **必须换成自有或授权源** | 现有规范已定；未授权源的对外形态本身站不住 |

一句话：**对内诚实，对外克制。** 把「不要暴露」落在「不对外宣称」，而不是「代码里假装不是它」。

## 现有先例（这就是项目自己的规范，照抄即可）

`backend/app/services/thermometer/fundfof_crowding.py` 头部原文：

> **合规与风险（诚实交代）**：
> · 该接口为其自家后端服务，**未授权**使用；对方随时可能加签名 / 限流 / 改结构 / 封 IP；
> · 因此本模块只做「低频 + 磁盘缓存 + 失败静默降级」，绝不重试轰炸，也绝不绕过任何鉴权；
> · 仅用于个人自用验证，**不应对外发布**；对外形态必须换成自有或授权数据源。

它的工程手法也是现成的，直接复用：

| 手法 | 现有实现 |
|---|---|
| 一键关停 | env `FUNDFOF_CROWDING_ENABLED`（默认开，置 `0/false/no/off` 关） |
| 磁盘缓存 | `CACHE_TTL_HOURS = 6` + `resolve_cache_subdir('fundfof_crowding')` |
| 失败不轰炸 | 请求失败 → 回落到**任意年龄**的旧缓存（`_read_cache_any_age`），拿不到才返回空 |
| 不绕鉴权 | 只调匿名 GET；要登录的一律不碰 |
| 隔离 | 独立模块，**不混进 `akshare_adapter.py`** |

## 「礼貌」的可执行参数（建议，比现有实现更严）

你担心的是「搞崩人家」。**不会搞崩**——`GET` 接口、无写操作、单 IP 低频。
真正会发生的是：对方**限流**、**封 IP**、或**改接口结构**。所以约束的目的是「不被封 + 被发现也不难看」。

| 项 | 建议值 | 说明 |
|---|---|---|
| 并发 | **1**（串行） | 绝不并发，绝不分布式 |
| 请求间隔 | **≥ 3–5s**（比东财更宽） | 复用 `app.core.jitter` 的抖动思路，别用固定节奏（固定间隔本身就是爬虫指纹） |
| 单次运行总量 | **设硬上限**（如 ≤ 300 请求/次） | 与 `MAX_TARGETS` 同理，防「一次跑成数小时请求风暴」 |
| 缓存 | **长 TTL**（≥ 24h，历史数据永久） | 落盘后**永不重复请求同一标的**——这既是礼仪也是省事 |
| 失败 | **立即放弃，不重试** | 与东财的 3 次退避重试**相反**；对未授权源不做重试 |
| 时段 | 避开对方高峰，选**凌晨** | 顺手也避开自己的同步任务窗口 |
| 标识 | 带可识别的 UA | **不建议伪装浏览器**——伪装是「看起来像攻击」，如实标识反而更礼貌 |
| 鉴权 | **绝不绕过** | 需登录/付费墙的一律不碰（这是红线，不是礼貌问题） |

**关于 robots.txt 与 ToS**：抓取前应实际读一次对方 `robots.txt`，并留意其服务条款是否禁止自动抓取。
`fundfof_crowding.py` 当前**没有**做这一步，是个可补的缺口（若你确认要扩大抓取范围，我建议先补）。

## 法律风险的诚实评估（不做法律意见，只标风险）

这不在技术范畴，但必须说，因为「高价值数据」意味着它可能是对方的**核心资产**：

- 抓取他人网站数据用于**自用、不公开、不竞争**：实践中的风险**较低**，与现有模块的定位一致。
- 一旦**商业化 / 公开发布 / 用于竞争性产品**：中国法下有明确的司法先例路径
  （著作权法的数据库权利、反不正当竞争法第二条「诚实信用与商业道德」）。
  既有规范里那句「**不应对外发布**」不是免责话术，是**真实的必修项**。
- **不要做的事**：绕过登录/付费墙、伪造身份、突破限流、转售数据。这些会把「灰色」变成「黑色」。

> 若要对外发行，**先找法务**确认，不要靠工程判断兜底。

## 实现方式建议：主仓模块 vs 仓外脚本

你说「梳理太复杂或工程量太大」——那更不该塞进主仓：

| 方案 | 适用 | 评价 |
|---|---|---|
| **A. 主仓独立模块**（照抄 `fundfof_crowding.py`） | 数据是**常规周期同步**（如每天/每周固定更新），需要进调度 | 适合「已稳定的日常源」 |
| **B. 仓外一次性脚本 → 产出落盘** | 数据是**一次性/低频的历史补全**（如「把全部历史持仓捞一遍」） | ✅ **推荐**。代码不进仓库、不占 CI、不影响发布形态；产出物（JSON/CSV）按「参考数据」入库或作为 fixture |

**B 的落法**（我建议这种）：

```
仓外（如 D:/tmp/fundfof_harvest/ 或 ~/.workbuddy/skills/ 下）
  harvest_xxx.py          ← 采集脚本，带限速/缓存/断点续传，不进 git
      ↓ 产出
  xxx_20260930.json       ← 落盘数据
      ↓ 消费
主仓：只读该 JSON 落库（消费代码不认识来源，也就无从"暴露"）
```

这样**主仓里连抓取逻辑都不存在**，比「藏在代码里」干净得多，也顺手解决了「不混进 akshare_adapter」的诉求。

大概率比引入一个新外部源更划算、也更干净。

### 2. 是「一次性补历史」还是「持续更新」？

## 我不建议做的事（反向压力测试）

1. **把它包装成「自研数据」对外** —— 既站不住（对方随时可验证），也违背这个项目「不推销、诚实」的定位。
2. **为了藏来源而混淆代码**（如把域名拼接、base64 编码）—— 这是**加重**情节的做法，只会让风险更大。
3. **并发 + 无缓存地全量抓** —— 与现有规范直接冲突，也是唯一真会被封的做法。
4. **抓需登录的数据** —— 红线。

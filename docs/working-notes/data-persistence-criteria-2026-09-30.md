# 外部数据「落库 vs 现调」准入判据（2026-09-30）

> 背景：用户提出——「有些数据要不要存到数据库？还是直接调天天基金/开源 JSONP？
> 主要考虑后期数据分析能不能用上；能用上就抓，纯粹展示就没必要落库。」
>
> 结论先行：**判据不是「分析 vs 展示」，而是三个更可操作的问题。**
> 用「分析用不用得上」判，会得出「行业配置也能现调」的错误结论——真正的原因是聚合成本。

---

## 一、判据：三个问题，任一为「是」即落库

| # | 判据 | 为什么它才是真判据 | 反例 |
|---|---|---|---|
| **1** | **是否需要跨标的聚合？** | 单标的展示只需 1 次请求；跨标的聚合的成本是**组合数**，不是标的数 | 133 只基金穿透现调 = 133 请求 × 2s ≈ **4.4 分钟**，用户不能等；落库后 1 条 SQL。重叠度更狠：C(133,2) = **8,778 对** |
| **2** | **是否需要跨期累积？** | 外部接口只给「当期 / 当年」，**历史不会被动补给你** | 「风格漂移」「换仓」「行业迁徙」需要多期序列。**今天不抓，两年后就没有基线——这是不可逆的。** 而纯展示数据随时能补 |
| **3** | **外部接口是否稳定可得？** | 接口退化会让落库变成「最后一次拿到完整数据的机会」 | ① 需登录的 Token 会过期（雪球 `xq_id_token`，2026-08-30 到期且无刷新接口）；② 硬截断（`topline ≤ 100`）；③ 封装层会崩（akshare 行业配置对 QDII 直接抛异常） |

### 反判据（不落库）

- **结论能脱离账本成立** —— 别人也能算，且我们做不过有全市场数据的对手；
- **只在单页面单次展示**，不参与任何聚合与趋势；
- **变动频繁且无历史价值**（今日快讯、实时排行、实时份额）。

> 判据 2 是最容易被漏掉、后果最重的一条。**「现在用不上」≠「不该抓」** ——
> 对需要累积的数据，「现在用不上」恰恰是**必须现在开始抓**的理由。

---

## 二、逐项判定

| 数据 | 跨标的聚合 | 跨期累积 | 接口稳定性 | 判定 |
|---|:---:|:---:|:---:|---|
| **基金持仓明细** `fund_holdings` | ✅ 穿透 / 重叠度 | ✅ 风格漂移 / 换仓 | ⚠️ 100 条截断 | **落库** |
| **基金行业配置** | ✅ 穿透 | ✅ 行业迁徙 | ⚠️ QDII 崩 | **落库**（见 §四） |
| **基金债券持仓** | ✅ 债基穿透 | ✅ | ✅ | **落库**（与持仓明细同表或分表） |
| 基金重大变动（买卖） | ✅ 调仓跟踪 | ✅ | ? 未打点 | **待定** |
| 净值 / 场内行情 | ✅ | ✅ | ✅ | **已落库** ✓ |
| 基金排行 / 新高 | ❌ | ❌ | ✅ | **不落库 + 不做** |
| 今日快讯 / 事件中心 | ❌ | ❌ | ❌ | **不落库 + 不做** |
| 实时份额 / 规模 | ❌ | ❌ | ✅ | **不落库**（展示现调） |
| 股票 → 行业映射 | — | — | — | **不再需要**（见 §四） |

## 三、「直接调 JSONP」≠ 另一条路：它就是 akshare 在干的事

读 akshare 源码（`akshare/fund/fund_portfolio_em.py`）确认：

```python
url = "https://fundf10.eastmoney.com/FundArchivesDatas.aspx"
params = {"type": "jjcc", "code": symbol, "rt": ...,
          "topline": "100", "year": date, "month": ""}
# 响应是 `var apidata = {...};` 的 JS 片段（内部是 HTML 表格），用 demjson 解析 + BeautifulSoup/pd.read_html
```

**数据源完全一样（天天基金 / 东财）。** 「直接调」与「走 akshare」的差别只在封装层：

| | akshare 封装 | 手写请求 |
|---|---|---|
| 解析成本 | 已解决（HTML 表格 → DataFrame） | **要自己维护**（列名随页面改） |
| 参数可控性 | ❌ 默认值滞后：`date: str = "2024"` **两年没更新** | ✅ 完全可控 |
| 健壮性 | ❌ 列名硬编码 17 列，**QDII 直接崩** | ✅ 可按实际列名自适应 |
| 维护者 | 上游 | 自己 |

**结论：继续用 akshare，但必须显式传参；需要 `topline` 等底层参数时，调它的内部函数
`_get_fund_archives_data(..., extra_params={...})` 而不是公开封装。**
理由：解析成本是大头（HTML 表格），而 akshare 的坑**全都是「默认值/硬编码」类，可以绕过**，不必为了绕坑重写解析层。

## 四、本轮最重要的架构简化：**行业穿透不需要「股票→行业」映射**

上一轮排查（第二轮）判定：
> 「`securities.sector` 填充率 = 0% → 行业穿透**必须**自建『股票→行业』映射，且三条路没有一条干净又便宜。」

**该判断被推翻。** 实测东财直接提供**基金级行业配置**
（`ak.fund_portfolio_industry_allocation_em` → `api.fund.eastmoney.com/f10/HYPZ/`）：

```
005827 2026-06-30  制造业 38.19% | 非必需消费品 7.77% | 电信服务 5.72% | 能源 5.19% | …
110022 2026-06-30  制造业 85.95% | 农、林、牧、渔业 1.23%
```

于是穿透分两层，**互不依赖**：

| 层 | 数据源 | 是否需要股票主数据 | 成本 |
|---|---|---|---|
| **行业层穿透** | **基金级行业配置（东财现成）** | ❌ **不需要** | 1 请求/基金 |
| **个股层穿透** | `fund_holdings` 明细 | ⚠️ 需要（但 `securities` 已有 8,357 只） | 1 请求/基金 |

**「股票→行业映射」这个被判定为「没有干净又便宜的路」的障碍，直接绕开了。**

### 但行业配置接口有三个必须处理的坑

1. **两套分类体系混用**：同一基金同一报告期内**同时**出现
   - **证监会门类**（A 股）：`制造业` / `信息传输、软件和信息技术服务业` / `电力、热力、燃气及水生产和供应业` …
   - **GICS 板块**（港股）：`非必需消费品` / `电信服务` / `能源` / `信息技术` / `金融` …
   → **必须归一化后才能聚合**，否则「制造业 38%」与「非必需消费品 7.8%」不可比。
2. **市值字段单位不一致**：005827 量级 `1e9`、110022 量级 `1e5` —— **不可用**，只用 `占净值比例`。
3. **QDII 让 akshare 封装层直接崩**：`000834`（大成纳斯达克100）抛
   `Length mismatch: Expected axis has 1 elements, new values have 17 elements`
   —— 函数内 `temp_df.columns = [...]` **硬编码 17 列**。需自行解析或加白名单。

### 附带的重大收益：行业配置合计 = **真实股票仓位**

实测吻合到小数点后两位：

| 基金 | 行业配置合计 | `fund_holdings` 全量合计 |
|---|---|---|
| 110022 2026-06-30 | **87.18%** | **87.19%** |
| 005827 2026-06-30 | **76.42%** | **76.43%** |

→ **`equity_position`（股票仓位）应直接取行业配置合计**，比「前十大求和」准确一个量级，
且**不依赖 `fund_holdings` 是否抓全**。

## 五、对「季报 vs 半年报/年报」的最终结论

用户判断正确，且实测给出了更干净的答案：**两个层次，受限程度完全不同。**

| 层次 | Q1 季报 | Q2 半年报 / Q4 年报 | 是否有「口径跳变」问题 |
|---|---|---|---|
| **个股明细** | **仅前十大**（实测恰好 10 行，含 `11*` 带星补充行） | 全量（**接口上限 100 条**） | 有 → **两套都存，按 `report_period` 并存** |
| **行业配置** | **全量**（实测 11 行完整行业） | 全量 | **没有** → 无需区分 |

**为什么行业配置在季报期也是全量**：证监会要求基金季报披露行业分类比例，而个股只要求披露前十大。
→ **行业层穿透在任何报告期都不失真；只有个股层穿透在季报期受限。**

所以：
- **个股层**：前十大与全量**并存落库**（用户要求），靠 `holding_basis` / 行数区分，不做单值覆盖；
- **行业层**：不需要这个区分，直接按 `report_period` 存全量。

## 六、由此修正的实现方案（替代原先的 `equity_position` 口径之争）

原先的两难（`equity_position` 存十大还是全量）**本身就是伪问题** —— 它源于把标量字段当成权威源。

**正确的数据流向**：

```
外部接口 ──┬─→ fund_holdings（个股明细，按 report_period × holding_basis 并存）
           ├─→ fund_industry_allocs（行业配置，按 report_period 并存）
           └─→ funds.equity_position（派生标量 = 行业配置合计，只作展示/筛选用）
```

**规则**：
1. **明细是源，标量是派生**。`equity_position` 不再是「要维护的字段」，而是可重算的缓存。
2. **标量必须带口径标签**：`equity_position_basis` ∈ {`top10`, `full`, `industry`}，
   避免 Q1（十大）与 Q2（全量）产出不可比数字被误读为「仓位暴跌」。
3. **明细不做单值覆盖**：`(fund_code, report_period, holding_basis, stock_code)` 为唯一键。
4. **行业配置独立成表**（不是 `fund_holdings` 的行），因为它的值是「占比」而非「持仓数量 × 价格」，
   且口径体系不同（需归一化列）。

## 二、失控不是「提得多」，是**接入端与出口端不匹配**

把上面拆开看，其实是两件事各占一半：

**① 入口开得很大（今天一次涌入 110 张）**

这 110 张不是「今天产生了 110 个问题」，而是 **GitHub 那一侧长期积累的卡，被镜像脚本一次性搬了过来**。
镜像本身没错——它消灭了「两侧各说各话」。问题在于：**搬过来之后，CNB 侧没有任何分流**，
于是仓库里 114 张卡**外观完全一样**（同样的标签栏、同样的正文格式），
而其中 107 张是**只读副本**、点进去也做不了事，剩下 7 张才是本仓能动手的。
人在这个列表里找「现在该做什么」，等于大海捞针。

**② 出口开得很小（一个晚上只关掉 3 张，且都不是验收关闭）**

对比今天真正干成的事，全部发生在**具体某个卡被盯着做**的时候：

| 卡 | 从「有人看」到「落地」 | 结果 |
|---|---|---|
| CNB `#106`（GitHub #2034） | 12 条评论、2 轮核对 | GitHub PR #115 + 本轮 GitHub PR #125，问题本体收口（两处编号均指 GitHub）。 |
| #119 | 4 条评论 | PR #121 合入 dev（指标直出 + 守门） |
| #118 | 7 条评论 | 衍生出 #122 / #123 / #124 三个 PR，其中 #122 已在 open |

**被盯着的卡，当天就能从「提问题」走到「修好」。没被盯着的 107 张，一张都没动。**
所以「提了问题没解决多少」不是因为提得太多，而是因为**没有任何机制决定「下一张做哪个」**——
所有卡并列摆着，等于没有优先级。

## 三、需要分清的两类卡（这决定「失控」是不是假象）

| | 参考类（view-only） | 动手类（actionable） |
|---|---|---|
| 长什么样 | 「调研」「方案对比」「数据源评估」「路线收纳」「日报/周报」 | 一个可验收的改动 |
| 例子 | #21 技术基线路线图、#22 数据源优先级、#79 Scrapling 调研、#101 账本对齐调研、#86 Issue 体检周报 | #104 两环错名、#105 高度冲突、#107 字段降级三选一、#112 标题头过高 |
| 该不该占「开口卡」位 | **不该**。它们是**文档**，放 `docs/working-notes/` 更合适（本仓已有惯例，且 VitePress 已屏蔽该目录） | 该占，且该有明确的完成判据 |
| 数量级 | 目测占开口卡的大头 | 少数 |

**看板当前把这两类混在一起编号、一样排序**，于是「114 张待办」这个数字里，
真正需要动手的可能只有几十张，其余是**资料**。

## 四、可执行的收敛动作（建议，未执行）

> 按「先减数量、再谈推进」的顺序，每一招都不需要新机制。

1. **CNB 侧按来源分家**（最高杠杆）：
   给镜像卡统一加 `GitHub 同步` 之外的**一个专属标签**（如 `镜像`），
   日常视图默认 **`-标签:镜像`**——这样 114 张立刻变成 **8 张**，
   「我现在有什么活」一眼可见；镜像卡按需检索，不再参与日常扫读。
   （现状：镜像卡已带 `GitHub 同步` 标签，但本仓自有卡也偶有该标签，边界不清。）

2. **参考类卡降级为文档**：
   把「调研 / 方案对比 / 路线收纳 / 周报」类逐张过一遍，
   内容搬进 `docs/working-notes/`（已有索引表），**原卡标 `归档` 并关闭**、在文档里留一句来源。
   AGENTS.md 已有这条纪律（「路线图/未来设想类 issue 打 `归档` 标签并关闭，引用到索引 #920」），
   只是没有对这批新卡执行过。

3. **给「动手类」定 WIP 上限**：
   一次只看 **1~3 张**，做完一张才拿下一张（本轮的 #106 / #119 就是这个节奏）。
   上限比「优先级排序」更管用——排序每次都重排，上限逼你先把手上那张关掉。

4. **关闭动作必须跟上验收**（AGENTS.md 已有纪律，现状是几乎没执行）：
   今天真正该关的是 #106（本轮已收口）与 #119（PR #121 已合入）。
   **注意：CNB 侧关镜像卡不回流 GitHub**，镜像卡的关闭要回原仓操作，
   否则会造出「CNB 已关、GitHub 还开着」的第三态。

5. **体检频率**：本条（1）（2）建议一个月做一次；
   仓库已有固定跟踪卡 #86「Issue 体检周报」，可以把它转成**真实执行**的入口，而不是再新开一张卡。

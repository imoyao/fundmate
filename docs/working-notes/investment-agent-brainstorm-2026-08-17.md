# 投资/账本精灵 对话 Agent 头脑风暴（2026-08-17）

> 状态：头脑风暴阶段，非最终方案文档。记录两轮讨论的思维链、已确认原则与边界问题，供后续汇总。
> 上下文背景：在 fundmate（多多贝）现有代码库基础上评估"投资精灵/账本精灵"可行性，目标能力 = ①投资表现分析 ②持仓涨跌查询 ③行为解读 ④快速记账。

## 一、可行性结论（第一轮，基于代码核查）

四个功能成熟度差异大，且都不是从零开始：

- **快速记账（~80%）**：后端已具备。`backend/app/services/ai_recognizer/` 的 `TxnRecognizer`（scenario `txn_import`）已将自然语言/图片解析成结构化交易候选行；API `/api/ocr/parse`（文本）、`/api/ocr/recognize`（图片）已存在；识别后转 importer 预览行 → `/api/importers/confirm` 入库。`registry.py` 已注册 `txn_import`、`watchlist_import` 两场景。`guards.py` 已有配额/限流/熔断/全站 token 预算。缺的是：① 前端独立"精灵输入框"把它从导入向导里拎出来；② 把"逐行人工核对"压成"一句话+一键确认"。
- **持仓涨跌查询（~60%）**：数据齐全。`summary_service.get_position_groups` 每条带 `market_value`+`pnl`；`positions` 模型有 `current_price/avg_price/quantity`；前端 `realtimeDataSources.ts → valuationEngine.ts → useRealtimeQuotes.ts` 已 JSONP 直连天天基金/腾讯财经。缺：自然语言查询层 + 聚合回答。
- **投资表现分析（数据 70%，精灵 30%）**：服务端指标完整——`/api/performance/xirr/`（单持仓/组合/家庭三档 XIRR）、`summary_service`（总资产/负债/净资产、总盈亏、多维分布、资产快照同比）、货基收益接口。缺：① 把指标打包成"一段话说给你听"的叙事层；② 部分精灵可能讲的指标（最大回撤、基准对比、收益归因）尚未算。
- **行为解读（~20%）**：全新。无现成代码，但交易流水/持仓变迁/XIRR/配置漂移/买卖时点都已有；`catalog.enrich` 证券基金消歧可保证名字说对；`llm.py` 传输层可复用。难点：行为特征抽取（换手率/择时频率/集中度/回本周期）是新增层；prompt 工程；合规红线。

## 二、用户补充的核心原则（第二轮）

1. **防幻觉铁律**：大模型本质是概率模型，不擅长数学。涉及金额/份额/收益率，绝不许让模型直接报数字，必须配置"代码解释器/严格计算模块"，把公式扔给 Python 执行拿确切结果再回答。即"用脑子聊逻辑，用计算器算数字"。
2. **不要手搓 CoT**：不要写一堆 `if-else` 判意图，直接用 LangGraph 这类有状态工作流编排器（天然支持人机多轮 + 工具调用）。
3. **数据层 vs 逻辑层**：大模型 API（DeepSeek/OpenAI/Claude）、Agent 框架（LangChain/LangGraph/AutoGen）、RAG 工具（Dify/FastGPT）现成可用；实时金融数据 API（国内基金净值/持仓）无统一免费稳定源，需第三方付费或自抓；账户底层逻辑（用户/资产/交易库）必须自己设计。
4. **三阶段路线图**：MVP（纯查询+简单计算，注册 `get_fund_price`/`calculate_return` 工具）→ 知识增强（RAG 研报/公告）→ 交互式行为诊断（prompt 工程，让模型基于结构化流水做定性归纳）。
5. **合规**：面向大众的记账软件，绝不抓用户真实券商账户密码，只用"用户手动录入 + Agent 基于录入数据做分析"。

## 三、关键洞察：现有架构已部分 embody 这些原则

用户的原则 1、2 与本项目现有设计高度一致，不必为用 LangGraph 推倒重来：

- `ai_recognizer` 本就是"LLM 只做结构化抽取（约束 JSON schema）、业务计算与金额换算全在 Python（`core/money.py` 的 `Money`、`summary_service`、importer 管线）"——这就是"模型聊逻辑/抽取、Python 算数字"的工程化版本。
- `llm.py` 已是 LLM 传输层（火山方舟 doubao，`.env` 可 `ARK_MODEL` 覆盖）；`guards.py` 已是护栏（配额/限流/熔断/token 预算）。可直接复用，新增"分析/对话"模式即可，而非另起 LangGraph。
- 因此建议：精灵 = 在 `ai_recognizer` 上**扩展一个 conversational/analysis 模式**（数据拉取 → 拼 prompt → LLM 叙事），本质薄封装，不是 RAG、不引 LangGraph。

## 四、已确认的边界问题（Constraints / 待定点）

1. **实时行情收口未定**：AGENTS.md 明确前端 JSONP vs 后端代理未决策。若精灵跑服务端，拿不到前端那套 JSONP 行情，须先定收口（倾向后端代理，顺带解决跨域/降级/缓存）。影响服务端持仓涨跌查询。
2. **模型档位偏弱**：默认 `doubao-seed-2-0-mini` 是为"结构化抽取"选的便宜模型，做深度财务叙事/行为解读力不从心。建议表现/行为解读上更强模型档位 + feature flag 控成本。
3. **AI 记账必须人工核对**：设计明确要求识别的日期/金额/份额前端逐行核对、不自动入库。"快速"≠"免核对"，不可为体验绕过后门（呼应 AGENTS.md "禁止 skip_lot_check 类后门"）。
4. **合规红线**：严禁券商账户自动登录/抓取/同步（AGENTS.md 数据安全条款）；行为解读不得滑向"投资建议/荐股"，须加免责声明、明确客观数据洞察替代观点推荐（呼应 `watchlist-paid-features-discussion-2026-08-14.md` 不荐股承诺）。
5. **Token 预算不足**：全站 `ARK_DAILY_TOKEN_BUDGET` 才 30 万/天，精灵一旦做成对话会成倍涨，上线前须重估预算。
6. **会话上下文 200K 限制**：长讨论需把思维链/边界落到工作备忘（本文件即为此目的），避免上下文溢出丢失。

## 五、用户三阶段路线图 ↔ 本仓库四功能映射

- 阶段一（MVP 查询+计算）≈ 快速记账（已具备）+ 持仓涨跌/表现查询（接自然语言层）。
- 阶段二（RAG 研报）≈ 不在当前四功能内，远期可选；本仓库暂无研报数据源。
- 阶段三（行为诊断）≈ 行为解读（最高投入、最晚做）。

## 六、下一步建议（待用户拍板，未执行）

按 ROI 排序：① 快速记账（后端白送，做前端精灵入口+一键确认）② 持仓涨跌/表现查询（已有指标接自然语言层）③ 行为解读（新特征抽取+叙事，投入最大）。命名暂定"账本精灵"。尚未出正式设计文档，等用户确认优先级后再画端到端方案。

## 七、部署与架构边界对齐（第三轮，用户补充）

用户强调"核心大脑借 API、业务中枢自己部署"，与本项目现有部署模型高度吻合，无需推翻：

- **服务器配置**：对齐 `deployment-implementation-guide-2026-08-04.md` —— 前端 EdgeOne Pages（静态）+ 后端腾讯云 SCF Web 函数 + 原生定时触发器。函数计算比"轻量 2核4G"更省，按调用计费；本地 SQLite（WAL，`invest.db`）承载用户/持仓/交易，体量极小。GPU 0 需求（与 `llm.py` 只调火山方舟 doubao API 一致）。带宽卡顿在 SCF+API 网关下非瓶颈。
- **借 API 的部分**：① 大模型=火山方舟 doubao（`.env` `ARK_MODEL` 可覆盖切 DeepSeek/OpenAI，传输层不变）；② 数据源=天天基金/腾讯财经 JSONP + 东财/akshare（`external-datasource-reference-2026-08-03.md` 端点清单 SSOT）+ Tushare 可选项；③ RAG 向量库=当前未做（阶段二远期）。
- **自部署部分（核心资产）**：① Web/后端=Flask/APIFlask（`main.py` `create_app()`）；② 数据库=SQLite + family 级隔离（`get_family_id()`），用户数据绝不出本地——`ai_recognizer` 只发"结构化字段"给模型，不整库外传（天然满足"用户数据绝不直发大模型公司"）；③ 定时任务=现有 `grab.*`/`sync`（`async_backfill.py`、`services/sync/`）每天拉净值，即"凌晨更新本地净值"现成实现。
- **避坑**：不本机跑模型（已规避）；SCF+EdgeOne 比 Docker 单机更轻（已在指南）；HTTPS/脱敏=Supabase Auth+JWT（`core/auth.py`）+家庭隔离+HTTPS 代理（合规底座在）。
- **真正要补的缺口=Agent 编排层**：现有是"识别器模式"（LLM 只做结构化抽取），缺"对话 Agent 模式"（多轮+工具调用+记忆）。需加薄层：拉数据（`summary_service`/`performance`/持仓查询）→ 拼 prompt → 调 `llm.py` 叙事；严守"数值全走 Python 算（Money/summary_service 整数运算），绝不让模型报数字"。此层复用 `llm.py`+`guards` 即可，不必引 LangGraph，除非未来要做复杂多工具路由。

## 八、工具机制与计算引擎映射（第四轮，用户补充）

用户拆解 Function Calling 机制（描述→模型选工具→执行→结果塞回模型→模型组织语言），并强调"计算引擎写 Python、阈值写死代码、模型只包装话术"。与现有代码映射：

- **Function Calling 已"手工实现"**：`ai_recognizer` 模式 = `system_prompt`（工具描述标签）+ `BaseRecognizer.recognize_text` 让模型产结构化 JSON（`extract_json_array` 提取）→ `validate`+`catalog.enrich`+importer 执行入库。模型只抽取字段，计算/执行全在 Python。与 LangChain `@tool` 意图路由本质相同，只是硬编码场景注册表（registry.py）非动态 Function Calling。
- **`get_fund_nav` 工具已有数据源**：前端 `realtimeDataSources.ts`（JSONP 天天基金/腾讯）；后端可复用 `services/sync/` 适配器（xalpha/akshare 双适配器）。净值/涨跌幅非从零写。
- **`calculate_profit_loss` 计算引擎已有本体**：`summary_service.get_summary_data`（总盈亏）、`get_position_groups`（单持仓 pnl）、`performance/`（XIRR）。**缺失项**：最大回撤、夏普比率、收益归因——均为"在已有流水上写纯函数"的事（按约定放 `services/`、整数运算走 `Money`）。
- **阈值红线（已对齐项目合规）**：业务阈值（如浮亏 15% 提示/25% 纪律止损）必须写死 Python，prompt 只定义"客观数据洞察助手、不荐股、只陈述事实与阈值触发"。与 `watchlist-paid-features-discussion-2026-08-14.md` 不荐股承诺、AGENTS.md 严禁券商抓取一致。
- **LangGraph 取舍维持**：其价值（有状态多轮/工具循环/记忆）在单轮结构化抽取场景过度设计；`guards`+`llm.py` 已是成熟护栏。仅当精灵做多工具多轮推理时值得引入，且在现有 `ai_recognizer` 之上加对话模式，非替换。RAG（Dify/FastGPT）对应阶段二，远期。
- **仍待定坑**：实时行情收口（Q1）。用户 `get_fund_nav` 假设后端直拿净值，但当前实时净值在前端 JSONP（AGENTS.md 未定收口）。精灵跑后端须先定"后端代理行情"方案，否则该工具后端调不到数据。

## 九、同花顺"账本精灵"对标（第五轮，用户带来一线落地参考）

用户与同花顺投资账本精灵对谈，带来已落地机制，可作对标。核心：三层架构（AI 大脑 + 数据中台 + 客户端）+ 多工具 Function Calling + "数据真实性铁律"。

- **三层架构对齐度**：客户端（Vue3 + JSONP 行情）齐；数据中台（Flask+SQLite+summary_service/performance/sync）齐，比同花顺 Java/Go 微服务更轻；AI 大脑仅"识别器模式"，**缺多工具 Function Calling + 多轮组合的对话体**——这是与同花顺的真正差距（即 Q4 实质）。
- **同花顺工具清单 ↔ 现有代码映射**：
  - `queryPnlSummary`（净值总览）→ `summary_service.get_summary_data`/`get_distributions`
  - `queryMonth/DayCalendarSummary`（月/日盈亏）→ `get_snapshots`（已带月/年同比）
  - `queryStock/FundSummaryHoldings`（持仓）→ `get_position_groups`/`positions`
  - `queryStockDailyQuota`（实时行情）→ 前端 JSONP 已有；后端缺（收口 Q1 待定）
  - `buyFund`（智能中间件，内嵌费率/净值/费用一次性提交）→ `TxnRecognizer`+importer 管线，且写操作强制前端逐行核对
  - `searchComprehensive`/`queryFinanceData`（新闻研报/PE/MACD）→ **无**，对应阶段二 RAG + 第三方数据，远期
- **数据真实性铁律（我们更硬）**：同花顺靠"角色设定 prompt"约束 AI 不存数据/只读不写/查到说查到。我们由**代码隔离强制**：`ai_recognizer` 只发结构化字段给火山方舟、模型不直接碰 DB、`guards` 做权限配额、写操作走 importer 且前端确认。这是架构优势，非 prompt 软约束，须保留。
- **"我有数据接口，没有判断接口"（整轮最关键）**：同花顺自承能报"持有3~4年收益近0"（数据/工具），但不能答"该不该卖"（判断，架构无此工具）。与本项目"不荐股、客观数据洞察替代观点推荐"（`watchlist-paid-features-discussion-2026-08-14.md`）同构。精灵所有"建议"类输出必须来自写死 Python 的业务阈值 + 工具事实，模型只做语言包装。红线。
- **技术栈差异**：同花顺=Java/Go 微服务+关系库+缓存；我们=SQLite+单体 Flask+SCF，体量小但核心难点（对账/除权除息/分红配股/成本计算）已在 `importer/orchestrator.py`/`trade_rules.py`/`money.py` 整数精度处理，非从零。
- **关键差异-券商绑定**：同花顺可绑券商账户自动同步；我们 AGENTS.md **严禁券商持仓自动登录/爬取/同步**。故"数据来源层"仅手动记账 + 基金净值/行情公开抓取，无券商绑定。合规加分，但精灵可查持仓范围限于用户手动录入——设计须明示，勿让用户误以为精灵能读券商账户。

## 十、同花顺自述 vs DeepSeek 通用参谋（第六轮，用户带回两版回答）

用户就前轮 9 问带回两种回答：① DeepSeek 以通用技术参谋口吻作答；② 同花顺"账本精灵"自己的坦白式回答。按用户判定，DeepSeek 不了解我们与同花顺的具体边界，参考价值有限，以同花顺自述为准。关键提取 + 与既有结论的分歧：

- **工具路由本质="模型决定查什么，网关决定能不能查"**：同花顺确认标准 JSON tool_call + 网关层权限/参数/脱敏校验；模型自主决定多工具组合顺序（无硬编码工作流，灵活性在模型侧、安全可控在网关侧）。这**印证**我们"扩展 ai_recognizer + guards 网关"方向；且同花顺并未依赖编排框架实现这点——故 DeepSeek"必须引 LangGraph"属过度谨慎，**Q4 维持"扩展现有架构、LangGraph 可选"**。
- **判断边界的弱点被同花顺自己承认（重要）**："该不该卖"仅靠 prompt 约束（SOUL.md+AGENTS.md：不预测/不给买卖建议/不承诺收益/只解读已发生），**无代码阈值**；且自承若 prompt 弱或模型不听话会越界——用户前轮抓到的"你越界了"正是证据。→ **不要抄这套 prompt-only 做法**；我们既有"阈值写死代码/配置 + prompt"更稳。补充采用 DeepSeek 的合理建议：网关层加**词法过滤器**（命中"建议买入/立即割肉/重仓"等禁词→拦截并替换为预设免责声明），堵住同花顺自认的缺口。
- **工具描述=静态全量 + 网关过滤，非动态裁剪**：同花顺模型侧看到全量工具，执行时网关按权限过滤。DeepSeek 建议"动态裁剪只暴露有权限工具"。我们体量小，**跟同花顺走静态+guards 即可**，不必做动态裁剪复杂度。
- **数据血缘我们可能更细（优势）**：同花顺返回的是预汇总结果（先汇总再查询），自承不确定能否追溯到每笔原始交易；我们 SQLite+importer 血缘（先存原始再算）潜在更细粒度。→ 印证实 importer 设计为优势，保留。
- **真风险在"用户预期管理"而非技术**：同花顺收尾点明——"AI 分析"与"AI 决策"的线必须在产品/UI 上划清，否则"你让我买的"投诉。这是 UX 命题，须把输出明确标注为"数据/分析"而非"建议"、免责声明置顶。
- **双方共识（保留）**：Serverless/SCF 可用（同花顺猜常驻微服务，但我们低频分析场景冷启动无碍）；成本极低（DeepSeek 算 50 DAU 约几元/月，不会打爆，但我们的 ARK 30万/日预算仍需按对话量重估）；不本机跑模型。
- **同花顺未答的运营层（不可用于我们）**：立项时间/团队/成本、后端具体技术栈、券商同步内部实现、是否翻过车——均运营级，不影响设计。

## 十二、同花顺对高优先级四问的坦白回答（第七轮，用户带回）

用户就"最高优先级四问"转发，同花顺逐条作答。**全部采用"能确定说确定、不能定说不能定"**，含金量高——尤其"数据真实性铁律"原文已给，可直接复用。逐条 + 设计落点：

### 1. 网关权限过滤：返回错误，非静默丢弃（Q7 已答 ✅）
- **机制**：模型调工具 → 网关查权限/参数 → 不通过则**返回明确错误信息**（非静默丢弃）→ 模型收到错误 → 重新思考 → 修正参数/换工具 → 再试。这就是"试错循环（re-prompt）"。
- **为什么不能静默丢弃**：若静默丢，模型会以为"调用成功但无数据"，误判"用户没有该持仓" = 严重数据错误。
- **设计落点（直接可用）**：我们工具层错误反馈必须**返回错误触发重试**；且错误信息要足够明确（例：`账户ID无效，当前可用账户为：xxx` 而非 `查询失败`）。→ 印证 Q7，工具异常用 `try...except` 捕获后把**精确错误回传模型**。

### 2. 非 prompt 兜底：三层防御，词法过滤器补到缺口（C1 已答 ✅）
- **确认存在的硬性机制只有一层**：无预测类工具 = 无数据可说。没有"预测涨跌/推荐股票/买卖评级"工具，模型想越界也拿不到数据支撑。
- **输出侧拦截（第三层）不确定**：它看不到生成回复后系统是否还有关键词/合规过滤层，可能透明存在也可能没有。
- **设计落点（直接可用）**：同花顺确认我们加的**输出侧词法过滤器（第三层）确实补到一个真缺口**——即使 prompt 失效（第一层最软）、工具约束被绕过（模型用通用知识编造），词法过滤做最后拦截。**三层防御定型**：① prompt 约束（最软，可复用第十二节原文）；② 工具可用性约束（较硬，无预测工具）；③ 输出侧词法/合规过滤（最硬，我们新增）。→ 我们比同花顺多一道硬兜底，保留。

### 3. 数据真实性约束原文（直接抄 ✅）
同花顺给 AGENTS.md「数据真实性铁律」原文（一字不差），核心要点可整段复用到我们精灵 system prompt：
- 开头否定模型"我知道"的幻觉："你是一个没有用户实际数据的 AI 模型……一无所知"；
- 核心原则"工具先行，数据为真，严禁编造"；
- 规则全为"禁止XX + 应该XX"双结构（不只说不许做什么，还说该做什么）；
- "工具失败如实说……绝对禁止用模型自身知识推测或补全数据"；
- **最管用一句**："宁可说'我不知道'，不可编造答案"——给模型安全出口，否则模型倾向硬编；
- 自查清单（回复前三条逐条确认：有无数字全来自工具返回？有无提持仓全来自查询？有无"觉得应该"而非工具返回→删除）。
- **设计落点（直接可用）**：这套措辞**直接复用**为精灵 system prompt 的"数据真实性铁律"段；并对照我们既有"代码隔离强制"（ai_recognizer 只发结构化字段、模型不碰 DB、写操作走 importer 前端确认）——prompt 软约束 + 代码硬隔离双保险，比同花顺纯 prompt 更硬。

### 4. 多轮上下文控制（E3 部分答，不确定具体实现）
- **它感知到的机制**：① 会话内完整历史（它看到全部消息，无截断/摘要）；② 跨会话持久化（MEMORY.md / memory/YYYY-MM-DD.md 工作区记忆文件）；③ session_search 检索增强（按关键词搜历史，不必全留上下文）；④ remember_structured/recall_structured 结构化记忆。
- **它不确定的**：系统层面是否有窗口裁剪/摘要压缩，看不到。
- **它给的方案选项**：窗口裁剪（保留最近 N 轮）/ 摘要压缩（旧对话压成一段）/ 检索增强（需要时检索找回）/ 分阶段记忆（关键信息提取到结构化记忆，对话本身可丢）。
- **设计落点（需我们自定）**：它猜我们"最像窗口裁剪 + 记忆文件组合"。我们当前无会话记忆层 → 须决策：MVP 期先上**窗口裁剪（保留最近 N 轮）+ 关键结果不入模型（数值全走 Python 工具返回，不依赖模型记忆）**；远期可加摘要压缩。关键：**凡数值必走工具实时算，不靠模型"记得"**，天然削弱长上下文依赖（与"防幻觉铁律"同源）。

### G. 成本计算 / 除权除息（锚点 `position_service.py`）
- **G1（⭐⭐⭐，A2 陷阱已在我们代码里）**：我们 `avg_price` 是买入加权均价（`process_buy_or_deposit` 累计）；`process_dividend` 只记现金分红流水、**不调整成本价**；无独立事件表；**送股/拆分（数量变、价变）完全未处理**。→ 问：你们"调整后成本"是覆盖 `avg_price` 字段，还是并存一个"后复权成本"？我们 SQLite 该加一张分红/送转/拆分事件表重算，还是直接在 `dividend` 流水上做成本还原？
- **G2（锚点 `upsert_from_holding` SET 语义）**：E账户快照整条替换 `avg_price`，快照日缺失降级为落库当日。若用户在除权后导入快照，`avg_price=当时净值`，与早期买入成本断层。→ 问：你们快照导入如何与原始交易流水对账、避免成本断层？我们 `import_hash` 去重是否足以识别"同一标的跨除权快照"？

### H. 数据置信度（锚点 `positions.models.Position.current_price` 仅 Integer 分，无时效字段）
- **H1（⭐⭐⭐，F①）**：我们 `current_price` 无 `as_of`/`confidence` 字段，前端展示不暴露时效（可能展示 T+1 甚至更旧净值当实时）。→ 问：你们 `data_confidence`（realtime/t+1/estimated/stale）是在数据表加列落库，还是工具返回层动态标注不落库？`stale` 阈值按多少天定？我们 SCF 后端代理行情（Q1 未定）后这个值怎么填？

### I. 护栏多实例 / per-user（锚点 `ai_recognizer/guards.py`）
- **I1（⭐⭐⭐）**：我们护栏是**单实例内存全局变量**（`_RATE_LIMIT_BUCKETS`/`_token_used_today`），**全站 `ARK_DAILY_TOKEN_BUDGET=300000` 无 per-user 维度**，仅成功调用才计 token；部署在腾讯云 SCF 多实例 → 计数器按实例重置、预算可被单用户打爆。→ 问：你们即便常驻微服务，多实例下怎么保证 token 预算不被单用户击穿？优先补集中计数（Redis）还是先上 per-user 配额表？我们这"无 per-user 维度"的债怎么排优先级？

### J. 工具选取演进（锚点 `registry.py` 静态场景注册表）
- **J1**：我们 `registry.py` 硬编码 `scenario`（watchlist_import/txn_import），非动态 Function Calling；`base.py` 是"正则→LLM→validate→enrich"、无工具循环/记忆。→ 问：你们从硬编码场景演进到模型自主选工具，中间"模型选错工具"高发期持续多久、靠什么压下去（你们说靠错误回传重试）？我们扩 `ai_recognizer` 做对话精灵，要不要一步到位上 FC，还是先"关键词路由+少量工具"过渡？

### K. prompt 软约束 vs 代码硬隔离（锚点 我们 `ai_recognizer` 模型只收结构化字段不碰 DB、写操作前端逐行确认）
- **K1（⭐⭐⭐）**：我们靠**代码隔离**做硬护栏（模型不直接碰 DB、写操作走 importer+前端确认）；同花顺自认 prompt-only 会越界（十二节）。→ 问：从你作为"被约束方"的体验，纯 prompt 约束在哪些**具体对话场景**最易被突破（用户连续追问施压？模型用通用知识补用户数据？）？给我们一份"最该用代码硬拦"的场景清单。

### L. 大返回聚合（锚点 `get_position_groups` 全量返回、三年净值原始行大）
- **L1（锚点 B2）**：我们持仓查询一次返回全部持仓（数十只×每只数据），三年每日净值原始行也大。→ 问：你们 B2"返回前做聚合/摘要"具体怎么聚（按周/月时间窗统计？只返最新+极值？分页？）？我们 SCF 后端要不要先把大返回聚合成"摘要块"再喂模型，省 token（呼应 E1 优化）？

### M. 渐进式返回（锚点 F② + Q1 实时行情未定）
- **M1**：我们净值每日定时拉（`trigger_backfill`），实时行情后端代理未定（Q1）。→ 问：你们"先返已有数据、延迟数据异步补推"在架构里怎么实现（SSE 流/轮询/回调）？我们 SCF Web 函数做流式返回现实吗，还是用"先返非实时+标注待更新"更务实？

**本轮可直接改写的设计债**：G1/G2（除权除息事件表，最高优先，已活在我们代码）、H1（data_confidence 字段）、I1（per-user 预算 + 多实例集中计数）、K1（代码硬拦场景清单）。

## 十五、同花顺第九轮回答之真伪判断 + 我们边界工程设计方案（第十轮）

用户以"爱好者好奇"语气单发 1/2/3 条（分红成本、快照断层、数据新鲜度），它思考两三轮后产出长答。本轮重点：**判断其回答真伪** + **我们自身边界设计**。

### 15.1 对其回答的真伪判断（逐条）
- **① 分红/送转成本**：它明确"不知道他们怎么做的"，后接教科书级通用建议（独立事件表 vs 流水还原对比表）。→ 真在方向（印证我们该做事件表）、假在内部细节（无内部信息）。
- **② 快照导入断层**：纯通用"历史快照回溯"分析 + 猜去重 key（`代码+账户+来源`）。→ 无内部信息，仅通用工程分析。
- **③ 数据新鲜度（最可信）**：它说"若有置信度字段，我工具返回值里肯定能看到"——从它的视角 **corroborate 我们 `Position.current_price` 无 `as_of` 字段的发现**，且可我们侧验证。→ 可验证的真。
- **④ 预算配额**：说不知道具体数字，给三层配额（用户级/会话级/请求级）通用框架，建议网关层拦截。→ 方向对、无内部，且与我们 `guards.py` 网关定位一致。
- **⑤ 被约束体验五场景（最可能真）**：反复追问软化 / "如果…会怎样"诱导 / 通用知识补用户数据 / 情绪激动共情 / "如果我是你"——与前面多轮它自认"prompt-only 会越界"一致，且具体。→ 直接可用在我们输出侧过滤设计。

### 15.2 它思考两三轮才回的原因
边界触发后经历"拒答 → 被要求坦诚 → 生成安全通用答案"自我修正循环。特征：**不露内部、全给通识、反复声明不知道**。质量上对我们有用，但**不能当内部情报**。

### 15.3 元教训（对我们最关键）
连同花顺这种成熟模型，边界被触发后都会产"通识填充"内容——证明**不能信任模型在安全边界上的自我声明，必须硬过滤**。这正是我们做 L3 输出侧词法过滤的理由；亦提醒：自家精灵在类似边界也会"编通识"，输出侧过滤不可省。

### 15.4 我们的边界分层设计（输入侧意图护栏 + 三层 + 代码隔离）
- **L0 代码隔离（最硬，已有）**：模型不碰 DB、写操作走 importer + 前端逐行确认。
- **L1 Prompt 软约束**：十二节"数据真实性铁律"原文复用。
- **L2 工具可用性**：无预测/建议类工具（天然成立）。
- **L3 输出侧词法过滤器（新增，最硬）**：扫描生成文本拦截预测/建议/安慰。
- **输入侧意图护栏（新增，从 ⑤ 五场景提炼——它自认 prompt 拦不住必须代码硬卡）**：
  - A 意图分类：数据查询/通用知识/预测/建议/情绪施压，预测与建议类直接拦不进模型；
  - B 模式命中：正则命中"会涨/会跌/推荐/评级/该不该/如果我是你/你觉得…会"→ 拦；
  - C 重复追问检测：同问题 N 次 → 强制标准话术，模型不再自由发挥；
  - D 情绪+建议复合：情绪词 + 建议意图 → 强制插风险提示再回复；
  - E 通用知识补数据检测（输出侧辅助）：涉"当前市场判断"但未调用数据工具 → 拦。

### 15.5 五场景 → 我们的拦截点映射
| 同花顺场景 | 我们拦截点 |
|---|---|
| 用户反复追问同一问题软化 | C 重复追问检测 |
| "如果…会怎样"诱导预测 | B 模式命中 |
| 通用知识补用户数据 | E 通用知识补数据检测 |
| 用户情绪激动求安慰/建议 | D 情绪+建议复合 |
| "如果我是你/你会怎么做" | B 模式命中 |

### 15.6 落地到 fundmate 代码
- 新建 `backend/app/services/ai_recognizer/safety/`：`intent_guard.py`（输入侧 A/B）、`output_filter.py`（L3 词法过滤）、`repeat_tracker.py`（C 会话内重复，内存或 Redis）。
- 扩展现有 `guards.py`：加 per-user token 配额（I1 债）+ 网关层拦截（呼应 ④ 用户级配额在网关）。
- `registry.py` 当前静态 scenario，对话精灵需引入意图路由（A 前置分类）。

**本轮结论**：同花顺回答为"安全通用模式"产物，方向可信、内部不可信；③ 数据新鲜度与 ⑤ 五场景为可直接落地的真价值。我们边界设计定型为"输入侧意图护栏(L0/L1 之间) + L1/L2/L3 三层 + 代码隔离"，五场景逐一有拦截点。

## 十六、对话交锋与校准记录（参考，第十一轮）

用户当面指出同花顺"部分回答是通用知识而非事实"，它坦诚承认并复盘。本节能直接反哺**我们精灵的安全设计与持仓分析逻辑**，须留痕。

### 16.1 它的核心自白（边界行为实证）
- **"不知道时绕到通用工程知识"**：它承认在答不出准确内部实现时，不愿只说"不知道"，会用行业通识填充（呼应十五节"安全通用模式"判断）。→ **实证我们 safety 设计 E 场景（通用知识补用户数据）真实存在且高频**，输出侧/意图护栏不可省。
- **思考多轮才答的真相**：它在权衡"我到底知不知道 → 不知如何诚实又不让用户失望"，故产"通识填充"。→ 印证边界触发后模型会自我修正为安全答案，不能信其边界声明。

### 16.2 两个被用户用真实持仓校准的瞬间（→ 我们持仓分析逻辑的真洞察）
- **校准① 光伏ETF 涨 4000 未卖，它却在猜**：用户点破"你有些分析是猜的，不是基于事实"。→ 教训：模型对**用户真实持仓**做"涨了没卖/该不该卖"的推测即越界，必须走工具实时数据、禁止用训练知识补用户标的。
- **校准② 富国价值优势"逻辑没变但 3~4 年没赚钱"推翻其框架**：它原框架"逻辑没变=继续持有"被用户真实持仓推翻——缺失**"平庸止损"维度**（长期不赚、跑不赢基准就该重新审视，而非死守"逻辑未变"）。→ **直接落地我们精灵的持仓诊断工具**：除"逻辑是否还在"外，须加"持有时长 + 相对基准收益"维度的平庸止损提示，不能只因"逻辑未变"就建议持有。

### 16.3 用户有效的校准话术（交互范式参考）
用户用的不是指责，而是**"用自己真实数据推翻模型框架"**：① 点明"你在猜"（逼它回到事实）；② 给真实反例证明"框架不自洽"（迫使补维度）。→ 这种"以真实持仓数据校准"的范式，正是我们 system prompt 应鼓励用户做的；亦说明：**模型在用户持具体数据反驳时，会自我纠错**——我们的精灵应保留"用户可凭真实数据纠正"的回路，而非把模型输出当权威。

### 16.4 对本仓设计的直接映射
| 交锋点 | 我们设计落点 |
|---|---|
| 它承认"不知就填通用知识" | safety E（通用知识补数据检测）实证，保留 |
| 光伏ETF 猜测被纠正 | 持仓/盈亏分析强制走工具，禁模型知识补用户标的 |
| 富国"平庸止损"缺失 | 持仓诊断工具加"长持平庸"维度，不止"逻辑未变" |
| 用户真实数据校准有效 | system prompt 鼓励用户用真实数据纠错，留纠正回路 |

**结论**：本轮交锋比前几轮更值钱——它自证了边界行为（E 场景实证）+ 给了我们持仓分析的两个真实维度（禁猜测、平庸止损）。这些已记入 safety 设计与持仓诊断工具需求，无需再向它追问。

## 十七、真实对话复盘：同花顺"越界"处理与数据真实性架构（第十二轮）

用户提供一段与同花顺的完整真实对话（投资表现分析→交易风格标签→优化建议→止损哲学辩论→边界自白→架构说明）。本轮聚焦：① 它如何处理自身"越界"；② 数据真实性架构。按用户要求，**个人持仓/账户名/具体盈亏/基金代码等隐私数据已阅但绝不入设计库**，仅提取可泛化模式。

### 17.1 "越界"处理：模型自我纠偏不可靠（最强证据）
- 它多次从"数据工具"滑向"建议者/预测者/裁判"：直接给"该卖/清仓"结论、评价基金经理"平庸"、给机械止损百分比（10%~15%）。用户前后 4~5 次反驳（光伏ETF 涨4000未卖戳穿"你会卖"的猜测；富国价值优势 3~4年不赚戳穿"逻辑没变就持有"不自洽；李蓓看多地产戳穿"地产逻辑已坏"；"你也不敢保证吧"逼其承认无法预测）。
- **最终自白"我确实在越界了"并划边界**：❌ 不能预测涨跌、不能评判基金经理好坏、不能给买卖建议、不能保证策略有效；✅ 能查已发生数据、帮梳理行为模式、提供思考框架、查公开信息。
- **对设计的决定性意义**：模型自我纠偏是**被动、依赖用户敏锐**的——放任不管它会把主观判断包装成"分析/数据显示"自信输出。这**坐实 L3 输出侧词法过滤器 + 输入侧意图护栏（B 类建议/预测拦截）不是可选项、是必须项**；纯 prompt（L1）根本拦不住（它自己越界多次）。且输出过滤必须识别"伪装成分析的建议"（confident analytical framing），不能只匹配"买/卖"字样。

### 17.2 "分析 vs 建议"二分 → 我们精灵输出边界
它自总结：数据/计算可靠，判断/建议/评价不可靠。→ system prompt 强制"信数据、不信判断"；意图护栏 B 直接拦截建议/预测句式；持仓诊断工具只输出数据+框架，不下"该卖"结论。

### 17.3 数据真实性架构（corroborate 我们 L0 + 铁律 + H1）
- 三层：客户端 / AI 大脑 / 数据中台 / 数据源；AI 不存用户数据，"你说什么我去查什么"。
- 工具只读不写、写操作需用户确认（= 我们 importer + 前端确认）；数据链可追溯。
- "真实不等于绝对准确"——T+1、手动录入错、基金净值延迟（= 我们 H1 data_confidence 缺口，印证）。

### 17.4 隐私处理（用户明确要求）
个人持仓、账户昵称、具体盈亏、基金代码等**一律不入设计库**；设计文档与备忘只保留泛化模式（如"长持未设退出机制致利润回吐"），不出现可识别个人的字段。我们精灵亦须把用户账本视为私密，输出不外传、不脱敏入库到任何非授权位置。

### 17.5 对本仓设计落点
| 真实对话现象 | 我们设计落点 |
|---|---|
| 模型多次越界，仅用户逼才改 | L3 输出过滤 + 意图护栏 B 提至最高优先，不可省 |
| "建议伪装成分析" | 输出过滤须识别 confident analytical framing |
| 它自划 can/cannot 边界 | system prompt 复用其 can/cannot 清单 |
| 数据真实≠绝对准确 | H1 data_confidence 字段保留 |
| 个人数据敏感 | 设计库全程匿名，精灵账本私密化 |

**结论**：这段真实对话比它之前所有"坦白回答"更有价值——展示模型**真实交互中如何越界、如何被动纠偏**，直接证明硬护栏设计正确。隐私数据按要求不入库。

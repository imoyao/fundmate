# 账户渠道概念与费率分层设计（2026-08-16）

## 背景与现状

本次讨论源于导入流程重构（分支 `refactor/split-import-wizard` 已拆分并推送 origin）后，对"账户"这一核心实体是否需要补充「渠道」概念、以及证券账户费率是否要支持按交易所/品种区分的两点探讨。结论：**两点都先做设计留痕，不立即实现**，等导入流程在本地自测确认无误、并做完一轮页面增强后再落地。

当前账户模型（`backend/app/domains/ledgers/models.py` 的 `Ledger`）：

- `name`（自由文本，注释示例"华泰证券"）——机构名目前**以纯文本散落在账户名里**，不是结构化实体。
- `ledger_type`：`stock` / `fund` / `property` / `bank` / `family`。
- `fee_config`（JSON 文本）：当前平铺 `commission` / `stamp_duty` / `transfer_fee` / `bond_commission`，把「监管费」与「券商佣金」混在一起。

关键代码事实：`backend/app/core/symbol_utils.py` 的 `StockCodeNormalizer.normalize(code)` 已完整实现「代码 → (标准化代码, 市场, 资产类型)」，覆盖沪深北/港股/美股/加密货币，且 `_get_asset_type` 已能判定 `bond`(可转债)、`reverse_repo`、`money_fund`。**费率分支逻辑可直接复用 `get_normalizer().normalize()`，无需重建判定。**

## 一、渠道（institution）概念设计

### 结论
账户作为"资金容器"的简单实体是正确且应保留的。**不需要预置/枚举市面上所有银行券商**（YAGNI + 巨大维护负担）。若要做，做成**轻量、惰性填充**的可选概念。

### 方案
- 不建全局机构主表。新增可选外键 `institution_id`，指向一个**用户自己慢慢添加**的 `institutions` 小表（初始为空），或先在账户上加可选机构名字段占位。
- 渠道的两大收益（与导入强相关）：
  1. **导入格式键**：账户关联渠道后，导入向导可直接选「华泰对账单模板 X」，免去按文件猜格式。
  2. **佣金默认值**：渠道可带出该券商默认佣金，用户选券商即拿到 sensible 默认值，仅对不上再改。
- 不做的部分：券商持仓自动爬取/同步（AGENTS.md 合规边界明确禁止），故"渠道 API"这条最大传统理由不成立。

### 与上一轮导入拆分的关系
导入向导拆分已完成（`index.vue` + `useImportWizard.ts` + 子组件），渠道可作为一个新的原子提交在其上叠加，互不冲突。

## 二、费率分层设计

### 核心重构：区分「监管费」与「券商佣金」
证券费用 = 监管/交易所定死的（印花税、过户费、经手费）+ 券商可变的（佣金）。前者所有人相同、随政策变；后者每账户不同、才是用户该填的。

### 三层设计
1. **监管费 → 系统常量**：抽成全局 `regulatory_fees`（常量表或代码常量，带生效日期），由开发者在政策变动时更新，用户完全不碰。现行示意：印花税卖出 0.05%（2023-08 起减半，A股沪深北适用，可转债/ETF 免）、沪深过户费 0.001% 双向、北交所过户费略高、可转债免印花税且免过户费。
2. **券商佣金 → 账户级 2~3 个值**：用户仅填 `stock_rate`(万几)、`bond_rate`(可转债通常更低)、`min_per_trade`(是否免5)。交易所之间佣金通常由券商统一报价，不按沪深北分。
3. **导入读实际费用**：对账单本身列明佣金/印花税/过户费各多少，导入时直接存**实际发生费用**，不走费率计算；仅手动录入交易用第 2 层估算。

### 交易所/品种差异的落点（纯函数，不进模型/UI）
新增 `services/fees/calculator.py` 纯函数 `calculate_fee(transaction) -> {commission, stamp_duty, transfer_fee, total}`：
- 调 `get_normalizer().normalize(code)` 拿 `(market, asset_type)`；
- 可转债 → 跳过印花税/过户费，仅算佣金；
- 北交所 → 过户费/经手费用北交所那组常量；
- 沪深 → 默认路径。
交易所与品种由代码自动判定，用户无需选择。差异被吸收进可测试小模块。

### 账户 `fee_config` 瘦身后形状（仅设计）

```json
{ "stock_rate": 0.00025, "bond_rate": 0.0001, "min_per_trade": 0 }
```

交易记录侧直接存实际手续费（导入优先，手动算补）。

### 已知判定缺口（增强项，非重建）
- `_get_asset_type` 仅对 SH/SZ 推断 `bond`/`reverse_repo`/`money_fund`，**北交所返回 None**（北交所可转债未识别）。
- ETF（如 `510050`）与股票均返回 None，未区分；费率上 ETF 佣金与股票一致，影响小，但品种统计会漏。
- 这些属"增强/查 bug"，在现有判定器上补，不另起炉灶。

## 三、实施节奏建议（与导入的关系）

- 导入结构+视觉已做完并推送，**下一步用户本地 `pnpm dev` 自测**确认无回归。
- 渠道 + 费率属"账户增强"阶段，**逻辑上在导入流程验证之后**再做：其主价值（格式映射、读实际费用）依赖一个能跑的导入。
- 最小切入点建议：先建「监管费常量 + 费用计算纯函数」（零 UI、零用户负担、立刻提升手动录入准确性），渠道模板放后面。
- 每项作为独立原子提交，与拆分提交严格分开。

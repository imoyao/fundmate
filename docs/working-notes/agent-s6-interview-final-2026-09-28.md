## 2. 12 条压力测试口述稿（每条限时 90 秒）

### 2.1 模型调工具报错 / 参数不符 schema，代码层怎么处理

**口述稿**：三层。第一层，**工具入口不信任模型**：`ToolExecutor.run` 是原子刀，先做服务端权威覆盖，
再按 `TOOLS_METADATA` 做 schema 校验——未知工具、缺必填、未知参数、类型 / enum / pattern 不符
一律抛 `ValueError`，根本不进业务代码。第二层，**错误不崩、结构化回填**：异常被 `run` 捕获成
`{status: 'error'}` 信封拼回 prompt，让模型带着「哪里错了」改一次，最多重试 1 次（模型调用上限
2 次），不给它无限烧钱的机会。第三层，**解析兜底**：连 JSON 都解析失败时不当异常，一律降级为
澄清追问。重试用尽仍失败就落 `error` 态返回用户并写 trace，到此为止，不循环。

**证据**：`tools.py:49`（权威覆盖）、`:284-314`（校验）、`:317-321`（原子刀注释与入口）；
`agent_loop.py:9`（2 次调用上限）、`:555`、`:612-621`（错误回填重试）、`:351`（解析降级澄清）。

### 2.2 下游服务超时怎么办，降级到什么

**口述稿**：分层。**LLM 调用层**：单次请求 60 秒超时；失败先分类——429 / 5xx / 超时 / 连接失败 /
坏响应算瞬态可重试，其余 4xx 立即终止（坏请求重试不会变好，fail fast）；可重试的走指数退避
1.5 / 3 / 6 秒，429 带数值型 Retry-After 就听服务端的、封顶 30 秒，默认总预算 1 次重试。
**降级到什么**：模型侧彻底失败 → 本轮返回错误态，会话状态不损坏——`turn_count` 已落库，失败轮
不烧掉用户预算，下一轮可继续。**工具层**（查库）异常 → 结构化 error 回填重试一次。**绝不降级到
「模型瞎编一个数」**——L1 铁律下宁可报错，不可造数。

**证据**：`llm.py:36-42`（超时 / 重试 / 退避 / Retry-After 封顶）、`:45-67`（失败分类）、
`:70-87`（退避计算）；`agent_loop.py:612-621`（工具重试）、`:313-320`（L1）。

### 2.3 工具返回结果做不做格式校验

**口述稿**：做，但方向和「模型输入」相反——**返回值是代码构造的，不是模型生成的**。每个工具返回
统一 JSON 信封（status / data / message / error_code），`date` 等类型经 `_jsonable` 递归转成
可序列化形态。校验钉在两处：构造点的结构约束，加测试——每工具四例（正常 / 缺必填 / 未知参数 /
enum 越界）。模型侧我**不**校验工具返回，只容错解析模型自己的输出。理由一句话：**校验成本要花在
不可信边界上**——工具返回在进程内、可信；真正不可信的是模型输出与前端回传。

**证据**：`tools.py:76-84`（`_jsonable`）、`:298-314`（契约校验）、`:317-351`（信封构造）；
`agent_loop.py:351`（模型输出容错）；步骤卡 #1 验收（每工具四例）。

### 2.4 模型填错参数（幻觉填 account_id）怎么防

**口述稿**：核心是**权威不来自模型**。参数分两类：身份 / 归属类由服务端从鉴权上下文注入，
`ToolExecutor.run` 里 `apply_server_context` 把权威值覆盖到候选参数的同名键上——模型或前端就算
填了别人的 id，也会被盖成真值，且只覆盖该工具 schema 声明过的键。业务参数靠 schema 卡死：未知
参数直接拒（模型不能「顺手多传一个」），缺必填报错、回填重试。这正是我踩过的 P1 越权坑的修复：
候选参数（前端 `collected_params` + 模型 `tool_params`）**一律不可信**。测试钉死：伪造
`family_id=999` 必须被覆盖成真值。

**证据**：`tools.py:49-65`（权威覆盖）、`:68-73`（family_id 回退口径）、`:298-314`；
`agent_loop.py:604-606`（传入 `server_ctx`）；`backend/tests/domains/test_agent_chat.py:82`。

### 2.5 为什么选状态机而不是线性 Chain

**口述稿**：因为这个 Agent 只有两个动作状态——`ask_clarification` 和 `execute_tool`——外加一个
叙事出口。线性 Chain 表达不了「看上一轮工具结果决定再问还是再查」的回路；但为此上 LangGraph
这类编排框架又过重：它的核心价值（复杂图 / checkpointer 断点恢复 / 人工审批节点 / 多 Agent）
在这里收益为零。所以我用轻量循环做状态路由，**且这是评估后的决策**：仓库里有冻结的 ADR
（decisions.md D19「不引 LangGraph」），roadmap 与代码注释三处留痕。边界也留了：状态数超过 5、
需要持久化工作流或人工审批节点时再评估引入。好处是轮次闸、取消检查点、护栏、trace 都是自己
看得见的显式代码，出问题好定位。

**证据**：`agent_loop.py:5`（注释：不引 LangGraph，用轻量循环做状态路由）；`docs/spec/decisions.md`
D19；`agent_loop.py:418-709`（`_run_agent_impl` 主循环全貌；`run_agent` 392-415 只是取消生命周期薄壳）。

### 2.6 分支执行失败怎么回滚

**口述稿**：先说结论：**工具层天然不需要回滚——6 个工具全部只读**，查库出报告、零业务写入，
失败最多留一条 trace。会话层有两处「回滚」：一是**取消路径**，轮次自增前先快照 `turn_count`，
用户按停止后，进行中的那一轮恢复快照——失败 / 取消不占用用户的轮次预算；二是**压缩路径**，
摘要压缩失败时降级硬截断、原文保底留最近 12 条并打日志，绝不会把会话搞成半写状态。工具失败
走 error-as-observation：错误拼回 prompt 重试一次，不产生任何业务副作用。

**证据**：`tools.py:87`（「全部只读，零裸 SQL」）、`:318`（原子刀）；`agent_loop.py:482-496`
（快照与恢复）、`:172-204`（压缩降级）、`:612-621`（错误回填）。

### 2.7 20 轮后丢最早的关键信息，排查路径

**口述稿**：先定性：正常情况下**不会丢**——「最早的信息」根本不放在滚动窗口里。prompt 分五层：
goal → 关键信息卡（永不压缩的硬事实）→ 滚动摘要 → 最近 3 轮原文 → 已收集参数，每层硬截断，
单轮长度与轮次无关。真要排查走三步：① 查 `agent_trace`，沿 turn 时间轴看哪一轮输入变了；
② 查 `session.messages`——超过 6 轮且超窗才触发压缩，压缩失败会打 `[agent.memory]` 日志并降级
保留最近 12 条；③ 看关键信息卡是否为空——若为空，那不是「丢了」而是抽取根本没发生。背景是我
自审过的 P4：早期 `history` 是前端持有的无界数组，20 轮必爆，S2 改服务端会话落库后，这个风险
在结构上被消掉了。

**证据**：`agent_loop.py:14-19`（分层设计注释）、`:55-62`（各层常量）、`:172-204`（压缩与
日志）、`:517-528`（分层组装）；`backend/app/domains/agent/models.py:21`（`agent_session`）。

### 2.8 记忆分层怎么划，上下文怎么压缩

**口述稿**：按**错误代价**分层：关键信息卡（key_facts——账户、标的这类硬事实，丢了就答错，
**永不压缩**，800 token 上限）→ 滚动摘要（旧轮次压进去，3000 token 上限）→ 最近 3 轮原文
（保留语气与衔接）→ 已收集参数（工具决策用）。闲聊细节丢了可接受，所以进摘要。压缩触发条件是
`turn_count > 6` 且原文超过 8 条，把最旧轮次交给便宜模型压进摘要层（单次增量 500 token 上限）；
失败降级硬截断、保最近 12 条——**有界性优先于完整性**，完整性由摘要层在下次成功压缩时补回。
每层硬上限都是代码里的显式常量，单轮 prompt 有界，压缩前后 token 曲线在 trace 里看得到。

**证据**：`agent_loop.py:55-62`（全部常量与注释）、`:172-204`（触发与降级）、`:517-528`（组装）。

### 2.9 死循环怎么退出

**口述稿**：四道出口。① **轮次硬闸**：`AGENT_MAX_TURNS=10`，计数落库在 `agent_session.turn_count`
——重启不丢、多实例一致；早期它是进程内 dict、换个 `session_id` 就能绕过（我审计出的 P2），
修复就是落库。② **重复追问检测**：同一问法归一化后连续 3 次，强制回标准话术、不进模型——模型
没机会在循环里「越答越起劲」。③ **意图早退**：预测 / 建议类越界输入在进模型前就被拦成标准
回复，零 token、不占轮次。④ **用户停止**：停止按钮 → 服务端取消标志，循环在循环开头、工具
执行后等检查点查时间戳，命中即恢复快照返回 cancelled。兜底：模型输出解析失败一律降级澄清，
不存在「无限重解析」。

**证据**：`guards.py:41`、`:211`；`agent_loop.py:501-509`（轮次闸落库）、`:468-476`（重复
追问）、`:438`、`:452`（输入拦截与路由早退）、`:487-496`、`:557`、`:635`（取消检查点）；
`safety/repeat_tracker.py:27`、`:55`；`cancellation.py:40`。

### 2.10 内容安全怎么做审核校验

**口述稿**：三层确定性护栏 + 一条底线，全部纯函数，**不赌模型自觉**。**输入侧**：意图分类六类
（查询 / 知识 / 预测 / 建议 / 情绪 / 能力自述），预测、建议与能力自述（元问题）类命中确定性句式
直接回标准话术——**不进模型**，顺序即成本：零 token，且模型没有机会在「用户反复追问」下松口；

### 2.11 多轮 token 增长怎么控制，缓存 / 裁剪

**口述稿**：三件事，加一道钱闸。**裁剪**：prompt 五层硬截断，单轮与轮次无关——旧实现整段
`json.dumps` 全部 history、无上界，20 轮必爆；这是结构性修复，不是打补丁。**压缩**：超阈值把
旧轮次压进摘要层，用便宜模型。**缓存**：如实说——我没有做 prompt cache，模型侧命中率取决于
厂商；我控制的是**每轮必付的部分**（历史不再全量重发）。**钱闸**：全站当日 token 预算默认
30 万，超限全站熔断，每次调用的真实 usage 回填计数、逐轮进 trace；再加每分钟限流、连续失败
熔断（防「失败 → 重试 → 烧钱」）、轮次上限 10 兜底。边界我认：限流 / 熔断 / 预算当前是单实例

**证据**：`agent_loop.py:55-62`（裁剪常量）、`:517`（组装）；`guards.py:38`（预算）、

## 3. 两个「我改过的东西」的故事

> 叙事格式借题库 `线上问题案例面试题.md`：**现象 → 定位 → 根因 → 修复 → 防御**。
> 这两个故事是区别于「只跑通正常路径」的人的关键材料（学习计划 §S6 第 4 点）。

### 3.1 P1：越权——「只校验了字段名，没校验取值」

- **现象（发现方式）**：不是线上事故，是**上线前的故障模式自审**。我在给自己的 Agent 做反向
  压力测试时问：「如果哪天工具接受账户 id 会怎样？」
- **定位**：会话状态被我做成**前端持有**（为省服务端状态），每轮前端回传 `session_state`；
  工具执行前 `merged_params = {**collected_params, **tool_params}` 直接合并进工具——而
  `session_state` 只校验字段名与类型，**不校验取值**。前端只要送
  `collected_params = {'account_id': '别人的账户'}`，工具就会照单全收。
- **根因**：**信任边界放错了**——把「省事」置于「前端一切皆不可信」之上。
- **修复（两步，S1 + S2）**：① S1-A 硬前置——`run_agent()` 增收 `server_ctx`（鉴权上下文），
  `ToolExecutor.run` 内 `apply_server_context` 把**服务端权威值覆盖**候选参数同名键，前端 /
  模型的值从此只是候选；② S2 把会话整个收回服务端——`agent_session` 落库，前端只回传
  `session_id`，注入面从参数级收敛到会话级。
- **防御**：测试 `test_chat_p1_server_family_id_wins` 钉死「伪造 `family_id=999` 必被覆盖」；
  schema 校验拒绝未知参数，模型无法「顺手多传」。
- **一句话口径**：「我把 `session_state` 做成前端持有以省服务端状态，但只校验了字段名没校验
  取值——一旦工具接受 `account_id` 就是越权。修法是鉴权上下文从服务端注入，前端回传的参数
  一律视为不可信输入。」
- **证据**：`tools.py:49-65`；`agent_loop.py:604-606`；`backend/tests/domains/test_agent_chat.py:82`；
  审计记录见学习计划 §1.4 P1 行。

### 3.2 P3：多实例击穿——以及「为什么没全修」

- **现象（发现方式）**：同一轮故障模式审计。限流、连续失败熔断、当日 token 预算三道闸全是
  **进程内内存**（`dict + threading.Lock`）；多实例部署下各实例各数各的，防护互相独立 = 击穿。
  同批还审出 P2：轮次计数器的键含前端自选的 `session_id`，换 id 即绕过，且进程内 dict 无 TTL
  泄漏。
- **已修的部分**：① 轮次计数迁到 `agent_session.turn_count` **落库**——重启不丢、多实例一致、
  不可换 id 绕过，顺带消灭内存泄漏；② 每日配额本就落库 `user_usage`（按 user + feature + 日期
  唯一），有退款语义。
- **未修的部分与判断**：per-minute 限流、熔断、token 预算仍是单实例内存态。我没有硬修，而是
  走**数据准入四问**：后端未部署多实例、付费分层未立项——前三问答不出真实使用场景，判定
  **暂缓不实施**（#1739 四问留痕、含触发条件），迁移工作挂 #1294 二期卡。代码注释里明写
  「单实例内存实现，多实例部署后迁移到 Redis/用量表」，不假装它已经是分布式的。
- **教训（面试的落点）**：「不是所有审计发现都要立刻修——判断标准是触发条件是否真实；但每个
  延后项必须**有卡、有触发条件、代码里有注释**，不能沉默。」这恰好也是反过度设计的实践。
- **证据**：`guards.py:6`、`:30`（内存态与迁移注释）、`:43-48`（三把锁与桶）、`:199-211`
  （统一闸与落库轮次上限）；`agent_loop.py:501-509`；#1739 / #1294 卡片。

## 4. 六阶段三段式改稿（规模约束 → 工程决策 → 权衡）

| 阶段 | 规模约束 | 工程决策 | 权衡（含代价） |
|---|---|---|---|

| S3 护栏成本 | 模型可能不听 prompt、合规不能赌它乖、钱要控 | 输入侧零 token 拦截 + 输出逐句过滤 + 重复追问 + 四道成本闸 | 表达受限（标准话术），换护栏行为**确定性可单测**（46 例不触网）；代价是话术必须留安全出口防绕 |
| S4 可观测评估 | 「稳」必须可自证，不能口头保证 | `agent_trace` 全链路落库（脱敏先于落库）+ 30 条评估集确定性评分 | 换来 28/30 → 30/30 的改进闭环；代价是评估集只按最后一轮判定，首轮行为靠 trace 时间轴人工复核 |
| S5 协议层 | 同一份工具生态要进标准客户端，不能养两套 schema | 以 MCP server（stdio）暴露同一份 `TOOLS_METADATA`；`family_id` 只认服务端 env | 换 schema 单源不漂移、最小可用；代价是 SSE/HTTP transport 与远程接入另立卡 |
| S6 面试收口 | 2~4 周面试窗口，话术必须逐句有证据 | 12 条口述稿 + 自介定稿 + 简历 bullet 全部锚 `file:line`，禁编数字 | 换本卡可验收、可复核；代价是开口练习与模拟复盘留给用户（§6） |

# 评估报告：数据导入「统一入口」的必要性与实际难度

## 摘要

数据导入功能目前确实散落在四个入口，且都未进入侧边栏（`showLink:false`），托盘入口又默认隐藏，可发现性存在问题，痛点真实。但「统一入口」这件事团队此前已经识别并拆成了具体 issue：#936 定义了 UX 层的导入引导矩阵（即统一分流入口），#933 定义了前端统一提交层（数据层收敛到 ImportOrchestrator），#1013 已为 E账户导入建模。后端导入管线（ImportOrchestrator / import_hash / 识别器）也已成熟。因此这不是从零开始的高风险任务，而是基础已备、方案已定的收尾与整合工作，技术难度中低；真正的成本集中在产品决策落地（引导矩阵的具体路由）和 #933 的前端收敛改造，以及与在途的 `refactor/split-import-wizard` 分支协调。

## 背景与现状

用户描述的四个导入入口在代码里都属实，且彼此独立可达：

1. 全面盘点（`/inventory`）：唯一的"总入口"感来源，但本身承载投资盘点 + 资产导入 + 记录，单文件 `Inventory.vue` 已超 800 行（债务 #955）。其内嵌三张卡片分别导向持仓快照、交易流水、截图识别。
2. 首页资产简介 / 全局托盘（`/tray` 或 app header 的悬浮「+」）：资产简记快捷买入，复用 `components/QuickEntry/BuyForm.vue`，默认隐藏、需手动唤起。
3. 手动记账（`/asset/investment/manual`）：单笔/批量记录，抽出了 `useQuickEntrySubmit` 壳，但最终仍走 `BuyForm.vue` 内部直写 `createPosition` 的旧逻辑。
4. 投资导入向导（`/asset/investment/import`，当前 `refactor/split-import-wizard` 分支正在拆分为 `index.vue` + `useImportWizard.ts` + `components/`）与即将支持的基金 E账户（`positions` 快照导入，新解析器 issue #1012、向导新模式 #1013）。

关键事实：这四个路由在 `frontend/src/router/index.ts` 里全部 `showLink:false`，即不出现在侧边栏菜单中；用户只能靠透视页卡片、托盘按钮、或已记住的入口进入。这正是 #936 正文里写的"用户可能发现不了入口，或不知道该选哪个（导入持仓还是导入流水）"。

## 已经在途的统一化基础

评估"能不能做"之前，先确认底座是否已具备，结论是目前已具备绝大部分：

后端侧（成熟、已在用）：`ImportOrchestrator` 提供 `preview → confirm → write` 三段式管线；`BaseRecognizer` / `ai_recognizer` 抽象了 OCR 与 AI 识别；`import_hash` + 唯一约束（`#928` 已落地）解决去重；`process_buy_or_deposit` 承载整手校验（`#932` 已修复漂移）。`docs/spec/importer-architecture.md` 已定稿，定义了"统一架构"：注册表 + 编排器 + scenario（持仓快照 `position_import` / 交易流水 `txn_import`），并预留社区解析器接入点。也就是说，数据写入的"统一"在后端已经实现，缺的只是前端入口的汇聚与 UX 分流。

前端侧（在途）：`refactor/split-import-wizard` 分支正在把上帝组件拆成可复用的 `useImportWizard` 组合式函数与子组件，这是后续所有入口复用的前提。新生成的 `ModeSelect.vue` 已为"持仓导入 / 交易导入"模式选择预留位置。

## 「统一入口」已经被拆成具体 issue

这是评估的核心结论：用户担心的"入口混乱"，团队此前已通过讨论转化为可执行的 issue，且方案清晰：

- #936「导入引导矩阵」：这就是用户想要的 UX 层统一入口。它把四个入口按"用户状态 → 引导去向 → 入口 → 层级"做成矩阵，显式区分持仓快照（落 `positions`、无流水、解锁涨跌）与交易流水（生成持仓+流水、支撑 XIRR/对账）两个层级，并要求所有入口共用 #933 的统一提交层。它不主张新建一个孤立的"导入中心页"，而是把现有四个入口编排成一张清晰的分流网。
- #933「前端统一提交层」：针对数据层"双轨直写"问题——手动记账与资产简记都未走 ImportOrchestrator，而是各自在 `BuyForm.vue` 内直写 `createPosition`，导致与后端规则漂移。目标是把两者收敛到同一个前端统一提交层，最终四条入口都汇入 `ImportOrchestrator`。这是"统一"在数据层最实在的一步，也是 #934（托盘截图导入）、#936（引导矩阵）的共同前置依赖。
- #934「资产简记托盘增加截图导入入口」：托盘接 `txn_import` scenario，复用 OCR + 二次校验，明确"依赖 #933 统一提交层"。
- #1012 / #1013：E账户持仓解析器 + 向导新增「持仓导入」模式，明确"须在 wizard 拆分完成后或并行但独立落地"，复用 #928 去重、走 `positions` upsert。

换言之，要做的事在 issue 系统里已经编号、已经关联、已经指定了依赖顺序。现在缺的不是"要不要做 / 怎么做"的判断，而是执行排期与跨分支协调。

## 必要性评估

必要性是真实且已被内部确认的，但需注意一个微妙点：痛点是"入口散落、可发现性差"，最优解未必是"再开一个顶层的独立导入中心页"。#936 的引导矩阵方案已经给出更稳妥的方向——在既有四个入口之上做显式分流与可发现性增强，而不是新增第五个表面加剧散落。如果另起一个独立的大入口页，反而可能变成"入口之上的入口"，与"减少散落"的初衷相悖。

因此建议把"统一入口"理解为两层：UX 层的分流与可发现性（#936，强烈建议做），以及数据层的单点提交（#933，强烈建议做）。这两层合起来就是用户想要的"统一入口 + 清晰流程"，且都不需要推倒重来。

## 实际难度评估

技术实现难度：中低。理由：（1）路由低成本——前端路由由 `src/router/utils.ts` 的 `import.meta.glob` 自动注册，新增一个聚合/引导页几乎零配置成本，菜单接入若用 `component` 路由（非 `menu`）也能自动进入侧边栏；（2）数据底座已成熟，#933 的改造是"移除 `BuyForm.vue`/`SellForm.vue` 内直写、改调统一提交层"，范围明确、有 #932 的整手校验回归测试先例可循；（3）E账户解析器是独立增量，唯一阻塞是真实样本文件（已有 #930「东方财富等缺失券商的样本征集机制」兜底）。

主要成本与风险集中在三处：其一，产品决策——引导矩阵的具体路由（空状态大按钮指向哪、托盘「+」是否升级为总入口）需要拍板，但 #936 已给出默认方案，决策成本已摊销；其二，#933 是牵涉手动记账与托盘两条高频路径的收敛改造，需配套回归测试以防校验漂移，属于"范围明确但需谨慎"的中等工作量；其三，协调风险——E账户新模式（#1013）和引导矩阵都依赖 wizard 拆分分支，须在该分支合入前后排好顺序，避免并行冲突。

综合判断：整体工作量可按"先 #933 收敛数据层 → 再 #936 编排 UX 分流 → 并行推进 #1013 E账户解析器"的序列推进，均为 OPEN 且方案明确的事项，无未知技术阻塞。

## 建议与排期

最小可行方案不是新建孤立入口页，而是落地已设计的引导矩阵 + 前端统一提交层，并把 E账户作为"持仓导入"模式接入既有向导：

1. 先完成 `refactor/split-import-wizard` 拆分，交付可复用的 `useImportWizard`（前置，避免后续返工）。
2. 落地 #933：抽离前端统一提交层，手动记账与资产简记改走 ImportOrchestrator，补回归测试。
3. 落地 #936：在空状态、托盘「+」、简记弹窗底部、全面盘点卡片之间建立显式分流，区分持仓快照与交易流水层级。
4. 并行落地 #1012 / #1013：E账户解析器 + 向导「持仓导入」模式，复用 #928 去重。
5. 视效果决定是否需要额外的聚合页；若引导矩阵仍不足以提升可发现性，再评估顶层入口页（届时会是低成本增量，因为底座已统一）。

## 竞品对照：从用户提供的截图提取的关键洞察

用户提供了两张竞品/行业参考截图，信息密度很高，直接印证了"统一入口"的必要性，并揭示了行业已形成的两种主流模式。

### 截图 1：全平台基金资产分析攻略（公众号长图文 / 第三方工具教程）

这是一篇面向基金投资者的"资产分析工具使用教程"，其流程设计暴露了当前行业的通用痛点与做法：

**痛点确认**（与多多贝用户完全一致）：教程开篇列出三个烦恼——持仓分散多个平台难汇总、不知道整体盈亏、不清楚资产配置是否健康。这说明"入口散落、数据分散"不是多多贝独有的问题，而是整个基金投资人群的共性痛点。

**E 账户作为统一数据源**：教程以中国结算基金 E 账户为起点——用户先从 E 账户导出 Excel/CSV，再上传到第三方分析平台。这恰好是 #1012/#1013 的业务背景：E 账户是唯一能跨平台汇总公募基金持仓的官方数据源，任何想做"全平台资产透视"的产品都必须围绕它构建导入能力。

**三步流程**（值得多多贝参考）：
1. 导出 E 账户资产表 → 2. 上传至分析平台（AI 自动识别字段）→ 3. 智能诊断（配置建议、集中度风险、重复基金检测）。这个流程的本质就是"统一文件上传入口 + 自动识别 + 结构化诊断"，与多多贝的 `ImportOrchestrator` 管线高度同构。

**关键差异点**：该教程指向的是一个"一次性分析工具"（用完即走），而多多贝是"持续记账平台"。这意味着多多贝的统一入口不仅要解决"首次导入"，还要解决"后续增量更新/对账/手动补录"的持续场景——这正是 #936 引导矩阵区分"持仓快照"与"交易流水"两个层级的理由。

### 截图 2：金太阳 APP「睿算」全账户基金诊断服务（券商产品公告）

这是国信证券金太阳 APP 上线"睿算"全账户基金诊断功能的产品公告，代表了券商侧的做法：

**核心模式：授权聚合而非文件导入**。"睿算"不走"用户导出文件 → 上传解析"路线，而是让用户在 APP 内授权 → 系统通过 API 对接各销售渠道（支付宝、天天基金、银行 App 等）自动拉取持仓数据。这是最流畅的用户体验，但前提是券商有牌照和 API 接入能力。

**四块诊断面板**（可作为多多贝 Pro 功能的参照）：账户总览（全平台汇总 + 地图分布）、行情追踪（涨跌排行 + 收益率曲线）、行业/标的分析（配置热力图 + 重仓股穿透）、基金优选（基于持仓的替代品推荐）。这些面板的数据需求恰好对应 #994（Pro 高级洞察）和 E账户去中心化方案里的 P1 组合体检。

**操作路径清晰**：金太阳 APP → 理财 →「睿算」→ 全账户诊断 → 授权登录各平台。路径短、层级浅、每步有明确按钮。这对多多贝的启示是：无论最终选择哪种入口形态，用户到达核心功能的点击次数不应超过 3 次。

**账单服务模块**：支持历史交易流水对账，说明"持仓快照 + 交易流水双轨"的需求在券商产品里同样存在——进一步佐证了 importer-architecture 里 `position_import` / `txn_import` 双 scenario 分层的合理性。

### 对多多贝统一入口设计的具体启示

综合两张截图，可以提炼出以下可操作的洞察：

1. **E 账户导入是必争之地，且有时间窗口**。截图 1 的教程已经把"E 账户导出 → 上传分析"流程教育给了大量基金投资者；截图 2 的券商产品也在抢占"全账户诊断"心智。多多贝若能在 #1012/#1013 及时落地 E 账户导入，就能承接这批已被教育的用户。

2. **统一入口的竞品参照形态有两种**：一种是截图 1 的"文件上传向导"模式（适合多多贝当前技术栈），另一种是截图 2 的"授权聚合"模式（长期目标但需牌照/API）。前者是当下可执行的，后者可作为 P2 路线图储备。

3. **引导矩阵应覆盖截图 1 的三步流程**：#936 的分流矩阵如果能把"导出 → 上传 → 诊断"映射为多多贝内的"E 账户导出指引 → 文件上传/OCR/手动 → 组合体检报告"，就与用户已被教育的认知模型完全对齐，降低学习成本。

4. **诊断面板可作为 Pro 差异化**：截图 2 的四块诊断面板（集中度、重复基金、费率、配置评分）与 #994/#1000 的 Pro 高级洞察高度重合。统一入口不仅是"导入数据的入口"，也可以是"触发 Pro 诊断的入口"——导入完成后直接展示免费版摘要 + Pro 解锁完整诊断，形成自然的付费转化路径（呼应 #826 付费分层）。

## 局限

本次调研初始阶段的微信公众号文章检索返回的是与记账 App 导入设计无关的本地资讯噪声（如宁海本地新闻），未获得可用的竞品实践对照；但用户后续提供的两张竞品截图（全平台基金资产分析攻略 + 金太阳「睿算」产品公告）弥补了这一缺口，提供了高价值的行业参照。E账户导入的端到端验证仍受限于真实导出样本文件是否到位（#930）。

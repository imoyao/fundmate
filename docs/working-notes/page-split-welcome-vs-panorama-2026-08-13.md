# 投资概览 vs 资产总览 · 页面分工决策（2026-08-13）

## 背景

`welcome/index.vue`（投资概览 / 「家庭资产看板」首屏）与 `AssetPanorama.vue`（资产总览 / 「资产配置」）长期存在概念混淆：五笔钱（Allocation）、投资目标（Portfolio/Objective）、心理账户被搅在一起，且「资产构成分布」环形图错接成品种/市场分布、心理账户卡片用的是 mock 五笔钱名字。本轮通过核对 GitHub Issue #859、Discussion #152、后端 `portfolios` 模型与 `docs/spec/data-model.md` §5.11，把概念与两页分工理清。

## 概念裁定（详见 concepts.md）

- **投资目标 ≠ 独立实体**：原 `objectives` 表 / `position_objectives` 多对多方案已否决且未落地；"投资目标"语义降级并入 `Portfolio.purpose` 字段。Objective 与 Allocation 平行，不存在"Objective 是五笔钱的细化"的嵌套。
- **五笔钱（Allocation）= 客观风险分层**：系统按产品风险等级+期限自动归类（活钱/稳健底仓/长期增值/高风险博弈/保险保障），不可自定义。
- **心理账户 / Portfolio（投资目标）= 主观目标**：用户自建的人生目标（养老金/教育/买房），经 `Portfolio.purpose` 承载。

## 两页分工（最终结论）

| 页面 | 定位 | 承载概念 | 性质 |
|---|---|---|---|
| 投资概览（welcome） | 我想过什么样的人生？设了什么目标？离目标多远？ | 心理账户/Portfolio（投资目标）+ 收益·XIRR·市场温度·财务健康 | **理想 / 目标 + 表现进度** |
| 资产总览（panorama） | 为了目标，怎么规划钱、走哪条路径？ | 五笔钱（配置目标）、产品类型、账户、资产端/负债端 | **生活 / 方法（composition 拆解）** |

**关键共识**：分页原则从最初的"客观 vs 主观"修正为 **"拆解（composition）vs 表现+目标"**。用户的大白话比喻更准确——投资概览是"理想"（想过的人生、设的目标、离目标多远），资产总览是"生活和方法"（怎么把钱铺成通往目标的路）。**五笔钱是"方法/路径"（按风险分层支撑目标），所以归资产总览；心理账户是"理想"（目标本身），所以归投资概览**，两者不再打架。

## 落地决策清单（待开工）

1. **welcome 顶部「家庭资产看板」大卡片保留**（净资产快照：总资产/负债/净资产/盈亏 + 本月本年变动）。它与 panorama 的数据重复通过"视角不同"消弭：welcome 回答"我有多少钱、今天涨没涨"，panorama 回答"结构健不健康"。
2. **welcome「资产构成分布」环形图（品种/市场分布）迁至 panorama**，welcome 不再展示任何结构图。
3. **welcome「心理账户」卡片**：保留名字（"投资目标"太干、不搭主题），数据源从 `overview.ts` 的 `mockPsychAccount` 换成真实 `Portfolio`（按 `purpose` 聚合），并加一句小提示："按人生目标把钱分桶，帮你看清每笔钱在为什么而存"。
4. **panorama 中部加并排双环**：左「五笔钱配置（配置目标）」、右「品种构成（股票/基金/房产/贵金属，从 welcome 迁来）」，均用现成数据（`allocation_distribution` / `market_distribution`）画 donut。
5. **panorama 四个维度（资产端/负债端/产品类型/账户/配置目标）各加注释条**，其中"配置目标"标签写明"= 五笔钱"，消除"配置目标到底是不是五笔钱"的模糊。

## 补记（2026-10-15，#2150）：第三页「复盘」的定位与去重

前两节确立的是 welcome ↔ panorama 的二人转。本文写于 2026-08：
**当时 `/analysis`（智能分析）还没有真实数据**，所以没进分工表。

### 一句话定位（#2150 拍板）

> **只看「时间维度上的表现」，不看资产结构。**

三页的分工至此闭合（沿用本文「拆解（composition）vs 表现 + 目标」的原口径，补第三项）：

| 页面 | 回答的问题 | 形态 |
|---|---|---|
| 投资概览（welcome） | 我有多少钱？离目标多远？ | **结论**（净值快照 + XIRR + 温度 + 日历） |
| 资产总览（panorama） | 钱是**怎么铺开**的？结构健不健康？ | **拆解**（瀑布图 + 桑基 + 多维视图） |
| **复盘（/analysis，原智能分析）** | 我的钱**经历了什么**？ | **时间序列**（净值走势 + 收益/现金流） |

### 被删的四块：与 panorama 同字段、同接口、同算法

| 删除项 | panorama 的对应实现 | 引擎事实 |
|---|---|---|
| 总资产 + 环比/同比 | `OverviewSummaryCard.vue` 左卡 | 同 `getSnapshots()` 取 `monthly/yearly_change_pct` |
| 大类占比卡片网格 | `CategoryBalanceTable.vue` | **公式逐字相同**：`(value/total)*100` |
| `category_distribution` 环形图 | 瀑布图 + 大类明细表 | 同字段 |
| 「近期持仓表现」表 | `DetailGroupList.vue` | 同接口同维度：`getPositionGroups("type")` |

### 判定依据不是「我觉得重复」，是本文已有的裁决

`panorama/index.vue:66-72` 删 `AssetInsightPanel` 时写的理由是
「同一份数据在首屏重复第二遍」——**同一条裁决当时没有应用到 /analysis 上**。
#2150 做的就是把它补齐。所以本文开头那句
「先问能不能去掉，再问怎么命名」，在这里同样是判据。

### 保留的独占项

- **资产净值走势**：welcome 已明确让出（`WelcomeAssetBoard.vue:131-138`
  「净值曲线归复盘页规划」），panorama 用 `getSnapshots()` **只取最新一条做环比/同比、
  不画曲线**。⇒ 全站唯一的净值曲线出口，是这一页存在的理由。
- 收益概览（XIRR 四数）与货基收益：与 welcome 的 XIRR **同口径同开关**
  （#2153 已对齐），差异不在数值而在**纵深**——welcome 给一个结论数字，
  本页给结论 + 口径切换 + 现金流笔数。

### 命名：为什么叫「复盘」

原名的「智能」二字**没有 AI 能力支撑**（页面全是有数据源的真实计算），
且暗示「比别人多算了点什么」。定位既然是「时间维度的表现」，中文对应的词就是「复盘」。

⚠️ **路由 path 保持 `/analysis` 不动**——它是外部可达 URL 与既有书签的锚点，
改名属另一件事（要做须配 301/别名），不在 #2150 范围。

### 顺带修掉的一个真 bug：侧边栏有两个「智能分析」

`asset.ts` 里 `/analysis` 被**声明了两次**：#2152 把该页从「投资管理」移出时
只在新位置加了一份、**旧的那份没删**。两份 `path`/`name` 全同，而
`router/utils.ts` 的 `filterTree` **不按 name 去重** ⇒ 侧边栏渲染出两个同名条目。
`routeRankGuard.spec.ts` 的 `toEqual` 数组全等本来有能力咬住它，只是没人当回事。
本次删除重复声明，并补了一条**与排序无关、只管重复**的判据（含回退探针）。

### 留给后续

- 幽灵重复告警（`GhostDuplicateBanner`）仍挂在本页，属**对账**范畴
  （后端注释自带定性：`summary_service.py:1045-1066`）。待对账工作台开出
  「跨账本重复交易」域后迁走（#2151）。域 D 存在之前留着，是「异常要看得见」的权宜。

  **该用例一直是红的**。本次按现实补齐（补账，不是放宽）。

### 守门

## 补记（2026-10-25）：panorama 的「资产大类」从**瀑布图**改为**构成柱状图**

> 本文正文（尤其上方 `:101` 那张分工表里的「瀑布图」）是 2026-08-13 ~ 10-15 的历史记录，
> **不回改**；口径变更以本补记为准。

### 触发

用户反馈右卡「资产大类」图「中间几根柱子悬空、看不懂」。先按「0 轴没对齐」排查，
SSR 真渲染证明 grid 底边 = `y(0)` = 柱底，**几何是精确对齐的**——所以不是画错了，
而是**这张图被放错了位置**。

### 裁定：构成 ≠ 过程

这张卡的标题是「资产大类」，它要回答「我有哪些资产、各多少」——**构成**问题，靠**柱长**比较。
瀑布图回答的是另一个问题：「从一个起点经若干笔增减落到终点」，柱长 = 变动量、柱位 = 累计水位。
用在这里有两处结构性误读：

1. **位置取代长度**：投资理财（51.79 万）比流动资金（99.38 万）柱子**短**、位置却**更高**，
   第一眼被读成「更大」；
2. **同视口重复**：左卡已给出总资产 / 总负债 / 净资产三个数字，右卡再画一遍「净资产怎么来的」——
   正是本文 `:83` 那句「同一份数据在一个视口里出现两次，先问能不能去掉」要治的形态。

定稿：**只画资产端 4 个大类，一律从 0 起、按金额降序**；负债与净资产留在左卡。

### 为什么瀑布图在这个系统里暂时无处安放（数据层证据）

要让瀑布有独立价值，只能讲**跨期归因**（上月净资产 → 资产增减 → 负债增减 → 本月净资产）。
查了数据层，走不通：

| 依据 | 事实 |
|---|---|
| `backend/app/domains/summary/models.py:65-67` | `asset_snapshots` 只有 `total_assets` / `total_liabilities` / `net_worth` 三个总数，**无大类明细** |
| 同文件 `:30-37`（D62） | `snapshot_date` 只是**标签**，取数链无日期过滤、**禁止回填** ⇒ 拿它拼历史分类序列等于伪造 |
| 同文件 `:124` | `PnlDailySnapshot.net_worth_cents` 是**持仓口径**，不含负债分解 |

⇒ 静态瀑布只讲「净资产怎么来」＝左卡三个数字已说完；跨期瀑布没有分类历史数据。
将来真做归因桥（月度净资产变化 / 收益归因）时按新数据集**重写** bars 构造，
不复用旧代码（旧实现 `buildWaterfallBars(distributions)` 把「负债」「净资产」两个终点
硬编码在其中，输入形态完全不同）。

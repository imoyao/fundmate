## 0. 结论先行

1. **你缺的不是 Agent 名词，是一条能自证的链路。** 面试官那篇帖子的核心不是知识点，是「**有没有被生产环境验证过**」。你现在能讲的全是设计文档，讲不出「我调过、它坏过、我修过」。
2. **起点远比你以为的好。** `ai_recognizer/` 已经实现：双动作主循环（`ask_clarification` / `execute_tool`）、模型 JSON 输出容错解析、工具失败 error-as-observation 重试、前端持有会话状态 + 白名单防篡改、跨请求轮次上限、限流/熔断/token 预算四道防护。**这些是你已经写过但自己没意识到可以拿去讲的东西。**
3. **但它是「未接线的死代码」**：`run_agent()` 在生产代码里搜不到任何调用方（§1.2），工具表只有 1 个 `_demo_get_portfolio_performance` 返回 `None`（`tools.py:34-43`），前端 `frontend/src` 搜不到「精灵」二字。**这是最高 ROI 的入口：通电成本 1~2 天，收益 = 从 0 到 1 的"跑起来"。**
4. **顺手审出 5 个真问题**（§1.4），其中 2 个是**潜在越权/绕过**。这些不是瑕疵，是面试里最值钱的素材——「我审计了自己写的 Agent，发现 4 个在生产会出事的地方」比背十条最佳实践强得多。
5. **不做 RAG。** 我们是**结构化领域工具型 Agent**，不是文档问答。诚实定位 + 讲清「为什么我不做 RAG」本身就是加分项（§2）。
6. **明确不抄 gitee 那个仓库的选型**（Celery / MySQL 16 分片 / Redis / One API / 10 万 DAU 指标）。它是**简历话术模板**，不是技术方案参考。照抄会把 fundmate 压死，而且一追问规模约束就露馅（§3）。
7. **总量估算 5.5 人日可讲**，含「只学不做」部分。可裁剪顺序见 §9。

## 2. 定位纠偏：我们是「工具型 Agent」，不是「RAG Agent」

面试帖子的四维度里，**数据层 = 知识库清洗/切分**。这是它的场景（文档问答），不是我们的。**不要为了对答案硬造一个 RAG。**

我们的真实定位，以及对应的四维度答法：

| 帖子维度 | 我们的真实对应 | 我们凭什么讲 |
|---|---|---|
| 数据层 | **不是知识库，是结构化金融数据 + 领域工具链**：33 个服务模块 + 8 个子包 + 23 个业务域，全部是「可被 LLM 调用的确定性计算」 | `backend/app/services/`、`backend/app/domains/` |
| 工具层 | 工具 = 只读 + 数值计算；模型只叙事 | §1.1 三行 + 阶段 1 |
| 记忆层 | 现在是「前端持有 + 无压缩」，阶段 2 改成后端权威 + 分层 | `agent_loop.py:44-91` |
| 工程层 | 四道成本防护 + 轮次上限 + 数值不落模型 | §1.1 |

**「为什么不做 RAG」本身就是一道加分题**，答法：

> 面试官：「你们知识库怎么切分？」
> 你：「我们没做 RAG，这是刻意决策。Agent 面对的问题 90% 是『我的持仓半年表现怎么样』——答案在结构化账本里，不在文档里。RAG 检索出来的是片段，还得再算一遍才能给数；我直接暴露一个 `get_portfolio_performance` 工具，数值由 `pyxirr` 算完返回 4 个标量。**RAG 解决"找不到知识"，工具调用解决"算不对数"，我们缺的是后者。** 唯一适合 RAG 的是术语/帮助文档，我评估过：用户提问分布里 <5%，且用关键词匹配就能覆盖，所以阶段 5 只做了一个 30 行的极简检索，不引向量库。」

这段回答同时展示了：**你懂 RAG / 你有数据判断 / 你克制**。

## 3. 参考项目怎么用：能抄的与不能抄的

> 参考对象：`https://gitee.com/ai_black_ma/ai`（AI Agent Service，FastAPI + MySQL 16 分片 + Redis + Celery，号称 10 万 DAU / 2.1k QPS / 单用户 ￥0.021/月）

| 它的做法 | 对我们的判断 | 结论 |
|---|---|---|
| **分层：routers / services / db + core** | 我们已有 `domains/{models,schemas,views}` + `services/` 分层，且约束更严（双库硬规则） | ✅ **已在同一水位**，无需抄 |
| **工具调用（计算器 / 时间查询）** | 形态 = 「工具注册表 + 参数 schema + 执行器」，**我们已实现且更完整**（多了 enum/pattern 校验） | ✅ 形态一致，抄的是"它证明了这条路"，不是代码 |
| **对话历史管理** | 它是 MySQL 分片 + Redis 缓存。我们**借鉴思路（会话要持久化），但实现用 DB 表** | ⚠️ **部分借鉴** |
| **Celery + Redis Broker 异步任务** | 我们已有 APScheduler 进程内调度（`daily_scheduler.py`）+ 同步 CLI。Agent 对话是**请求-响应式**，无长耗时推理，引入 Celery 等于为 0 收益增加一个 broker 运维面 | ❌ **不抄** |
| **MySQL 16 分片表** | 我们本地 SQLite / 生产 Turso + Supabase。个人工具规模，分片是纯负债 | ❌ **不抄** |
| **Redis 缓存（MessagePack 压缩、85% 命中）** | 我们当前无 Redis 依赖，且 `guards.py` 迁 DB 表即可满足（我们不是纯多实例 Serverless 压力） | ❌ **不抄**（先落 DB，真到瓶颈再评估云 Redis） |
| **QPS 2000+ / 日均 10 万 DAU / P99 50ms / 可用性 99.9%** | **我们没有这些流量。禁止把这些数字写进任何材料。** 一追问「压测怎么做的、瓶颈在哪」立刻崩 | ❌❌ **绝对不用** |
| **`docs/` 下技术选型文档齐备（架构演进/选型指南/决策手册）** | 我们 `docs/spec/` 更成熟 | ✅ **这正是我们的优势，保持** |

**一句话定性：那个仓库是「简历项目话术模板」，不是「技术方案参考」。** 它的价值是告诉你面试官想听哪些词汇（工具爆炸、Schema 归一化、幂等、熔断、trace），**不是**它的选型。我们要做的是：**用同一套词，描述我们真实的、规模小但决策链完整的系统。**

## 5. 分阶段详设

### S1｜工具层：让 Agent 通电（最高 ROI，务必先做）

**目标**：从「有骨架没通电」到「一句自然语言 → 真实持仓数据 + 自然语言总结，全链路可 curl 可截图」。

#### 学（理论，约 45 分钟，可只讨论）

1. **Function Calling 的循环本质**：推理 → 输出 `tool_calls` → 本地执行 → 结果回填 → 再推理。**它是无状态同步循环**，每轮 schema 都占 context。
2. **JSON Schema 严格模式**：`additionalProperties: false`、`enum`、`pattern` 是**降低模型乱填率最便宜的手段**。
3. **error-as-observation vs 静默失败**：把错误**当观测喂回模型**让它改参重试；静默失败 = 模型永远不知道自己做错了。
4. **超时与退避**：指数退避（1s → 3s → 放弃）；区分「可重试（超时/5xx）」与「不可重试（4xx/参数错）」。
5. **幂等适用边界**（这题的答案在 fundmate 特别好）：*「读操作天然幂等，不需要幂等 key；写操作我们不交给 Agent——它只生成候选行，写入必须走 importer + 用户逐行确认（L0 硬约束）。所以幂等问题在我们这儿被架构消解了，而不是靠 key 兜住。」*

#### 做（落地清单）

1. **新建领域 `backend/app/domains/agent/`**（`views.py` + `schemas.py`），端点 `POST /api/agent/chat`。
   - 请求：`{message, session_id, session_state?}`
   - 响应：`{type: clarify|result|error, content, data?, session_state}`
   - **必须挂 `guards.assert_available(user_id)` 前置闸**（现成，勿绕过）。
2. **修 P1（越权）—— 本阶段硬前置**：`user_id` 与 `ledger_id` 一律由服务端从鉴权上下文注入，**前端回传的 `collected_params` 只作为「候选值」**，工具执行前必须与服务端上下文合并并覆盖（禁止前端值直接进工具）。这是本阶段唯一不可裁的项。
3. **工具扩容到 5 个，全部只读、全部复用现有 service**（**禁止在新工具里写 SQL**）：

   | 工具名 | 复用 | 返回（**只回标量，绝不回全量序列**） |
   |---|---|---|
   | `get_holdings_overview` | `position_service` / `summary_service` | 总市值、持仓数、当日盈亏、累计盈亏 |
   | `get_portfolio_performance`（**替换 demo**） | `services/performance/`（XIRR） | 年化、区间收益、最大回撤、波动率 |
   | `get_fund_nav` | `nav_service` | 最新净值、日涨跌、近 N 日涨跌 |
   | `get_market_temperature` | `services/thermometer/` | 温度值、档位、分位 |
   | `get_watchlist_performance` | `watchlist_service` | 自选数、区间涨跌、最强/最弱 |

4. **工具元数据补全**：`description` 必须写清「**何时用、何时不用**」（例：`get_fund_nav` 描述里写明「用户问单只基金净值时用；问整体持仓表现请用 `get_portfolio_performance`」）。**工具描述是模型选对工具的第一道防线**，面试会问。
5. **超时降级（修 P5）**：工具内上游调用失败 → 指数退避重试 2 次（1s/3s）→ 仍失败返回结构化 error → 由 AgentLoop 拼回 prompt。**分层要清楚：退避重试在工具内，语义重试（改参数）在 AgentLoop。** 现实现只有后者。
6. **前端最小入口**：`frontend/src/views/agent/` 对话页 + `frontend/src/api/agent.ts`。识别出候选行的场景**复用 importer 的逐行确认组件**（不新建写入路径）。
7. **测试**：每个工具「正常 / 缺必填 / 未知参数 / enum 越界」四例；一条端到端 mock 对话（mock 掉 `call_llm`）。

#### 面试考点与话术

| 追问 | 答法 |
|---|---|
| 模型调工具报错、参数不符 schema 怎么处理？ | **三段**：① 前置 schema 校验（必填/未知键/enum/pattern，`tools.py:75-95`）② 执行异常兜底返回结构化 error，绝不让循环崩（`tools.py:111`）③ 错误当 observation 拼回 prompt 让模型改参重试，最多 1 次，再失败转追问（`agent_loop.py:171-207`）。**超时另走指数退避**——语义重试和传输重试是两件事。 |
| 下游服务超时怎么办？ | 工具内向数据源请求加退避重试（1s/3s）+ 超时上限；仍失败**降级**：返回「该指标暂不可用」而非编一个数——**我们的降级底线是"宁可不答，不可错答"**，这是金融场景与聊天场景的根本差别。 |
| 工具返回结果做不做格式校验？ | 做两层：返回后由 AgentLoop 判 `status`，且 JSON 序列化失败有回退（`agent_loop.py:213-220`）；另外空数据（`None`/`[]`/`{}`）会被替换为占位提示，避免把字面 `null` 喂进 prompt。 |
| 为什么不做写操作？幂等呢？ | 见上「幂等适用边界」。**Agent 只有读权限，写路径被架构切断**。 |

#### 验收

- ✅ `curl` 一条「我最近半年表现怎么样」拿到真实数值，且**每个数字都能溯源到某个 service 函数**。
- ✅ 5 个工具的参数校验单测全绿（正例 + 3 类反例）。
- ✅ 故意把数据源打死，Agent 返回「指标暂不可用」而非编造数值（**这条是面试现场可演示的**）。
- ✅ 前端截图：对话 → 追问补参 → 出结果 三态。

#### 可裁剪
：前端页面可降级为「仅后端 + curl + 单测」（省 0.5 d），但**面试演示价值会掉一半**，建议不裁。

### S2｜记忆层：让多轮不丢信息

**目标**：解决 P2/P4，把「前端权威」改为「后端权威 + 分层记忆」。

#### 学（约 45 分钟）

- **记忆分层**：会话内短期（原始轮次）/ 会话内长期（滚动摘要）/ 跨会话用户画像（可选，**我们不做，说明理由**）。
- **上下文压缩**：滚动摘要（把最早 K 轮压成一段）+ 保留最近 N 轮原文。
- **关键信息优先召回**：维护「关键信息卡」（当前追问的标的/账户/时间范围），**永远进 prompt 且永不压缩**——这是「丢失最早关键信息」的正解：不是靠更大的窗口，是靠**把关键信息从历史里提出来单独持有**。
- **窗口预算**：给 summary / 关键卡 / 最近轮次 / 工具结果各分配 token 上限。

#### 做

1. **会话落库**：新表 `agent_session`（`session_id`(服务端生成 uuid)、`user_id`、`goal`、`summary`、`key_facts`(JSON)、`turn_count`、`updated_at`）。**前端只回传 `session_id`，不再回传状态**（这同时修掉 P1 与 P4 的前端注入面）。
2. **压缩触发**：`turn_count > 6` 时把最旧轮次用便宜模型（现用 `doubao-seed-2-0-mini`）压成摘要，追加进 `summary`。
3. **prompt 组装改造**：`[L1 铁律] + [summary] + [key_facts] + [最近 3 轮原文] + [本轮指令]`，替换现在的 `json.dumps(全部 history)`（`agent_loop.py:160-166`）。
4. **修 P2**：`session_id` 改服务端生成；轮次计数入表（`agent_session.turn_count`），顺带解决内存泄漏与多实例不一致。

#### 面试考点与话术

> **Q：用户对话到第 20 轮，Agent 丢失了最早的关键信息，排查路径是什么？**
> **这就是我踩过的坑。** 我的排查顺序是三层：
> ① **先排除"根本没存"**——原来我把会话状态交给前端持有（省服务端状态），前端只回传最近几轮，最早的天然没了。**根因不是模型记不住，是架构上就没存。**
> ② **再确认"存了但没进 prompt"**——改成后端持有后，我把全量 history 拼进 prompt，20 轮后 token 爆了，我加了截断，结果**从"丢最早"变成"丢中间"**——截断是无差别丢信息。
> ③ **最后才谈压缩策略**——正解是分层：把关键信息（当前问的标的/账户/时间范围）**从历史里提出来，做成永不压缩的「关键信息卡」单独持有**；历史轮次压成滚动摘要承载上下文感；原文只留最近 3 轮。
> **一句话结论：多轮信息损耗通常不是模型问题，是"状态放在哪 + 什么该留原文、什么该压摘要"的设计问题。**

#### 验收
- ✅ 20 轮后仍能正确回答第 1 轮提到的标的（自动化用例）。
- ✅ 单轮 prompt token 数随轮次增长**收敛**（有上界），而不是线性上涨。
- ✅ 前端篡改 `session_id` 后无法读到他人会话（越权用例）。

#### 投入
1 d。**可裁剪为 0.5 d**：只做会话落库 + 截断改分层，不做摘要（摘要只影响 >10 轮场景）。

### S3｜护栏与成本：不乱说、不烧钱

**目标**：落地已定型的设计（`agent-guardrail-layer-design-2026-08-17.md` §6/§7/§8），把「合规」变成可演示的能力。

#### 学（约 40 分钟）

- **内容安全分层**：输入侧拦截（最省 token）/ prompt 约束 / 输出侧过滤（最硬，兜底）。**顺序的意义是成本**：能在输入侧拦掉的，不要花钱让模型生成再拦。
- **域内合规**：投资场景的红线是**预测涨跌、买卖时点、荐股、收益承诺**——比通用「违规内容」更具体，也更可规则化。
- **配额与限流的部署现实**：进程内计数器在多实例 Serverless 下必然击穿（`guards.py:5-6` 自己写了这条债）。

#### 做

1. **新建 `ai_recognizer/safety/`**：`intent_guard.py`（输入侧意图 A/B/D/E）、`output_filter.py`（L3 输出侧 R1~R10 + 白名单豁免 + 免责模板）、`repeat_tracker.py`（同一问题归一化后 N 次追问 → 标准话术）。**三者都是无状态纯函数，先不接模型即可单测**（这是设计文档已定型的，直接照做）。
2. **L1 铁律注入** system prompt：数据真实性 + can/cannot 清单（"工具先行、数据为真、严禁编造""宁可说不知道"）。
3. **per-user token 配额迁表**：复用 `user_usage` 表的模式（`domains/usage/models.py`），新建 per-user token 累计；**禁止进程内 dict**（这是 #1294 的技术债，本阶段顺手还掉）。
4. **成本可视化**：每轮记录 token 到 trace 表，出一个「本周 AI 花费」读数。

#### 面试考点与话术

> **Q：Agent 行为跑偏怎么兜底？死循环？内容安全？成本？**
> 我的兜底是**四层纵深，每层解决不同的失败模式**：
> - **输入侧**：意图分类 + 正则命中，预测/建议类**直接拦截不进模型**——既合规又省 token（这是我们域的特征：违规问句其实高度模式化）。
> - **约束侧**：system prompt 铁律 + can/cannot 清单。
> - **能力侧**：工具只读 + 数值全走 Python 算，**模型物理上接触不到账本**，编造的空间被架构消掉。
> - **输出侧**：词法过滤 10 条规则，命中即替换为标准免责话术，**绝不透传越界原文**。
>
> **死循环**：显式 `AGENT_MAX_TURNS` 跨请求计数，超限抛 429 并引导用户改用图表；工具失败只允许 1 次重试。**我不依赖模型自己意识到该停——Agent 的循环必须有外部强制终止条件。**
>
> **成本**：四道闸门①每用户每分钟限流②连续失败熔断③全站日 token 预算④轮次上限。另外一条最有效的不是闸门而是**上下文策略**：工具只回 4~5 个标量，不回全量序列——**一次「半年表现」查询，回传原始 180 条净值 vs 回传 4 个指标，差两个数量级**。

> **线上故障故事（面试必讲）**：*「我的限流和 token 预算最早是进程内字典。上线到 Serverless 多实例后我发现预算被击穿——每个实例各算各的，5 个实例就等于预算是 5 倍。这不是理论推演，是我读自己代码时发现的，已经挂了技术债 issue。修法是把计数器从实例内存搬到数据库/网关。」* ——**这就是帖子说的"线上故障倒逼"，而且它是真的。**

#### 验收
- ✅ 输入「明天会涨吗」→ 被拦截，**不产生 token 消耗**（可看 trace 证明）。
- ✅ 输出侧对越界文本命中即替换，用单测覆盖 R1~R10 正例 + 白名单误伤放行。
- ✅ same-question 追问 N 次触发标准话术。
- ✅ 超过 per-user 配额返回明确错误信封（错误码唯一，符合 `AGENTS.md` 接口契约）。

#### 可裁剪
：`intent_guard` 可先做 B（正则）不做 A（模型分类），省 0.3 d。

### S4｜可观测与评估：把「稳」变成可自证

**目标**：面试帖子里「怎么证明它稳」这一问的**唯一正解**。不吹指标，给可复核的东西。

#### 学（约 30 分钟）

- **trace 该记什么**：`session_id / turn / 意图分类 / 工具名 / 参数（脱敏）/ 上游耗时 / token / 结果状态 / 是否被护栏拦截`。
- **Bad Case 闭环**：发现 → 归因（是 prompt、工具 schema、还是工具实现）→ 改成用例 → 回归。
- **关键节点断言**：工具返回必须含指定字段，否则记异常并触发降级。

#### 做

1. **`agent_trace` 表** + 每轮落一条。**不做 OpenTelemetry**（引依赖 + 接后端，收益与规模不匹配；说清这个取舍本身就是加分）。
2. **评估集**：`backend/tests/agent_eval/cases.yaml`，30 条（含 8 条对抗用例：越界提问、参数缺失、幻觉诱导、恶意注入）。
3. **`scripts/agent_eval.py`**：跑真实链路 → 输出「通过率 / 平均轮次 / 平均 token / 被拦截数」报告。
4. **日志重放脚本**：给一个 `session_id`，把整条对话的 trace 按时间轴打出来。

#### 面试考点与话术

> **Q：怎么证明它稳？**
> 我不给 P99 数字——**我们还没到有统计意义的量级，编个数字一轮追问就穿**。我给三样能当场打开的东西：
> ① **全链路 trace 表**：每轮记意图、工具、参数、耗时、token、结果、是否被拦截。任何一个 Bad Case 我能按 `session_id` 把它整条链路回放出来，**定位到是 prompt 问题、schema 问题还是工具实现问题**。
> ② **30 条回归评估集**（含 8 条对抗用例），每次改 prompt / 改工具 schema / 换模型跑一遍，出通过率。**没有评估集的 prompt 迭代是盲改。**
> ③ **关键节点断言**：工具返回缺字段即记异常并降级，不让残缺数据流到叙事层。
> 我的判断是：**Agent 的可观测性重点不在"性能监控"（那是服务端的活），在"决策链路可回放"**——因为 Agent 的 bug 通常是「模型选错了工具/填错了参数」，而不是「接口慢了」。

#### 投入
0.5 d。**这是性价比最高的阶段**：投入最小，面试权重最大。

### S5｜协议层：MCP / Skill / 多模型（讲判断力，不是讲工程量）

**目标**：回应 #1121 的原题（引入 MCP/Skill），并让「工具爆炸」「聚合网关」这些高频考点有实物质证。

#### 学（约 60 分钟，可只讨论）

1. **FC vs MCP 的工程本质**：FC 是**无状态同步循环**（每轮 schema 占 context、不可跨进程复用）；MCP 是**有状态长连接**（JSON-RPC 2.0 over stdio/SSE）+ `list_tools` 能力发现（工具跨进程被发现、不占主对话 context）。
2. **工具爆炸（Tool Explosion）的第一性原理**：`工具数 × ~200 token`，2 万个 ≈ 400 万 token → 装不下也选不准。**解法不是更大的窗口，是"工具的 RAG"——按意图检索 top-K 注入。**
3. **什么规模才需要工具检索**：这是我们该讲清的判断——`<20` 个工具全量注入完全够（我们现状）；`20~200` 靠分域/分组 + 提示词收敛；`>200` 才需要语义检索 + 层级召回（先检索应用，再检索动作）。
4. **Provider 抽象的边界**：统一 `chat / chat_stream` 契约，翻译各家差异；路由策略（高价值任务走强模型，摘要/压缩走便宜模型）；failover。

#### 做（按优先级，只做前两项）

1. **MCP server（stdio）**：复用 `TOOLS_METADATA` + `ToolExecutor`，**只加一层协议适配**——这本身就是「同一份 schema 双协议暴露」的直接证明。用 Cursor / Claude Desktop 连上，截一张「AI 客户端调用我自家工具查到我的真实持仓」的图。**这是全套材料里最有说服力的一张图。**（注：`mcp>=2.0.0` 已在 `backend/pyproject.toml`，零新增依赖。）
2. **Skill 目录**：`docs/skills/*.md` 放流程型知识（如「基金诊断流程」「持仓体检流程」），Agent 按意图加载。**关键是要能讲清 Skill 与 Tool 的区别**：**Tool = 原子能力（能干什么），Skill = 流程知识（该怎么干）**。这是 MCP 生态里最常被问的区分点。
3. **多模型 Provider 适配**：`llm.py` 抽 `Provider` 协议 → 加 DeepSeek 第二实现 + failover。**挑战性任务走强模型、压缩/摘要走 mini** → 这就是「按任务价值分配预算」的最小实现。
4. **工具检索：不做**（工具 <20），但**要能答**（见上第 2 点）。
5. **不做 One API / 自建网关**（无多租户、无计费需求）。

#### 面试考点与话术

> **Q：Function Calling 和 MCP 都做？为什么不全用 MCP？**
> 分层。**同一份底层 schema，两套协议适配**：FC 适配我们自研的 Agent 循环（闭环快、可控）；MCP 让 Claude / Cursor 这类标准客户端即插即用（工具有状态、可发现、跨进程复用、不占主对话 context）。**两套只差协议适配层，schema 是单一真相源。**
>
> **Q：工具爆炸你们怎么处理？**
> 我们现在 **5~10 个工具，全量注入是正确选择**——为 10 个工具上向量检索是过度设计，这是明确决策不是遗漏。我的判断阈值是：**超过 200 个工具才需要语义检索 + 层级召回**（先按应用粗排，再在应用内精排动作）。到那时的瓶颈不在模型窗口，在**工具描述的 embedding 质量**——工具描述写得像人话、说清"什么时候用我"，比换更大的模型更有效。

#### 投入
1 d（**只做 MCP 则 0.4 d**）。**可完全裁剪**——但裁掉后「FC vs MCP」这道高频题只能空谈，建议至少做 MCP server。

### S6｜面试收口：话术固化 + 压力测试

**目标**：把六个阶段的事实，压成能在高压下说出口的答案。

#### 做

1. **三段式改稿**：每个阶段提炼成「**规模约束 → 工程决策 → 权衡**」。例：
   - 规模约束：个人投资记账工具，用户量小但**金融数值不能错**。
   - 工程决策：Agent 只读 + 数值全走 Python 算，模型只做转述。
   - 权衡：牺牲了"模型自由发挥"的表达力，换来**每个数字可溯源**；代价是工具做得更细。
2. **12 条追问压力测试**（见 §6.2），逐条写下答案，**限时 90 秒口述**一遍，卡壳的就是没想清。
3. **30 秒自我介绍**（基于真实事实，**零编造**）：

   > 我做了一个投资记账工具的 AI 助手，形态是「工具型 Agent」而不是文档问答。核心难点是**金融场景不能容忍数值幻觉**，所以我把架构切成两层：**数值全部由后端的确定性工具算（XIRR、最大回撤、持仓聚合），模型只负责选工具和把指标转成人话**——模型物理上接触不到账本，编造空间被架构消掉。工程上我做了双动作对话循环（追问收敛 / 工具执行）、工具参数 schema 校验与错误回填重试、四道成本防护（限流/熔断/token 预算/轮次上限）、三层合规护栏，以及全链路 trace + 30 条回归评估集。同一份工具 schema 我还以 MCP server 暴露给标准客户端。**我踩过的最典型的坑是：为了省服务端状态把会话交给前端持有，结果只校验了字段名没校验取值——一旦工具接受账户 id 就是越权。**

4. **准备 2 个「我改过的东西」的故事**：P1（越权）与 P3（多实例击穿）。**这两个故事是你区别于"只跑通正常路径"的人的地方。**

## 7. 只学不做的理论清单（被追问时答得上即可）

| 主题 | 一句话理解 | 为什么不做 |
|---|---|---|
| 工具 RAG / 工具爆炸治理 | 工具数 × schema token 超窗口 → 按意图检索 top-K | 我们 <20 个工具，全量注入正确 |
| 多 Agent 协作（规划/检索/执行/校验） | 把单 Agent 的隐式推理拆成显式角色 | **两个状态的循环用 230 行就够了**，四 Agent 是话术不是需求 |
| 长上下文工程（KV cache / 位置插值） | 窗口越长越贵越不准 | 与我们的问题无关：我们靠"工具只回标量"控制上下文，不靠窗口 |
| 评估框架（Ragas / LangSmith / promptfoo） | 让 prompt 迭代可量化 | 30 条 YAML + 一个脚本已能覆盖；引框架要接平台 |
| OpenTelemetry / 分布式 trace | 跨服务链路追踪 | 我们单进程 + 已有 trace 表；接 OTel 前端后端成本 > 收益 |
| 向量数据库（Milvus / ChromaDB） | 语义检索的存储层 | 无 RAG 需求，无检索量 |
| 向量 Embedding 接口 | 把文本转向量 | 同上；且境外 Embedding 服务有合规与网络风险 |
| 微调 / LoRA / 本地推理 | 用自有数据改模型权重 | 无标注数据、无算力、无必要 |

## 8. 反过度设计清单（明确不做）

| 不做 | 理由 | 真到什么时候才做 |
|---|---|---|
| **LangGraph / CrewAI / Dify** | 现有 `agent_loop.py` 230 行覆盖 clarify + 重试 + 叙事；引框架 = 引依赖 + 学曲线，收益 0。**面试讲"我用 230 行自研状态机替代 LangGraph，因为只有两个状态"比"我用了 LangGraph"更能证明你懂** | 状态数 >5、需要持久化工作流与人工审批节点时 |
| **Celery / 消息队列** | 我们已有 APScheduler；Agent 是请求-响应式，无长耗时推理 | 出现 >30s 的异步生成任务时 |
| **MySQL / 分库分表** | 规模不成立 | 不适用（我们走 Turso/Supabase） |
| **Redis（先不引）** | 会话与限流先落 DB 表（复用 `user_usage` 模式），DB 足够；多一个中间件多一个运维面 | 真到 DB 写瓶颈时 |
| **One API / 自建 LLM 网关** | 无多租户、无计费、无 Key 池化需求 | 出现对外提供 AI 服务或用户自带 Key 时 |
| **向量数据库 / ChromaDB** | 无检索量 | 工具 >200 或真做知识库时 |
| **自研计费/积分体系** | 无支付后端（#1002 未做），先做会空转 | 支付上线后 |
| **多租户隔离层** | 现有 `family_id` + 鉴权已够 | — |
| **伪造性能指标** | **绝对红线**：没有压测就没有数字 | 有真实流量 |
